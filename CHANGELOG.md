### Added

- OBS-001 "Platform Observability & Alerting" (Phase B, P0 — **no business behaviour changed, no query added to any business endpoint**): operators can now determine platform, consumer, projection, notification, payment, and security health **without reading application logs**. The layer is built around this platform's actual failure shape: it is event-driven, so collection can commit and then every downstream step — outbox, consumer, notification, receipt, projection — can stop *while the API keeps answering perfectly*. That is the dangerous state, so `background_workers` is a first-class health component, consumer lag is a headline metric, and every alert names the business consequence rather than the technical symptom. **Metrics:** all 50 metric families centralized in `core/metrics.py` — previously scattered across four modules, which is how a metrics surface becomes unreviewable — with a **cardinality rule enforced by a test** (labels are bounded vocabularies, never identities; a `tenant_id` label would multiply every series by the customer count, which at 1M dairies is existential). New coverage for payments, receipts, offline sync, pricing, settlements, auth/authz failures, rate limiting, JWT verification, projection lag/drift, notification provider latency, and per-component health. **Bug found and fixed:** HTTP metrics labelled the router-relative path, silently dropping the `/v1` prefix — a future v2 API would have collided into the same series; labels are now the templated full path, so an id can never leak in. **Correlation (BR-0024):** one id flows request → outbox event → consumer → notification/receipt, with the consumer now *rebinding* it into its log context — the link that was missing, exactly where a chain crossing a process boundary needs it most. **Health:** a four-level model (healthy/warning/degraded/critical) across eight components, overall status = **worst** component (averaging hides outages), a failing probe becomes `critical` rather than a 500, and **degraded stays ready** because pulling a degraded instance removes capacity that still works without fixing anything. **Alerts:** 12 rules declared once and driving both the operator API and the generated Prometheus rules, so pager and dashboard cannot disagree; every rule carries an **action** — a test enforces it, because a rule without one is a notification and notifications train operators to ignore alerts. Thresholds document the judgement behind each number. **Operator API:** `/v1/_ops/overview` (the first screen), `/health`, `/alerts`, `/alert-rules`, plus consumer **pause/resume** through the same config kill switch the runner already reads — one switch, not two that can disagree. **Tracing:** OpenTelemetry supported but not required — spans are no-ops unless the SDK is installed *and* an exporter configured, and configured-but-uninstalled warns loudly rather than implying instrumentation that is not happening; correlation works with or without it. **Artifacts:** 7 generated Grafana dashboards, Prometheus scrape config, and alert rules generated from the platform's own definitions. New `docs/03-architecture/06-operations/` layer: [OBSERVABILITY](docs/03-architecture/06-operations/OBSERVABILITY.md), [METRICS](docs/03-architecture/06-operations/METRICS.md) (generated from the registry), [ALERTING](docs/03-architecture/06-operations/ALERTING.md), [TRACING](docs/03-architecture/06-operations/TRACING.md), [DASHBOARDS](docs/03-architecture/06-operations/DASHBOARDS.md), [RUNBOOK](docs/03-architecture/06-operations/RUNBOOK.md). 39 new tests (727 collected: 718 pass locally, the 9 PostgreSQL RLS tests skip without a database); no existing test weakened. **Two defects found by running it for real:** the `component_health` gauge — which every alert rule reads — was only populated when an operator opened the ops API, so the alerts would have stayed silent precisely because nobody was watching; a health sampling loop now populates it unattended. And the projections probe read fields that do not exist on `ProjectionStatus`, so it reported `critical` for a healthy projection; a test now asserts no probe raises against a working platform.
- SEC-001 "Production Security Hardening" (Phase B, P0 — **no business behaviour changed**): the platform's trust boundaries hardened for an enterprise security review. **JWT/RS256 with rotation:** tokens are signed RS256 from a key registry and carry the signing `kid`; verification resolves exactly that key — an unknown, retired, or expired kid is a rejection, never a fallback, and never an algorithm taken from the token's own header (both `alg: none` and HS256-signed-with-the-public-key are proven rejected by hand-assembled forgeries, since PyJWT refuses to build them). Rotation is **additive**: a new key signs while every unexpired predecessor keeps verifying, so no live session is invalidated; retirement kills every token a key signed, at once — the emergency lever. Public discovery at `/.well-known/jwks.json` (active keys only; a retired key is never advertised as trustworthy) and an operator view at `/v1/_security/keys` that cannot return private material. HS256 survives only as a documented rollback path, refused in prod without an explicit secret. **PostgreSQL Row Level Security (BR-0022):** every tenant-owned table gets a policy comparing `tenant_id` against a `SET LOCAL` session variable — transaction-scoped, so a pooled connection cannot carry one request's tenant into the next — with `WITH CHECK` as well as `USING` (without it a caller could move a row *into* another tenant, succeeding silently) and `FORCE` (without it the application, which connects as the table owner, bypasses its own policies). An unbound session matches nothing and fails **closed**; cross-tenant machinery uses an explicit, logged, transaction-scoped bypass rather than a superuser connection. Application filters stay as defense-in-depth. **The table list is derived from metadata, not hand-maintained** — the drift test immediately caught three projection tables that register at consumer discovery rather than at import. SQLite has no RLS, so policy *execution* is proven by a new PostgreSQL CI job whose **skip fails the build**. **Headers/CORS:** nosniff, DENY framing, no-referrer, deny-all Permissions-Policy, `default-src 'none'` CSP, and `no-store` (a shared proxy caching one tenant's data is a leak with extra steps); HSTS opt-in because a browser honours it *after* a rollback; CORS narrowed from wildcard methods/headers to explicit lists, never reflecting an origin. **Rate limiting:** Redis fixed-window, one round trip (INCR+EXPIRE pipelined), on login, refresh, password reset, invitation acceptance, notification preview, projection rebuild, and consumer replay; credential endpoints keyed per-IP **and** per-identifier because credential stuffing and distributed brute force are different attacks and a per-IP budget catches only one. 429 carries structured retry data and a `Retry-After` header. **Fail-open by default and deliberately** — a dairy must not stop accepting milk because a cache is down — with fail-closed one setting away. **Secrets:** nothing sensitive in source (a test greps for committed PEMs); production *refuses to start* on a dev default, a debug flag, or wildcard CORS. **Audit (BR-0023):** login success/failure, refresh, reuse detection, logout, password reset, permission denial, key rotation, and rate-limit violation land in the same immutable trail as business events and mirror to the log stream, so an attacker who reaches the database cannot erase what already left the host. New security documentation layer `docs/03-architecture/05-security/`: [SECURITY](docs/03-architecture/05-security/SECURITY.md), [THREAT-MODEL](docs/03-architecture/05-security/THREAT-MODEL.md) (12 threats, each with residual risk and its proving test), [JWT-ROTATION](docs/03-architecture/05-security/JWT-ROTATION.md), [RLS-GUIDE](docs/03-architecture/05-security/RLS-GUIDE.md), [SECURITY-CHECKLIST](docs/03-architecture/05-security/SECURITY-CHECKLIST.md) (pre-production gate, monitoring signals, incident response). Migration `a1c7f3b90e22`; new dependency `pyjwt[crypto]`; 41 new security tests plus 9 PostgreSQL RLS tests (688 collected: 679 pass locally, the 9 RLS tests skip without a database and are run by the CI job whose skip fails the build); no existing test weakened and no API contract changed.
- OFF-001 "Offline Collection Sync" — the last Phase A item, and the field prerequisite: the operator app now collects milk with **no connectivity at all** and reconciles when it returns, without forking a single business rule. **Offline is a transport problem, not a business one** (BR-0021; register v1.8): every operation captured on a device is applied, on sync, by calling the same `MilkCollectionService` method the online API calls, with the same principal, tenant context, and state machine — a step the engine refuses online is refused offline, an archived supplier is still archived, a closed session is still closed. The device is a **recorder, not a decider**: it never prices milk, never validates identity, never advances a state on its own authority, and reports platform-owned values as `pending_sync` rather than guessing; a 409 is an *answer* and is rethrown unchanged, so only transport failures fall back to the queue. **Flutter**: a new `offline/` layer — an `OfflineStore` port with an in-memory adapter and a file adapter that writes-then-renames (atomic, so a crash leaves the previous complete queue or the new one, never half a morning); a durable `SyncQueue` (PENDING/SYNCING/SYNCED/FAILED/CONFLICT, attempts, exponential backoff capped at 5 min mirroring the platform's own consumer schedule, local→server id map, last sync timestamp, conflict metadata) surviving app restart, device reboot, and crash — operations stranded in SYNCING by a process death are recovered on load because replay is idempotent; a `SyncEngine` with batch upload, automatic retry, progress, cancellation honoured *between* batches (work already in flight has its outcome applied first), and resume; and an `OfflineApiClient` that intercepts the collection calls so **the wizard is unchanged** — the operator's flow is answered from a projection folded over the queue. **Backend**: a new `sync` module whose service is explicitly a transport (`_dispatch()` routes each kind to the online service; if a business decision ever appears there, the design has failed), with client-generated `operation_id` as the idempotency key — a lost acknowledgement re-sends without doubling a collection — and `client_reference`/`target_ref` local ids resolved to server ids **across batches and persisted server-side**, which is what makes an interrupted sync resumable rather than restartable. Conflicts are structured and never silently overwritten: `already_accepted`, `supplier_unavailable`, `session_closed`, `unresolved_reference`, `invalid_state`, and `rate_card_changed` — the last of which **applies anyway**, because milk is perishable and MVP-001 forbids blocking a collection on pricing, so the collection stands and the divergence is flagged. Offline never bypasses authorization: the sync endpoint reuses `collection.transaction.record`. 4 endpoints under `/v1/sync`; 1 new permission (`sync.read`, read-only monitor); migration `e8845cde90c0`; 26 new backend tests (638 total) and 19 new Flutter tests (49 total) covering offline collection, restart, queue persistence, crash recovery, duplicate replay, idempotency, network loss, partial sync, conflicts, retry, batch upload, cancellation, and cross-tenant isolation. New reference: [Offline Collection Sync](docs/03-architecture/04-technology-layer/OFFLINE-SYNC.md). Portal: read-only /sync monitor (per-device activity with last-sync age, outcome filters, conflict explanations in operator language, failed-item retry, statistics). Flutter: offline banner, sync status screen with queue/pending/failed/conflict counts, retry, cancel, last successful sync, and a conflict detail screen. `payment.completed.v1` unchanged; no existing test modified.
- RCP-001 "Receipt Engine" — the artifact a farmer can hold. A new `receipt` module whose Receipt aggregate owns ReceiptLines (one per settlement the payment covered). Receipts are **generated only by consuming `payment.completed.v1`** off the durable log — never requested by a business module, never issued for a draft, failed, or cancelled payment — and one completed payment produces exactly one receipt, enforced by a unique `(tenant, payment)` constraint so consumer replay re-finds the artifact instead of handing a farmer a second one (BR-0020; register v1.7). Because the content is frozen, the receipt **copies** what it shows (supplier name and code, payment reference and method, settlement numbers, centers, periods, amounts) at generation time: re-deriving later could show a different world, and a receipt must show the world as it was when the money moved — proven by a test that renames the supplier afterwards and asserts the receipt is unchanged. Lifecycle generated → delivered → archived is the ONLY permitted mutation (CAS-guarded); archived receipts stay fully queryable, listable, and renderable, and the module has no update or delete path at all — a test asserts DELETE/PUT/PATCH are 405. **Rendering** is a pure derivation of the immutable record, so nothing is stored and any format re-derives identically forever: a `ReceiptRenderer` Protocol with a registry mirroring the NOT-001 provider abstraction ships `json` (canonical), `html` (self-contained — no external stylesheet, font, image, or script, because a village printer has no connectivity), and a **PDF placeholder** that announces itself as one (`placeholder: true` surfaces as a badge in the portal and a card in the app) so a download never quietly pretends to be a real PDF; **no PDF engine or external service is integrated**, and a deployment swaps one in with a single `register_renderer` call. An unsupported format is a 422 business exception, not a 500. `payment.completed.v1` was enriched (payee name/code, per-settlement centers, periods, and totals) so the consumer never calls back into the payment, settlement, or supplier modules — the same producer-enrichment pattern NOT-001 established; re-reading finalized settlements is safe by BR-0010. Three events (`receipt.{generated,delivered,archived}.v1`); the notification engine consumes `receipt.generated.v1` through a new `receipt_available` template (English + Swahili). 6 endpoints under `/v1/receipts`; 3 permissions (read/manage/download); migration `76b51e9e9990`; 41 new tests (612 total) covering automatic generation, multiple settlement lines, partial payments, duplicate prevention, numbering, immutability, the rendering abstraction (including renderer swapping), history, events, permissions, pagination, and cross-tenant isolation. New reference: [Receipt Rendering](docs/03-architecture/04-technology-layer/RECEIPT-RENDERING.md). Portal: /receipts section (history with search/status filters/pagination, detail with settlement lines and trace, live JSON/HTML/PDF preview with a sandboxed HTML frame, and a blob download that carries the bearer token). Flutter: receipt history, detail with preview format chips, and a download placeholder that copies the artifact and says plainly that no PDF engine exists (2 new widget tests, 30 total).
- PAY-001 "Payment Execution Engine" — the money finally moves (as a record): a new `payment` module whose Payment aggregate owns PaymentLines (the allocation against each settlement) and PaymentAttempts (the execution history). **Payments consume settlements and never modify them** — only a FINALIZED settlement is payable, allocations belong to one supplier and one currency, and the settlement side stays untouched (BR-0018). **Outstanding balance is always computable**: payable − live allocations, where draft/pending/processing/completed all RESERVE (a draft is an intent that must stop a second payment claiming the same money) and failure/cancellation release — which is what makes partial payment, remaining balance, and duplicate prevention one rule instead of three. The balance list joins allocation sums in SQL and filters/paginates in the database, so a growing payables ledger is never fetched whole. **Lifecycle** draft → pending → processing → completed (immutable) with failed (retryable) and cancelled (terminal); every transition CAS-guarded; cancelling a *processing* payment is deliberately refused because money may be in flight and the truthful sequence is fail-then-cancel; every execution opens a NEW attempt row (number, provider, reference, operator, timestamps, failure reason) so a payment's failure history survives its success (BR-0019; register v1.6). **Idempotent execution** via a client-supplied `idempotency_key` unique per tenant: re-posting returns the existing payment instead of paying twice. Payment methods (BANK_TRANSFER, CASH, CHEQUE, MOBILE_MONEY) are **metadata only** — no gateway, no bank integration, no provider SDK, no credentials anywhere. Six events through the outbox (`payment.{created,processing,completed,failed,cancelled,retry}.v1`); `payment.completed.v1` closes the loop NOT-001 left open — the notification engine consumes it **unchanged** and finally has a producer for its `payment_completed` template (a multi-settlement payment names itself, since one payment means one message). `Money.minus` added to the platform VO with the same exactness story as `plus`. 10 endpoints under `/v1/payments` (+ `/v1/settlements/{id}/balance`); 4 permissions (read/manage/retry/cancel); migration `96442d50d1f5`; 57 new tests (571 total) covering partial payment, multiple settlements, duplicate prevention, retry, cancel, failure, outstanding balance, event emission, permissions, history, pagination, idempotency, concurrency, and cross-tenant isolation. Portal: /payments section (outstanding-balance selector with pay button, partial-amount form, history with status/method filters + search + pagination, detail card with allocations, attempt log, and lifecycle actions). Flutter: read-only payment history + detail with the attempt log (2 new widget tests, 28 total) — the device never executes a payment.
- NOT-001 "Notification Engine" (Phase A — no push, no production provider): messaging becomes a **consumer of the event log** rather than something modules call. Every producer lost its notifier (`auth`, `organization` no longer hold one at all) and instead emits a durable event carrying what a message would need (email/locale/expiry, supplier name/phone/locale, settlement currency, rejection reason); the new `notification-dispatch` consumer maps 8 events onto templates, and a `notification-recipient-directory` **projection** (replay order 5, rebuildable per BR-0015) supplies phone/email/locale so the dispatcher never calls back into a business module. A rolled-back transaction can no longer notify anyone, a provider outage can no longer fail a milk collection, and an unsent message is always replayable (BR-0016). **Templates**: `(key, channel, language)` with variables derived from the body — rendering with a missing variable is an error, never a half-substituted message; language falls back to the platform default so a market can ship one locale at a time (Swahili ships for supplier-registration and settlement-finalization). Nothing is hardcoded. **Providers**: a one-method `ChannelProvider` Protocol with `LoggingProvider` (delegates to the existing notifier port) and `PlaceholderProvider` — **no SES, no Twilio, no credentials anywhere**. **Delivery lifecycle**: idempotent on `(event_id, template_key, channel)` so duplicate consumption and consumer replay re-examine rather than resend; delivery failure is a property of the notification, not the event (raising would roll back the very history this module keeps), so the notification row owns its retry using the consumer framework's `backoff_delay`/`MAX_CONSUMER_ATTEMPTS` — failed → backoff → retry → dead, swept by the background loop and forceable from the API (BR-0017; register v1.5). **Framework fix:** `registered_consumers()` now orders projections (by replay order) ahead of plain consumers — read models are inputs to other consumers, and alphabetical import order had dispatch running before the directory that feeds it. 7 endpoints under `/v1/notifications` + `/v1/notification-templates`, 2 permissions; migration `5d394226efec`; 37 new tests (514 total). New reference: [Notification Engine](docs/03-architecture/04-technology-layer/NOTIFICATION-ENGINE.md); the technology-layer index (empty since the layer was created) now lists it and the PLT-001 reference. Portal: /notifications section (delivery stats, status/channel/template filters, search, pagination, inspect card with rendered text + originating event payload, retry, retry-all-due, and a template catalog with live preview). Flutter: read-only notification history + detail (2 new widget tests, 26 total) — no push registration, the device never sends.
- PLT-001 "Projection Lifecycle & Replay Framework" — projections become first-class platform infrastructure ahead of Notifications/Offline/Analytics/AI read models. A `Projection` IS an `EventConsumer` (one declaration, both roles), so it keeps every consumer guarantee and adds: **metadata** (name, version, owning module, description, source events, rebuild strategy, replay order, owned models); **auto-discovery** reusing the single consumer import path; a **registry** (`GET /v1/_projections`) whose status is DERIVED — position from the cursor, processed counts from the ledger, pending from the log, row counts from the tables — so it can never drift; a **rebuild engine** replaying the outbox log (never transactional tables) for one/all projections, batched with per-batch commits, live progress + ETA, and cancellation honoured between batches; **reset** (rows + cursor + ledger, after which the ordinary consumer loop rebuilds naturally); **dry run** reporting work and an ETA measured from the previous rebuild's real rate; **versioning** — a bump marks stored data `outdated` until a *completed* rebuild claims the new version (cancelled/failed claim nothing); and **integrity verification** — version, corrupted replay, missing events, dead letters, duplicate natural keys (read from each model's own unique constraint), ledger gaps, plus optional **drift detection** by shadow-replaying into a transaction that is always rolled back. Because replay uses the projection's own handler, a rebuilt projection cannot diverge from an incrementally-built one (BR-0015; register v1.4). Ops API: `GET /v1/_projections`, `GET|POST /{name}[/rebuild|/cancel|/verify]`, `POST /rebuild-all`, `DELETE /{name}/reset`. The reporting projection now declares full metadata. New reference: [Projection Lifecycle & Replay](docs/03-architecture/04-technology-layer/PROJECTION-LIFECYCLE.md). **Latent bug fixed:** consumer discovery ran *after* `create_all`, so projection tables were only created if another import happened to register their models first — discovery now runs first. Engineering review: the statement-counting test helper (copied in three modules) collapsed onto `tests/conftest.count_statements`. Migration `aa742d7b6987`; 40 new tests (477 total).
- SPRINT-008B "Event Consumer Framework" — the receiving half of the Relay: consumers read the DURABLE OUTBOX LOG (per-consumer cursors over (created_at, id), not the transport) with an idempotency ledger (`consumer_execution`, unique consumer+event — also the execution history and the consumer-side DLQ), strict per-consumer ordering, exponential-backoff retries (reusing the relay's backoff), poison-message dead-lettering after 5 attempts (cursor advances past poison; dead executions replayable with a fresh budget), per-event isolated transactions (handler writes + ledger + cursor commit atomically; failures roll back the handler and are recorded out-of-band — BR-0013: consumers NEVER affect business transactions; BR-0014: at-most-once per consumer; register v1.3), automatic discovery of the independent `platform_core.consumers` package at startup, per-consumer config kill switch (`platform.consumers.<name>.enabled`), Prometheus metrics (processed/failed/retried/dead/latency/lag), background consumer loop, and the `/v1/_consumers` ops API (status/health with lag, run, executions, dead-letters, replay). Two production consumers: **notification-placeholder** (internal notifications through the notifier port — no SMS/email yet) and **reporting-projection** (daily/center/supplier totals projection tables maintained purely from event payloads — the scale path REP-001 promised). The `collection.transaction-completed.v1` payload enriched for consumers (center/supplier/weight/amount/currency/rejected) and milk events gained aggregate metadata. Engineering review fixes: `require_current_tenant()` extracted to core (was copied in 11 services), `envelope_from_outbox()` dedup, evidence-backed `ix_outbox_consume` index. Migration `d34a2e05d4e3`; 25 new tests (437 total).
