Three answers: `reachable`, `unreachable` (`phone_missing`, `invalid_phone`, `email_missing`), `unknown` (`whatsapp_unknown`, `provider_unavailable`, `no_supported_channel`). **WhatsApp is never `reachable`** — a phone number is not a WhatsApp account, nothing here can ask a gateway, and the same number IS reachable by SMS, which is the whole point of the distinction. **A disabled channel blames the deployment, not the farmers**: `provider_unavailable` is `unknown`, never `unreachable`, because listing 250 blameless farmers as unreachable would bury the one fact an operator needs. The phone check is deliberately permissive — a false *invalid* accuses a record of being wrong and sends someone to fix what is fine, while a false *valid* lets the send fail visibly where failure is already handled. Contacts are masked. **It blocks nothing**: a test strips a farmer's phone number BEFORE finalizing and requires the settlement to succeed, because money and communication are separate domains — the point of counting the unreachable is that somebody sees them, and nobody is silently skipped (every affected recipient is named, and when the list is capped the response says so). - DEMO-027 "Commercial Foundation II: Subscription Payment & Activation" — a subscription can now go from trial to active **because a payment provider said so**, and Lacteva still cannot take money, because no provider has been contracted. Both halves of that sentence are the milestone. **The survey found two things that shaped everything.** `modules/payment/` is NOT this and must not be extended — it is PAY-001, the operational engine paying farmers against finalized settlements, and its own docstring declares the scope wall (no gateway client, no provider SDK, no credential handling); a dairy's money and Lacteva's money share a word and nothing else, so the separation here is physical rather than conventional, and two tests hold it up (dairy `payment`/`settlement` counts are asserted unchanged across a complete SaaS payment, and the subscription module is asserted never to import either). `amount = quantize_money(unit_price × centres, organization.currency)`, with the unit price from `subscription.price.<PLAN>.<CURRENCY>` in the existing config store and **no price in source**, so an unpublished (or zero, or negative) price refuses the checkout rather than opening one for nothing. *The provider owns the confirmation*: nothing activates a subscription except an outcome the provider itself reported, the reported amount and currency are compared against the stored intent and a mismatch is refused and recorded, and `/checkout/refresh` **takes no arguments** — a browser back from a hosted checkout knows only that something may have changed, never what. *A repeat is not a second event*: one open payment per organization (`uq_subscription_payment_open` on `(tenant_id, open_key)`, nullable so NULLs do not collide and the constraint is portable to SQLite), one payment per provider reference, one action per provider event id, and a CAS `UPDATE … WHERE status = 'pending'` for the terminal transition. **The webhook is the platform's only unauthenticated write path** and is built accordingly: constant-time HMAC over the raw body, tenant resolved from *our* stored row and never from the payload (a test forges a body naming a second tenant and asserts that tenant is untouched), no payment ever created (an unknown reference writes nothing, so the endpoint cannot be used to fill a table), 200 for replays and unknown references because a gateway reads non-2xx as "retry", and 401/404 that never say which check refused. It runs on a `PlatformSessionFactory` and sets the tenant contextvar around the work, because `EventEnvelope.new` reads it and publishing without it would write outbox rows belonging to nobody — the defect class DEMO-025 found. It is deliberately **not** an `IdempotentRoute`: that keys on a client-supplied header and a gateway sends its own event id instead. **`past_due` now exists**, and the reason it did not in DEMO-026 is the reason it does now — it is reachable only from a signature-verified renewal failure, never from a client and never from a timer. It **operates**: access continues to `grace_ends_on` (14 days, configuration rather than a constant, because it is commercial policy), since on the other side of a declined card is a dairy with milk arriving. Nothing is destroyed at any state: no data deleted, no user removed, no administrator locked out, `can_read` always true. **Provider research, and no vendor was contacted:** the structural finding is that no single provider serves India and Kenya well — India's practical recurring rails are UPI AutoPay and e-NACH, Kenya's is M-Pesa with no native subscription concept, and the international providers with the best subscription primitives fit both worst — so the recommendation is to plan for two providers side by side, which is why the webhook route is addressed per provider and both unique constraints are provider-scoped. - **WAL archiving had been dead for eighteen hours, silently.** `cp` is not
  atomic; a copy interrupted at 2026-08-12T17:41Z left 3.3MB of a 16MB segment
  at the destination, and `test ! -f` then saw a file and retried the same
  segment every second thereafter. 58 segments and 945MB queued in `pg_wal` on
  the database's own disk, point-in-time recovery holed across the window, and
  no alert — PostgreSQL logs a warning and keeps serving. Very likely the
  mechanism behind DEMO-009's two disk-full events. `archive-wal.sh` writes to
  a temp file and renames, treats a byte-identical file as success, and
  refuses a same-name-different-content collision rather than destroying a
  recovery point. The truncated segment was quarantined, not deleted; the
  archive drained 58 → 0 and fell from 3.1GB to 97MB once pruning ran.
- **The physical backup could never have worked** — three defects, none seen
  because the unit had never executed: it ran on the host and the database
  port is deliberately not published; `--format=tar` cannot be verified in
  place by `pg_verifybackup` on PostgreSQL 16, so its own verification step
  contradicted its own backup step; and the manifest digest was written INSIDE
  the backup directory, making every later verification report a spurious
  error. Also: a failed run left a directory that looked exactly like a
  recovery point.
- **The nightly script reported catastrophe on success.** A container path was

- DEMO-009 "Customer Management & Sales" — the receivable half of the business,
  and the workflow waiting dairy customers asked for by name: **customer →
  delivery → daily report → monthly bill → payment → receipt**. Built as three
  new bounded contexts under the governed CAP-0006 (CMA) capability — `customer`
  (SLS.02 Buyer Relationship Management), `delivery` (DST.01 Distribution &
  Fulfillment) and `billing` — and deliberately **not** a reuse of the
  procurement tables. The direction is the whole reason: a settlement is what
  the organization owes a supplier and a payment is money going *out*; an
  invoice is what a customer owes the organization and a customer payment is
  money coming *in*. Reusing settlement/payment would have produced a payment
  whose "supplier" is a customer and an outstanding balance meaning the
  opposite of what it says.
- **Delivery pricing comes from the customer's agreed plan, never the client.**
  A `DeliveryPlan` carries the selling rate; the delivery call takes a
  quantity and the domain computes `quantity × unit_price` once, in `Decimal`,
  and stores it. The pricing engine was deliberately not reused: it prices
  *procurement*, resolving a rate card by centre and quality band because what a
  cooperative pays a farmer depends on the fat in the churn. What a customer
  pays is an agreed price (CMA.PRI.02), and pushing it through the fat-band
  matrix would have produced a number nobody agreed to. A rate change
  supersedes the plan rather than editing it, so a delivery priced last week is
  still explainable.
- **The daily delivery report**, aggregated in SQL — headline totals, customers
  served, skipped days, and a per-day breakdown over any window. The delivery
  list's totals cover the whole filtered set rather than the visible page.
- **Monthly billing that reconciles exactly.** An invoice is generated *from*
  unbilled deliveries, its lines are copies of those rows, and generating it
  stamps each delivery so the same milk cannot be billed twice. It carries the
  customer's brought-forward balance. Issuing is irreversible — the same rule
  BR-0010 applies to a finalized settlement — and the detail page shows the
  platform's own `totals_match_lines` answer rather than a sum computed in the
  browser.
- **Customer payments and receipts.** A payment is money already received, so
  it has one state rather than a provider lifecycle; allocations apply it to
  the oldest unpaid bills and leave the remainder as credit. The receipt is

- DEMO-008 "Authentication, RBAC & Permission Architecture" — the foundation
  work order, and the first finding was that most of the foundation was already

- PILOT-F03 "Late Collection Settlement" — the one business defect PILOT-001 found that could cost a supplier real money, traced to root and closed. **Root cause:** three individually-correct rules that are jointly fatal in one arrangement. A collection's business date is the day it is recorded (`tx_date = as_utc(tx.created_at).date()` — there is no back-dating anywhere); nothing stops a settlement being finalized while its period is still running (`STL-2026-000001` covers 2026-07-11→2026-08-10 and was finalized on **2026-08-09**, a day before its own period ended); and a finalized settlement is immutable (BR-0010) while periods may not overlap for a supplier (BR-0009). So every collection recorded on 2026-08-10 landed inside a period that was already closed: it could not join that settlement, could not get one of its own, and `add_calculation()` refused to carry it into a later one. Every door locked, and **no error an operator could act on** — the collection succeeded, priced correctly, showed a normal `COMPLETED`, and simply never appeared on any statement. PILOT-001 left one such collection worth **1,800.00 KES** as evidence. **The rule was discovered, not invented.** BR-0009's own test list already contains `test_adjacent_period_allowed`; `settlement_line` has *always* stored its own `transaction_date`, distinct from the period — so a line whose collection date lies outside the period that pays for it was already representable, needing no new entity, column or migration; and CAP-0007/PEF.SET.01 orders its business events "Settlement Period Closed; **Settlement Computed**", closing the period before computing the settlement. Registered as **BR-0027** (register 1.16 → 1.17): *a late collection is carried forward; a closed period is never reopened to receive it.* **Implementation** — one file. `_assert_line_date_settleable()` admits a line inside its period as before; **always** refuses one dated after it (milk not yet collected cannot be settled); and admits one dated before it **only when a finalized settlement already covers that date** — the precise definition of stranded. A collection whose own period is still open is *not* late and is still refused, so a period's money cannot be scattered across two statements. `collect_period()` lost its lower bound so the ordinary "collect" finds stranded milk, with `add_calculation()` remaining the sole authority on eligibility. **Adjustments were investigated, not invented:** BR-0011 fixes them at zero until the bonus/penalty/tax engines exist and no other legitimate source exists in the domain, so `NO_ADJUSTMENTS` is now a named constant citing the rule and `calculate_totals()` performs `net = gross.plus(adjustments)` through `Money` rather than adding a literal zero — the arithmetic is real, ready for the day adjustments are. **Deliberately NOT done:** forbidding finalization of an unelapsed period. It is the weaker fix — it reduces how often money strands, where BR-0027 makes stranding recoverable in principle — and it would break the legitimate settle-today workflow, so it is recorded as a recommendation rather than smuggled in. **11 new tests, and they were proven to detect the defect: 8 of the 11 fail against the pre-fix service**, the other 3 being regression guards that must pass both sides. - BKP-003 "Execute and Prove Off-Site Backup Replication" — the second of the two remaining pre-AWS blockers, closed to the limit this machine can actually prove. **What existed:** a backup engine that writes a verifiable directory and restores it (DR-001), a nightly shell wrapper that prunes by `find -mtime`, and an `ObjectStorage` port with `put_object` and `presigned_get_url` — **no S3 integration in the backup path at all**, and `/backup/logical` on the same volume as the database. **What was added:** `core/backup/offsite.py`, a replication layer ON TOP of the existing engine rather than a replacement, because DR-001's evidence is worth more than a rewrite. - `pricing_matrix_row.unit_price` migrated **FLOAT → NUMERIC(12,4)**, with before/after verification executed against PostgreSQL 16.2. This was the top data-integrity item left by DEPLOY-001: BR-0005 made all *arithmetic* exact, but exact arithmetic on an inexact input is still inexact — the price was already approximate before the first multiplication, and it is the number every calculation, settlement, payment and receipt descends from. The race is now **executed** against a real engine in `tests/test_payment_concurrency_postgres.py`, together with a **control that removes the lock and asserts the double payment does occur** (2000.00 allocated against a 1000.00 payable); without the control, the passing test would prove nothing. Wired into `infra/ci/postgres-proof.sh`, where a skip is a hard failure. **Executing it properly found a new defect the lock itself had introduced:** `PaymentService.create` acquired settlement locks in CLIENT-supplied order, so two payments allocating the same two settlements in opposite order deadlocked — reproduced against real PostgreSQL as `DeadlockDetectedError` (SQLSTATE 40P01), reaching the operator as a 500 while paying a farmer, and needing nothing more exotic than one supplier with two unpaid settlements. Fixed by sorting allocations by settlement id so every transaction in the platform takes these locks in the same sequence; the new test was verified to fail with a deadlock when the ordering is removed. **A second class of finding: three production defaults were configured to look healthy while doing nothing.** Both notification channels default to `logging`, whose `send()` returns ACCEPTED — so a production deployment that changes nothing renders every message, records every delivery as accepted, keeps every dashboard green, and tells no supplier anything; `prod` now refuses `logging` and `placeholder` on either channel, leaving `dry_run` and `disabled` as the deliberate choices (email must now declare that it has no transport rather than pretend). And `LACTEVA_RLS_ENABLED=false` short-circuited `bind_tenant`, `bind_platform_context` **and** `assert_rls_is_enforceable` alike, so one environment variable both removed the tenant boundary and silenced the startup check that detects a SUPERUSER connection ignoring every policy — now refused in prod. Recorded and **not** implemented, because both touch delicate guarantees and deserve their own work orders: every consumer scans the entire event log with a separate session and commit per skipped event (O(consumers × events), ~240k wasted transactions/day at a modest dairy), and there is still no retention, archival or **tenant-deletion** path, so a pilot customer can be onboarded but not offboarded. Two Critical items block an unattended pilot and neither is a code defect — **the production stack has never been executed** (no Docker, host or `terraform apply` in any environment that has touched this repository, at exactly the maturity the database layer had before VER-001 found fourteen defects) and **backups share the database volume**, so the DR and PITR proofs restore from a copy that may not survive the incident requiring it.

- PITR-001 "Execute and Prove Point-in-Time Recovery" (**no business behaviour changed**): the physical recovery path, executed. This closes divergence #26, open across four work orders, and it was the last major guarantee on this platform that had never been run. **The headline finding is that the capability did not exist:** production had `wal_level=replica` and **no `archive_mode`**, a combination that looks configured for PITR and is not — `wal_level` makes WAL sufficient to replay, `archive_mode` is what makes it leave the server. Without it WAL is recycled in place, the only recoverable point is the base backup, and the documented **5-minute RPO was fiction** (the real RPO was the age of the last logical backup, up to 24 hours) while three documents described PITR procedures that could not have worked. Now configured in `docker-compose.production.yml` with an `archive_command` that **refuses to overwrite** (`test ! -f` first — silently replacing an archived segment destroys the recovery window from that segment forward and nothing reports it), an `archive_timeout` (a segment is archived when it FILLS, not when it is written, so a quiet night would otherwise leave the last transactions unarchived for hours), and a **separate `wal_archive` volume**, because an archive that dies with the data directory recovers nothing. **Four more defects, all found by executing:** (1) `pg-restore-test.sh` ran `alembic upgrade head` on the recovered instance — a physical restore is byte-identical to its source at the target, so migrating it MUTATES the recovered data by applying a migration that point in time never had, during an incident; it now asserts the revision instead. (2) Both scripts read the database before recovery finished: `pg_ctl -w start` returns when the server ACCEPTS CONNECTIONS, which during recovery is "ready to accept read-only connections" — before the target is reached and before promotion — so everything after it talked to a read-only, still-replaying database; both now poll `pg_is_in_recovery()`. (3) The retention prune could delete **every** base backup: `find DIR -maxdepth 1 -type d` matches DIR itself, so `rm -rf` removes the whole backup root; latent rather than active, because it only fires once `base/` is older than the window — which happens precisely when backups have stopped and the old ones matter most. (4) WAL retention was not tied to base-backup retention at all; the archive is now pruned against the **oldest retained base backup** with `pg_archivecleanup`, never against a date, and refuses to prune rather than guess when it cannot find the `.backup` label. **The timeline trap** is documented and closed: a recovered cluster promotes onto a new timeline, and if it archives, `recovery_target_timeline`'s default of `latest` lets the NEXT recovery follow the recovered timeline and overshoot its target with no error; recovered clusters now set `archive_mode=off` and pin the timeline. `./infra/ci/pitr-proof.sh` runs ten steps against a real cluster, **destroys the primary**, and recovers four times — to a timestamp, a transaction boundary (xid), a named restore point, and latest — asserting for each not only what is present but **what must be ABSENT**, which is the difference between proving point-in-time recovery and proving a restore. Money, receipts, 52 forced RLS policies and the schema revision are identical in every recovery. New docs: [PITR](docs/03-architecture/06-operations/PITR.md) and the [PITR-001 report](docs/03-architecture/06-operations/PITR-001-RECOVERY-REPORT.md); DISASTER_RECOVERY, BACKUP, RECOVERY_CHECKLIST, INFRASTRUCTURE and DEPLOYMENT corrected where they said PITR was unavailable. Six new tests, each verified to fail against the pre-PITR-001 configuration. Remaining: replica promotion, an off-host archive, and recovery time at scale.

- **Phoenix Software Engineering Standard** ([STD-0007](docs/00-standards/STD-0007-phoenix-software-engineering-standard.md)) — a permanent engineering directive rather than a work order: it has no scope, no deliverables and no completion, and it outlives whatever work order is in flight. It records the **project identity** (this repository is not a standalone application; it is the flagship product of Phoenix Software), the six operating scales Lacteva must serve in *one* architecture — individual farmers, collection centers, cooperatives, private dairies, milk unions, multi-country deployments — and **fifteen binding engineering principles**. Three of those get expanded treatment because they carry the most weight here. **Principle 6, every production guarantee must be executable:** stated more strongly than the rest because this repository has the evidence for it — VER-001 and DR-001 executed guarantees that were already written, already reviewed and already CI-wired, and found nine defects, four of them fatal (the platform could not serve one request on PostgreSQL; every RLS policy was inert because the application connected as a superuser; every backup aborted on a `time` column; a corrupt backup restored a settlement worth 1.00 instead of 5647.50). So a PostgreSQL guarantee tested only on SQLite is *untested*, a skipped proof is worse than an absent one because it is green, and a proof must show the guard is capable of *refusing* rather than merely present. **Principle 10, reusable platform capabilities over feature-specific implementations:** the Notification Engine rather than an SMS implementation, the Payment Framework rather than a Razorpay implementation — with the counterweight stated, since a capability with one implementation and no second in sight is speculative generality. **Review policy:** when an earlier decision is *objectively* incorrect, document it, correct it, update the documentation, and never preserve a mistake merely because it already exists — the bar deliberately above "I would have done it differently", as when ABR-002 correctly withdrew two of DBR-001's findings. Also establishes a six-dimension **Definition of Done** (implementation, tests, documentation, architecture consistency, operational impact, production readiness) where "considered and not applicable, because …" is a complete answer and silence is not. Wired into the permanent context: [CLAUDE_CONTEXT](docs/ai/CLAUDE_CONTEXT.md) §0 and its reading order, the standards index and precedence rules, `README.md`, `CONTRIBUTING.md` (PR rules and rejection criteria), and `docs/INDEX.md`. **No business functionality was changed** — this increment is documentation and engineering guidance only.

- ARCH-001 "Final Platform Production Readiness Review": an independent pass over every subsystem, reviewed as if the first dairy goes live tomorrow rather than as the author of the code. **Four production problems found and fixed, one of them critical.** (1) **Two concurrent payments could each claim the full outstanding balance of one settlement.** Allocating is a read-modify-write — read the live allocations, compute what is outstanding, refuse anything larger, insert the line — and nothing locked. Under READ COMMITTED a `SELECT sum(...)` takes no locks, so two transactions never conflict: both read the same sum, both see the full balance, both pass the check, and both insert. **The settlement is paid twice, and nothing detects it**, because partial payment is legitimate so no unique constraint can collide. The settlement row is now taken `FOR UPDATE` *before* the balance is read, which serialises payments against that settlement only — two payments to different settlements still run concurrently. (2) **The connection pool was never configured**, four work orders after ABR-002 rated it the highest-probability cause of the first production incident and put it first in the recommended order. The engine took SQLAlchemy's defaults: 5 connections, no `pool_pre_ping` (so a connection killed by a load balancer, a firewall idle timeout or a database failover is handed to a request and fails it — the "mystery 500s after a network blip" every Python service eventually reports), no recycle, and **no `statement_timeout` or `lock_timeout`** (so an unbounded query holds its snapshot and blocks VACUUM across the *whole* database, and a migration needing `ACCESS EXCLUSIVE` queues behind a long read while every subsequent query queues behind the migration — the classic lock pileup that takes an application down during a "safe" deploy). All configured, with sizing derived from a stated budget rule rather than inherited, and a test asserting the workers × pool product leaves headroom under `max_connections` so an operator can still connect during an incident. Because a 30-second request ceiling would have broken projection rebuilds, backups and deep integrity checks the moment it landed, `platform_session`/`PlatformSessionFactory` raise it to 15 minutes for cross-tenant work — **raised, never removed**, since "unbounded" is the condition that made a timeout necessary. (3) **The payables selector had no index matching its filter.** The screen an operator opens to pay people filters `(tenant_id, status='finalized')` and the only usable index started `(tenant_id, supplier_id, period_from)`, so PostgreSQL read every settlement a tenant had ever had to find the handful unpaid — five years of history is ~50,000 rows scanned to locate ~200. (4) **Money had no database-level guard.** The service refuses a non-positive payment; the database did not, in a schema with two check constraints across fifty-seven tables. `amount > 0` closes every path the service layer does not sit in front of. Migration `ced805436869`. **Also verified and found correct:** the outbox writes in the caller's transaction so a rolled-back business change cannot emit an event; the mobile and portal clients against every API change made since API-001 (page-size bounds now 422 rather than a silent clamp — all client limits are ≤100, checked by a test that reads the client source rather than assuming); the CI proof already runs every PostgreSQL-only module. 14 new tests (985 total), including two PostgreSQL tests that stage what SQLite structurally cannot: that the settlement lock genuinely serialises two concurrent claimants, and that the request path carries a statement timeout at all.
- MSG-001 "Production SMS Delivery Adapter": **suppliers can now actually be told.** Until this, the platform rendered every message, dispatched it off the durable log, retried it, and recorded it — and then handed it to a provider that discarded it. A farmer was never told they had been paid. The gap was documented honestly in three places and closing it was the last functional step in the primary business flow. **The adapter extends the NOT-001 abstraction rather than replacing it.** `send()` now returns a `DeliveryResult` — `provider_message_id` (what a support conversation with the gateway quotes), `status`, and `metadata` (segment count, cost, the gateway's own status string; never credentials) — because a bare reference string is enough to write in an audit trail and not enough to operate. **The central finding was not the adapter: it was that every failure was retried.** An invalid phone number consumed five gateway calls and five backoff windows to reach the answer it had on the first attempt; a missing template — a *deployment* fault, not a delivery fault — did the same, burying the real signal under a retry backlog. Providers now state permanence (`PermanentSendError`) and the retry engine honours it, sending those straight to `dead` on the first attempt. **The base error stays retryable**, so every pre-MSG-001 raiser behaves exactly as it did and an unfamiliar provider error is tried again rather than silently dropping a message a supplier is waiting for. A permanent failure is never a silent drop: recorded, counted, visible in the history, and retryable by an operator who has fixed the data. BR-0017 extended (register v1.16). **Vendor neutrality by construction:** `HttpSmsProvider` posts a small documented JSON contract and classifies outcomes by **HTTP status**, which every gateway agrees on even when their payloads do not — 400/401/403/404/422 permanent, 408/425/429/5xx retryable, timeout and network retryable. Dairy markets differ by country and a deployment may change provider without touching code; a gateway whose shape does not fit implements `ChannelProvider` and is installed through the `register_provider` seam NOT-001 already built. **Idempotency:** every send carries `Idempotency-Key: lacteva-{notification_id}`, stable across every retry, because the one double-send the platform cannot prevent alone is a message the gateway accepted and whose response we lost — only the gateway knows, so it is told. The platform's own uniqueness on `(event_id, template_key, channel)` stops a duplicate *dispatch*; this stops a duplicate *delivery*. **Four modes**, and the distinctions are operational rather than cosmetic: `logging` (dev), `placeholder` ("no gateway configured yet"), **`dry_run`** (renders and logs a real message against production-shaped configuration *without sending* — staging, so a credential or sender-id mistake surfaces before a farmer sees it), `http`, and **`disabled`**, which raises permanently rather than succeeding silently, because a notification marked sent that was never sent is a lie the platform would then repeat to whoever asks why a supplier was not told. An unknown provider name is a startup failure, not a message that quietly goes nowhere. **Security:** `mask_phone()` turns `+254700123456` into `+2547****3456` and is applied at every log site — a log carrying every supplier's number is a copy of the directory with weaker access control than the database it came from; gateway error bodies are truncated to 200 characters before reaching an exception, because they echo the request often enough to carry the number and occasionally the credential; the API key is sent as a bearer header and never logged, and belongs in a Docker secret. **Observability:** a new `notification_provider_errors_total{channel,provider,kind}` where `kind` is a three-value vocabulary — permanent, transient, timeout — never the provider's error string, which is unbounded and partly attacker-influenced; existing sent/failed/dead/retry/latency metrics unchanged. SMS **segment count** is reported in delivery metadata and the dry-run log, because segments are what a gateway bills and a template that quietly crosses the 160-character boundary (70 outside GSM-7) doubles the cost of every message it sends. 41 new tests (971 total) covering success, every transient status, every permanent status, timeout, unreachable gateway, unparseable and wrong-shaped 2xx responses, duplicate dispatch, stable idempotency keys, all five modes, configuration failures, PII masking, credential leakage, and metric cardinality. Docs: [NOTIFICATION-ENGINE](docs/03-architecture/04-technology-layer/NOTIFICATION-ENGINE.md) v1.1, `.env.production.example`, DEPLOYMENT.md and INFRASTRUCTURE.md — whose readiness checklists now say to prove SMS in `dry_run` on staging first, since a wrong sender id is a permanent rejection and suppliers would silently stop being told they were paid.
- IDM-001 "Platform-wide Idempotency Framework": one capability on **every** POST/PUT/PATCH, not a payment-specific solution. A client on a poor network cannot distinguish a lost response from a lost request; it retries, and without help the platform performs the operation twice. This platform is explicitly built for field use over intermittent connectivity, so that is the normal case rather than an edge case. **Three partial answers already existed** and each solved its own problem well — `payment.idempotency_key` (a business *intent*), `sync_operation.operation_id` (one captured operation across batches), `consumer_execution` (one consumer handling one event) — and none of them dedups an **HTTP request**, which is what a retrying client actually repeats. The framework adds that layer and deliberately replaces none of them: they mean different things, and a payment key that survives across two genuinely different requests is a guarantee worth keeping. **The design's central property is that the reservation, the business write and the stored response share ONE transaction.** That required establishing where the pieces can see each other: a router-level dependency has the request's session but never sees the response; a route class has the response and — because FastAPI closes dependency teardown *after* the route handler returns — the session is **still open** when it regains control. That ordering was verified with a probe before the design was committed to, and is now pinned by a test, because if it ever changes the framework would silently stop storing anything. The alternative, a separate transaction for the reservation, leaves a key claiming an effect that never happened and refuses the retry until it expires — stranding exactly the client the framework exists to help. **Behaviour:** a retry after completion replays the original response verbatim (same status, same body, `Idempotent-Replay: true`); a retry while the first is in flight gets 409, because inventing an answer is worse than asking the caller to wait; the same key with a different body gets 400, because replaying would silently discard the second request; a failed operation **releases** its key, since a failure holds no effect worth deduplicating and answering every future retry with it would be wrong. Keys are 1–128 characters, and an **empty header is refused rather than treated as absent** — a client that sends one believes it is protected and is not, and silent non-protection is the failure the framework exists to remove. The fingerprint is a sha256 of method, path and body, never the body itself, because bodies carry credentials and PII and this table has a retention period. **Two defects were found and fixed during implementation.** `include_router` carries each child's own route class through (`route_class_override=type(route)`), so declaring it on the parent alone built every route with the wrapper absent — idempotency would have appeared enabled while storing nothing; the declaration now lives on all 26 sub-routers and a test asserts 174 of 174 `/v1` routes are wrapped. And router-level dependencies run **before** authentication, so `get_current_tenant()` reflected only the `X-Tenant-ID` header — which token-authenticated clients do not send — putting every tenant's keys in one namespace, the same class of defect MT-001 found in the rate limiter; the guard now derives the tenant from the token claim, which is authoritative and costs no database round trip. **Also:** tenant-scoped `(tenant_id, key)` uniqueness with an RLS policy (SEC-002 made an unprotected tenant table a build failure, and this is the first new table since); configurable retention (24 h) swept by a background worker on a timer, small and frequent rather than one large DELETE that would lock the table the request path reads; five metrics (replays, stored, conflicts, mismatches, swept) with the key never used as a label; structured logging; localized messages in all three languages; migration `f73f41473469`. 21 new tests (930 total) — duplicate POST and PUT, mismatched body, empty and oversized keys, failure-releases-key, replay after restart, tenant scoping, expiry and reuse-after-expiry, plus three PostgreSQL tests for the guarantees SQLite structurally cannot stage: SQLite's `StaticPool` gives the whole process one connection, so two "concurrent" requests share a transaction and the unique constraint never fires. [API-0001](docs/06-api/API-0001-platform-core.md) v1.1 documents the capability and closes its own §8.1.
- API-001 "Complete REST API Architecture Review": all **177 operations across 155 paths** reviewed as if preparing a public SaaS release, which changes what counts as a defect. **Three fixes, each architectural rather than local.** (1) **The error contract was never published.** The platform has always RETURNED RFC 9457 problem details — `type`, `title`, `status`, translated `detail`, machine-readable `extra`, `application/problem+json`, `WWW-Authenticate` on 401 and `Retry-After` on 429 — and the OpenAPI document declared exactly **one** non-2xx response, FastAPI's automatic 422. Every generated client therefore treated an error body as an unknown shape, and every integrator would have learned the real contract by causing errors in production. Now published from one place by three mechanical rules: every `/v1` operation declares 401/403/422/429, an operation with a path parameter declares 404, an operation that mutates declares 409 — applied in `main._publish_error_contract` rather than as a `responses=` argument repeated on 177 routes, because a per-route list drifts and nothing fails when one forgets. 174 operations now document the universal set, 95 document 404, 104 document 409. (2) **Page sizes were clamped silently.** Services did `max(1, min(limit, 100))`, so a client paginating with `limit=1000` believed it had read 1000 records, received 100, then jumped to `offset=1000` — **skipping 900 rows it never saw**. Silent clamping turns a page-size mistake into missing data. Every paginated route now declares its bound (`Query(20, ge=1, le=100)`), so the maximum is published in OpenAPI and an out-of-range value is **rejected with 422** rather than quietly honoured as something else. (3) **`/v1/collection-sessions` had no bound at all** — the one business list returning every row, and sessions are opened ~2 per center per day and never deleted, so a tenant with sixty centers accumulates ~44,000 a year into a single response. Now paginated with the same `items/total/limit/offset` envelope as the other thirteen. Also added: the conventional **`Idempotency-Key` header** on payment creation (paying twice is the worst outcome this API has, and a mobile client on a village connection cannot distinguish a lost response from a lost request; the header is accepted alongside the existing body field and wins when both are present). **Reviewed and found correct:** REST semantics throughout (201 for creation, 200 for state transitions on an existing resource, 204 for deletion — the distinction is deliberate and now asserted), CAS-guarded transitions making every state-changing POST retry-safe by construction (the second attempt gets 409, not a double-apply), tenant isolation (a resource in another tenant is 404, never 403, so the API does not confirm it exists), the token's authority over the `X-Tenant-ID` header, audit coverage on state changes, correlation-id propagation, presigned downloads issued only after the tenant-scoped resource check, and the closed set of 7 unauthenticated endpoints — now asserted by test, so a new public endpoint must be added deliberately. New [API-0001](docs/06-api/API-0001-platform-core.md), the first document in a layer whose own rule says an undocumented endpoint is an incident: conventions, the error table with retry guidance per status, the pagination rule (grows with business volume → paginate; bounded by structure → array is fine), retry safety per method, and **seven recorded limitations with the reason each is acceptable** — no general idempotency, no `ETag`/`If-Match`, no client-controlled sorting (an unindexed sort is a way to take the platform down from a query string), no cursor pagination, no batch endpoints, no cache headers, no API-level timeout. 17 new tests (909 total) that assert the contract over the whole OpenAPI document rather than per handler, including that an out-of-range page size is rejected rather than clamped and that a repeated payment request does not pay twice. The Flutter client's `listOpenSessions` was updated for the paginated envelope — the one consumer the change touched, found by grep rather than by a broken build.
- MT-001 "Full Multi-Tenancy Audit": every endpoint, service, repository, projection, consumer, background job, cache key, event handler, migration and reporting query reviewed against the tenant boundary. **Three real defects, one of them severe.** (1) **The bypass was documented and never implemented.** SEC-001 stated that "the relay dispatcher, consumers, and projection rebuilds set `lacteva.bypass_rls`" — nothing did. Those components built sessions from the ordinary factory, which binds neither a tenant nor a bypass, so on PostgreSQL the policy evaluated to false on every clause: `current_setting` returns NULL when unset, `NULL = 'on'` is not true, and `uuid::text = NULL` is not true either. **The entire asynchronous half of the platform could see only platform-global rows** — the relay would find no tenant events to dispatch, consumers would consume nothing, and every projection write would be refused by `WITH CHECK`. No error, no exception, no alert: requests succeed, milk is recorded, and no receipt is generated, no notification sent, no projection updated. That is the failure shape the platform's own runbook calls the most dangerous it has, and SQLite could not catch it — the fourth defect of exactly that shape. Fixed with a **`PlatformSessionFactory`**: components whose job spans tenants (relay, consumer runner, projection rebuilder, backup engine, health probes, the ops APIs) are constructed with a factory whose every session binds the bypass and logs the reason. A factory rather than a call at each of ~25 sites, because a component built with it *cannot forget*, and one built with the ordinary factory is visibly request-scoped. (2) **The per-identifier rate-limit key was not tenant-scoped.** Email is unique *per tenant* (`uq_user_tenant_email`), so `alice@example.com` can be two different people in two organizations — and both were charged to one Redis counter. An attacker with an account anywhere could exhaust that address's login budget in **every** tenant by failing to log in to their own: a cross-tenant denial of service on authentication. `RateLimitRule.key()` now takes a tenant, and the login route passes it. (3) **The notification dispatcher resolved recipients by `subject_id` alone.** Harmless while UUIDs do not collide — but dispatch runs inside the bypass, where RLS is switched off by design, so that filter was the only thing standing between a payment notification and *another dairy's phone number*. Now scoped by tenant as well. **Reviewed and found correct:** object-storage keys (tenant-prefixed, with `platform/` for tenantless objects), document download (resolves the supplier first, which is tenant-scoped), receipt rendering and every receipt query, pagination totals (counted over the already-filtered statement, never a fresh select), all reporting queries including the `settlement_line → settlement` join, audit records (written with and read within a tenant), the notification idempotency key (`event_id` is globally unique, so scoping by it scopes by tenant transitively), JWT claims (the token's tenant is authoritative and a header cannot override it — asserted), and backup/restore (whole-database by definition, and now correctly platform-bound). **No websocket endpoints exist**; a test asserts that, so the first one added fails until its tenant binding is designed — a socket outlives the request that authenticated it. BR-0022 extended (register v1.15): the bypass **must** be set, inside a bypassed session the application filter is the *only* isolation, and a tenant boundary is not only a database boundary — any key namespace built from a per-tenant-unique identifier must carry the tenant. New [RLS-GUIDE §3d](docs/03-architecture/05-security/RLS-GUIDE.md) documents the boundary and the two-factory rule. 22 new tests (892 total), including three PostgreSQL tests that demonstrate the defect rather than argue it: an unbound session sees no tenant events, an unbound projection write is refused, and the platform binding lets a consumer do its job.
- INF-001 "Infrastructure as Code & Production Environment" (**infrastructure only — no business logic, API or schema changed**): a production environment can now be provisioned from zero. **Terraform** for Hetzner Cloud (primary) and AWS (an optional abstraction, deliberately thin — two half-maintained infrastructure definitions are worse than one maintained one, and the second is always the one nobody has applied since March): one VM, one **static IP and one data volume that outlive the machine**, one firewall, SSH keys, provider snapshots. That IP-plus-volume pairing is the whole server-replacement story — build a new machine, re-attach both, deploy; DNS never changes, so no propagation wait and no certificate reissue. `prevent_destroy` on both, and `ignore_changes = [size]` on the volume because it can be grown online and never shrunk, so a smaller number in tfvars must not plan a destroy-and-recreate of the volume holding production data. **Terraform deliberately does not format the volume** — cloud-init does, and only when `blkid` finds no filesystem, because a `format` attribute lets an apply after a state mishap reformat a live database. **cloud-init** installs Docker (with `live-restore`, so a daemon upgrade does not take the platform down), builds the filesystem standard (`/opt/lacteva/releases` + `current` symlink, root-only `/etc/lacteva`, `/var/lib/lacteva` and `/backup` on the data volume), hardens SSH to keys-only with no root login, brings up ufw **and** fail2ban as a second layer inside the machine — the cloud firewall sits outside it and holds even mid-boot or after somebody flushes iptables while debugging — configures chrony (**not cosmetic**: the platform signs JWTs with a 30-second leeway, and a drifting clock rejects every valid token while looking exactly like a key problem), logrotate for host-written logs (a nightly backup log otherwise fills the volume the backups are written to), and enables security-only unattended upgrades with **automatic reboot off**, because rebooting a single-host platform without warning is an unplanned outage. **Firewall: 80, 443, and SSH from named ranges only** — both configurations *refuse `0.0.0.0/0` at plan time*, since key-only auth reduces the risk of exposing sshd to the internet without removing it. **systemd** starts the stack on boot with `RequiresMountsFor=/var/lib/lacteva` (starting before the volume is mounted creates an empty PGDATA on the root disk, silently) and a `TimeoutStopSec` that exceeds the API's 90-second stop grace, so systemd cannot kill the drain DEP-001 exists to make possible. **Backups on timers:** nightly logical (taken, then **verified**, and only then pruned — pruning first means a failing job deletes its way through the retention window and the day you need a restore there is nothing left), weekly physical, and a weekly **restore verification** that loads the newest backup into a throwaway database and runs deep business integrity including a projection rebuild, per BR-0025. All timers are `Persistent=true` so an overnight reboot does not silently skip a night. **`deploy.sh`** is one command: pull → pre-deployment backup → migrate → up → verify → smoke test, with **automatic rollback** on any failure past the migration, because the alternative is a half-deployed platform sitting broken until somebody notices. It never rolls the schema back automatically — a code rollback is safe after an expand-only migration and unsafe after a contract, and no script can tell from the outside — but it reports when the schema moved and points at the compatibility matrix. - DEP-001 "Production Deployment Automation" (**no business behaviour, API, or schema changed**): the platform becomes deployable. A nine-container production stack (`docker-compose.production.yml`) with **one published port** — nginx — and everything else on `expose:` only, because reaching the database should be a decision someone makes rather than a port someone forgets. **Startup ordering is by health check and contains no sleep at all** (a test asserts it): postgres and redis must pass `pg_isready`/`PING`, then a one-shot `migrate` service runs `alembic upgrade head` and must **exit zero** before the API is allowed to start — `restart: "no"` is the load-bearing line, because a restart policy would turn a clear migration failure into a crash loop that looks like a slow start, and `service_completed_successfully` then never fires so nothing serves traffic against a schema that did not apply. **Two operational defects were fixed on the way.** (1) **Shutdown abandoned work.** The relay, consumer and health loops were `task.cancel()`ed, which throws wherever the loop happens to be — possibly between a consumer's write and the ledger row recording it. Safe (the transaction rolls back and the event retries) but not clean: every rolling deploy left work to redo. Shutdown is now cooperative — `workers.sleep()` wakes on a flag, each loop finishes the unit of work it is in and exits at its next sleep, stragglers are cancelled after a grace period, and the log reports `drained` versus `cancelled_after_grace` per worker because that difference predicts whether the next start has catching up to do. The engine is disposed last, after the loops, since disposing it while a consumer holds a session turns a clean shutdown into a stack trace. (2) **`/health/ready` was a `SELECT 1`.** A load balancer was told an instance was ready while its consumer loop was dead and nothing downstream was happening — this platform's most dangerous failure shape, because it looks healthy. Readiness now aggregates the same nine probes the ops endpoint and every Prometheus alert use, **degraded stays ready** (only `critical` removes an instance; taking a degraded instance out of rotation turns a partial problem into a total one), and it answers from the background sampler's most recent evaluation rather than running nine probes per poll, because a health check that is itself a load source is how a wobble becomes an outage. The response's `status` field keeps its original two-value vocabulary — DEP-001 is not allowed to move a contract — with the four-level detail added beside it. **Also new:** `.env.production.example` with every variable documented and a test that fails on an undocumented one; **Docker Secrets** support via pydantic-settings' `secrets_dir`, so a signing key need never appear in an environment block; production nginx (HTTPS, HSTS, gzip, websocket upgrade, 25 MB uploads, edge rate limiting, static caching, and `/metrics` restricted to private networks — publishing it would expose tenant counts and error rates); Loki + Promtail reading the container logs the platform already writes, so nothing ships from inside the API process; `infra/deploy/verify-deployment.sh` (readiness, every component, schema revision matches the image, **RLS coverage and FORCE** — a database restored from a pre-SEC-002 backup can serve traffic with the policies simply absent — Redis, outbox actually draining, nginx); and `infra/deploy/smoke-test.py`, which creates its own throwaway tenant, never deletes, and polls for the consumer-generated receipt rather than sleeping. [DEPLOYMENT.md](DEPLOYMENT.md) covers deploy, upgrade, rollback, backup, restore, disaster recovery, version upgrade and troubleshooting — including the **rollback compatibility matrix**: expand-only migrations roll back freely, contract migrations do not, and `alembic downgrade` on a live database drops columns holding data written since the upgrade, so it is a development tool and the honest options are roll forward or restore. 23 new tests (845 total). **Nothing here has been executed** — no Docker or production host exists in the development environment; the artefacts were validated by parsing, static analysis, dry-run against stubs, and tests that assert their contents.
- OPS-001 "PostgreSQL Continuous Verification" (**verification infrastructure only — no platform code changed**): the PostgreSQL-only guarantees get their own pipeline. - DB-002 "Exact Numeric Aggregation" (**no API response changed; the reporting module was not redesigned**): the last correctness gap the Architecture Board reviews had left open. Money was already exact — `Decimal(str(x))` arithmetic, `NUMERIC` columns, an explicit rounding policy (BR-0005) — but **aggregation was not**. `net_weight`, `fat` and `snf` are `double precision`, and floating point addition is not associative, so `SUM(net_weight)` depended on the order the planner happened to produce; that order changes with statistics and with parallel workers, and the result was written into a `NUMERIC(16,3)` projection column, which made a non-reproducible number look exact. **Every aggregation in the platform was reviewed and classified**: 13 required conversion (all in `reporting/service.py` — the daily, per-center and per-supplier weight sums, the weighted fat/SNF numerators and denominators, and the two `ORDER BY SUM(...)` clauses), 1 was accepted as lossy-but-harmless (`AVG(event_delivery.latency_ms)`, an operational metric), and the rest were already safe (integer counts, and sums over `NUMERIC` — `gross_amount`, `settlement_line.gross_amount`, `payment_line.amount`, `AVG/MIN/MAX(unit_price)`). The fix is one helper: `_exact()` casts to unconstrained `NUMERIC` inside the aggregate, so the arithmetic stays in SQL and only its exactness changes — deliberately unconstrained, because pinning a scale would round every ROW where the platform rounds the TOTAL once. On PostgreSQL `float8::numeric` renders the shortest decimal that round-trips, the same rule `Decimal(str(x))` follows, so a weight aggregates as the value it displays as. **A second, unreported divergence was found while testing the first:** the reporting projection rounded its running total whenever a flush happened to occur — once per event for the incremental consumer, once per BATCH for the rebuild engine — so a rebuilt projection did not reproduce the incrementally built one, and two rebuilds at different batch sizes disagreed. Six weights of 0.0005 kg came to 0.006 incrementally and 0.003 in one batch: the same events, the same log, two different totals, and no error anywhere. **That was a hole in BR-0015**, whose whole promise is that a rebuilt projection is provably identical to an incrementally built one. The handler now quantizes to the column's own scale at every step, making the flush boundary irrelevant. Registers: BR-0005 extended to SQL aggregation, BR-0015 gains flush independence (register v1.14). 28 new tests: order independence over random insertion orders, rebuild-versus-incremental at batch sizes 1/2/5000 driven through the real projection engine, repeated-rebuild byte-identity (`Decimal.as_tuple()`, not just equality — a value comparing equal with a different exponent still serialises differently), decimal edge cases including classic half-way values, a 10 000-row exactness check, a structural guard that fails if a future report sums a float column directly, and a new PostgreSQL-only module proving the two premises SQLite cannot exhibit — that `SUM(float8)` is order-dependent while `SUM(float8::numeric)` is not, and that `numeric(16,3)` **rounds on store**, which is why the projection divergence was invisible in the main suite. Both are now wired into the CI proof job. **Still open and explicitly out of scope:** the column *types*. `pricing_matrix_row.unit_price`, `from_value`, `to_value` and the three weight columns remain `FLOAT`; this work order made the aggregation exact, not the storage.
- SEC-002 "Complete PostgreSQL RLS Coverage" (P0 — **no business behaviour or API changed**): the architecture principle *every table has an explicit isolation strategy* becomes something the build can check. Each of the 56 tables now declares exactly one of three: **tenant-owned** (carries `tenant_id`, standard policy — 50 tables, derived from the metadata rather than listed, because a hand-kept list is how a new module ships unprotected), **platform-global** (deliberately unprotected, **with the reason on record** — 5 tables), or **mixed** (both kinds of row, or isolated by a column other than `tenant_id` — 12 entries). `unclassified_tables()` returns nothing and a test asserts it, so "nobody decided" is a build failure. **Thirteen tenant-owned child tables gained `tenant_id` and a policy** (migration `f2d18ba60c47`): supplier profiles, bank accounts and documents, settlement lines, payment lines and attempts, receipt lines, price bands, center config/windows/calendar, device health reports, role permissions. They were reachable only through a parent, so SEC-001's "does it have a tenant_id column" rule skipped them and BR-0022's promise — *a query that forgets its filter returns NOTHING* — was simply false for them; `supplier_profile` (names, phones, national IDs) and `supplier_bank_account` (account numbers) were the worst of it. Denormalising is safe because no aggregate here is ever reparented. **`organization` gained an identity policy**: it has no `tenant_id` because it IS the tenant, so it was readable by any bound session and a tenant could enumerate the platform's customer list; it now compares its own primary key, with **no `IS NULL` escape** — creation and platform-admin reads take the audited bypass instead, because both are genuinely cross-tenant acts. **A worse defect was found while verifying the flows: authentication itself was broken under RLS.** `get_current_principal` read `auth_session` and `user_account` — both tenant-owned — and only *afterwards* re-bound to the token's tenant, so under RLS the session row was invisible to the request that owned it and every authenticated call without an `X-Tenant-ID` header would have failed as 401. The token is signed and self-contained, so its tenant claim is authoritative before any row is read; binding now happens there. Three more pre-tenant flows were repaired the same way: **tenant-scoped login** (the tenant is named in the request body, which the middleware never sees), **invitation acceptance** (anonymous, and `invitation` is tenant-owned — resolved by the narrowest possible bypass, one indexed read by token hash, then an immediate bind), and **organization creation** (nobody can be bound to an organization that does not exist yet). `rebind_tenant()` now moves the context variable and the database binding together — `set_current_tenant()` alone left the binding behind, which presents as "the row is invisible to the request that owns it" and was the second half of the same defect. `password_reset_token` is deliberately **not** protected and the reason is recorded: the flow that reads it is definitionally unauthenticated, and a policy there would make password reset impossible for every tenant-scoped user. 22 new tests — 14 PostgreSQL tests running against the **real migrated schema** rather than a synthetic probe table (coverage of enable+force+USING+WITH CHECK across every tenant table, cross-tenant read/insert/update/delete on `settlement_line` and `payment_line`, PII isolation on `supplier_profile`, organization identity isolation, and the bootstrap/registration/invitation/anonymous/role-catalog flows), plus 8 that run on SQLite including `test_authentication_binds_the_tenant_before_reading_any_row`, which records binds and reads on one timeline and was verified to fail against the pre-SEC-002 order. The CI proof script now asserts policy **coverage** rather than policy count — counting would have passed while the money and PII tables sat unprotected, which is exactly what happened. Docs: [RLS-GUIDE](docs/03-architecture/05-security/RLS-GUIDE.md) v1.2 (the A/B/C taxonomy and a table of every pre-tenant flow), BR-0022 extended (register v1.13), [DBD-0001](docs/07-data/DBD-0001-platform-core-database.md) v1.1 — which also **strikes findings F-4 and F-9 as measurement errors**: both were derived from `str(column.type)`, which renders through SQLAlchemy's default dialect, and all 97 timestamps are already `TIMESTAMPTZ` and all 176 ids already native `uuid` on PostgreSQL.

Three work orders in a row had ended with a P0 guarantee that was written, tested, and CI-wired but **never actually executed**, because the test stack is SQLite and the guarantee is PostgreSQL-specific. - BAK-001 "Backup, Restore & Disaster Recovery" (Phase B, P0 — **no business behaviour changed**): the platform can now *prove* it recovers. The centre of the work is a test that builds a real dairy (collection → pricing → settlement → payment → receipt → notifications), takes a backup, **deletes every row in every table**, restores, and asserts the money is identical to the cent, the receipt still renders under its original number, the platform still refuses a second payment on a fully-paid settlement (rules came back, not just rows), new business still succeeds, and every business invariant holds — including a deep projection rebuild from the event log. **A successful backup is not evidence; a successful restore is (BR-0025).** **Classification first:** every table is classified critical/important/rebuildable/ephemeral, derived from the mapped metadata rather than hand-maintained, with an unknown table defaulting to *critical*. Projections are excluded because BR-0015 guarantees they rebuild from the log; **consumer ledgers are deliberately included**, because restoring without them replays the entire event log and re-sends every notification and re-mints every receipt — a dedicated test proves consumers do not re-fire after a restore. **The engine** is dialect-portable (so it runs on SQLite and PostgreSQL alike) and writes a manifest with deterministic per-table checksums over primary-key-ordered rows; types are tagged rather than coerced, so a Decimal never becomes a float (BR-0005) and a UUID never becomes a string. Corruption and truncation are detected *before* a restore depends on them, a future format version is refused, and restoring over a non-empty database is refused unless explicitly forced. **Restore is CLI-only and always will be** — an endpoint that overwrites the database is one misrouted request from catastrophe — and it exits non-zero when the restored business is wrong, because that is a failed restore. **Integrity verification** checks the platform's own rules: settlement totals (BR-0011), payment allocations (BR-0018), one receipt per completed payment (BR-0020), orphaned rows, consumer cursors within the log (BR-0014), audit-trail presence, and projection rebuildability (BR-0015); tests prove each check can actually fail. **Operator surface:** a `backups` health component (so a schedule that silently stopped is visible beside everything else), read-only ops endpoints for status/history/classification/integrity, and a CLI with status, history, classification, backup, verify, integrity, and restore. **A live latent bug was found and fixed:** `migrations/env.py` had lost every model import to an earlier `ruff --fix` (they exist only for their registration side effect), so the next `alembic revision --autogenerate` produced a migration that would have **DROPPED EVERY TABLE** — including every payment, receipt, and settlement. Nothing had failed for three commits. Restored, exempted from the linter in `pyproject.toml`, and guarded by a new `test_migrations.py` that also asserts the migration chain stays linear. Physical PostgreSQL PITR (`pg_basebackup` + WAL) is scripted in `infra/backup/` with a five-gate automated restore test and a CI job, but **has not been executed** — no PostgreSQL was available; the logical path is the one demonstrated. - OBS-001 "Platform Observability & Alerting" (Phase B, P0 — **no business behaviour changed, no query added to any business endpoint**): operators can now determine platform, consumer, projection, notification, payment, and security health **without reading application logs**. The layer is built around this platform's actual failure shape: it is event-driven, so collection can commit and then every downstream step — outbox, consumer, notification, receipt, projection — can stop *while the API keeps answering perfectly*. - SEC-001 "Production Security Hardening" (Phase B, P0 — **no business behaviour changed**): the platform's trust boundaries hardened for an enterprise security review. **JWT/RS256 with rotation:** tokens are signed RS256 from a key registry and carry the signing `kid`; verification resolves exactly that key — an unknown, retired, or expired kid is a rejection, never a fallback, and never an algorithm taken from the token's own header (both `alg: none` and HS256-signed-with-the-public-key are proven rejected by hand-assembled forgeries, since PyJWT refuses to build them). Rotation is **additive**: a new key signs while every unexpired predecessor keeps verifying, so no live session is invalidated; retirement kills every token a key signed, at once — the emergency lever. Public discovery at `/.well-known/jwks.json` (active keys only; a retired key is never advertised as trustworthy) and an operator view at `/v1/_security/keys` that cannot return private material. HS256 survives only as a documented rollback path, refused in prod without an explicit secret. **PostgreSQL Row Level Security (BR-0022):** every tenant-owned table gets a policy comparing `tenant_id` against a `SET LOCAL` session variable — transaction-scoped, so a pooled connection cannot carry one request's tenant into the next — with `WITH CHECK` as well as `USING` (without it a caller could move a row *into* another tenant, succeeding silently) and `FORCE` (without it the application, which connects as the table owner, bypasses its own policies). An unbound session matches nothing and fails **closed**; cross-tenant machinery uses an explicit, logged, transaction-scoped bypass rather than a superuser connection. Application filters stay as defense-in-depth. **The table list is derived from metadata, not hand-maintained** — the drift test immediately caught three projection tables that register at consumer discovery rather than at import. SQLite has no RLS, so policy *execution* is proven by a new PostgreSQL CI job whose **skip fails the build**. **Headers/CORS:** nosniff, DENY framing, no-referrer, deny-all Permissions-Policy, `default-src 'none'` CSP, and `no-store` (a shared proxy caching one tenant's data is a leak with extra steps); HSTS opt-in because a browser honours it *after* a rollback; CORS narrowed from wildcard methods/headers to explicit lists, never reflecting an origin. **Rate limiting:** Redis fixed-window, one round trip (INCR+EXPIRE pipelined), on login, refresh, password reset, invitation acceptance, notification preview, projection rebuild, and consumer replay; credential endpoints keyed per-IP **and** per-identifier because credential stuffing and distributed brute force are different attacks and a per-IP budget catches only one. 429 carries structured retry data and a `Retry-After` header. **Fail-open by default and deliberately** — a dairy must not stop accepting milk because a cache is down — with fail-closed one setting away. **Secrets:** nothing sensitive in source (a test greps for committed PEMs); production *refuses to start* on a dev default, a debug flag, or wildcard CORS. **Audit (BR-0023):** login success/failure, refresh, reuse detection, logout, password reset, permission denial, key rotation, and rate-limit violation land in the same immutable trail as business events and mirror to the log stream, so an attacker who reaches the database cannot erase what already left the host. - OFF-001 "Offline Collection Sync" — the last Phase A item, and the field prerequisite: the operator app now collects milk with **no connectivity at all** and reconciles when it returns, without forking a single business rule. **Offline is a transport problem, not a business one** (BR-0021; register v1.8): every operation captured on a device is applied, on sync, by calling the same `MilkCollectionService` method the online API calls, with the same principal, tenant context, and state machine — a step the engine refuses online is refused offline, an archived supplier is still archived, a closed session is still closed. The device is a **recorder, not a decider**: it never prices milk, never validates identity, never advances a state on its own authority, and reports platform-owned values as `pending_sync` rather than guessing; a 409 is an *answer* and is rethrown unchanged, so only transport failures fall back to the queue. **Flutter**: a new `offline/` layer — an `OfflineStore` port with an in-memory adapter and a file adapter that writes-then-renames (atomic, so a crash leaves the previous complete queue or the new one, never half a morning); a durable `SyncQueue` (PENDING/SYNCING/SYNCED/FAILED/CONFLICT, attempts, exponential backoff capped at 5 min mirroring the platform's own consumer schedule, local→server id map, last sync timestamp, conflict metadata) surviving app restart, device reboot, and crash — operations stranded in SYNCING by a process death are recovered on load because replay is idempotent; a `SyncEngine` with batch upload, automatic retry, progress, cancellation honoured *between* batches (work already in flight has its outcome applied first), and resume; and an `OfflineApiClient` that intercepts the collection calls so **the wizard is unchanged** — the operator's flow is answered from a projection folded over the queue. **Backend**: a new `sync` module whose service is explicitly a transport (`_dispatch()` routes each kind to the online service; if a business decision ever appears there, the design has failed), with client-generated `operation_id` as the idempotency key — a lost acknowledgement re-sends without doubling a collection — and `client_reference`/`target_ref` local ids resolved to server ids **across batches and persisted server-side**, which is what makes an interrupted sync resumable rather than restartable. - RCP-001 "Receipt Engine" — the artifact a farmer can hold. A new `receipt` module whose Receipt aggregate owns ReceiptLines (one per settlement the payment covered). - PAY-001 "Payment Execution Engine" — the money finally moves (as a record): a new `payment` module whose Payment aggregate owns PaymentLines (the allocation against each settlement) and PaymentAttempts (the execution history). **Payments consume settlements and never modify them** — only a FINALIZED settlement is payable, allocations belong to one supplier and one currency, and the settlement side stays untouched (BR-0018). **Outstanding balance is always computable**: payable − live allocations, where draft/pending/processing/completed all RESERVE (a draft is an intent that must stop a second payment claiming the same money) and failure/cancellation release — which is what makes partial payment, remaining balance, and duplicate prevention one rule instead of three. - PLT-001 "Projection Lifecycle & Replay Framework" — projections become first-class platform infrastructure ahead of Notifications/Offline/Analytics/AI read models.
