- PORTAL-001 "Make the Admin Portal Deliverable" — the portal built cleanly and could not be shipped: no Dockerfile, no compose service, no nginx route, no mention in DEPLOYMENT.md, zero tests, and a session token in `localStorage`. **F-11 first, because it decided the rest.** There is no way to store a token in a browser that page script cannot read, so the token is no longer in the browser: `POST /api/auth/login` exchanges credentials on the server, puts the access and refresh tokens in `HttpOnly; SameSite=Strict; Secure` cookies and returns **no body**, and every page call goes same-origin to `/api/proxy/...`, which attaches the bearer header server-side. CSRF is `SameSite=Strict` plus an `Origin` check on every state-changing route. Sign-out revokes the platform session as well as clearing the cookies — clearing the cookie alone would leave a captured refresh token working, the same gap SEC-003/F-02 closed for deactivation. **F-03:** a multi-stage, non-root, health-checked Dockerfile in the same shape as `services/platform-core/Dockerfile` (one deployment architecture, not two), `output: "standalone"`, a `portal` service that is internal-only with nginx still the sole port publisher, and nginx routing `/` and `/_next/static/` to the portal while `/v1/`, `/health/`, `/metrics`, `/docs`, `/redoc` and `/openapi.json` stay on the API. **`NEXT_PUBLIC_API_URL` is gone**: Next inlines those at build time, so one image could only ever reach one backend and an image built without it shipped `http://localhost:8000` to production browsers. The portal reads `LACTEVA_API_URL` server-side at request time, so the same image runs anywhere and nothing secret is in it. An unreachable platform is reported as **502, not 500** — the distinction tells an operator which tier is broken. **F-05:** release builds were signed with the public Android debug key under a TODO. A release build now FAILS with an explanatory `GradleException` unless `android/key.properties` supplies a real keystore; `key.properties` and every `*.jks`/`*.keystore` are gitignored, an annotated example is committed, and four tests assert the release block never selects debug signing, that the guard exists, that the real file is absent, and that the example carries only placeholders. - SEC-003 "Close the Access and Measurement Boundary" (issued as SEC-002; recorded as SEC-003 in code because SEC-002 already names the RLS-coverage work order in 67 places) — the four security findings FINAL-001 rated as blocking a pilot, closed and proven by execution. **F-01: fabricated measurements could reach production.** `source=mock_scale`/`mock_analyzer` derive a weight and a fat/SNF/CLR reading from `sha256(container_id)`; the API accepted them in every environment, including `prod`, and the mobile app shipped two unconditional buttons that used them. That number is priced, settled, paid and receipted exactly like a measured one, and no downstream check can tell the two apart. Closed at three layers, each tested in its own right: `prod` refuses `LACTEVA_ALLOW_MOCK_HARDWARE=true` at startup (the setting derives from the environment when unset, so the safe answer needs no operator action); `MilkCollectionService` refuses the source before touching state, which covers the HTTP route **and the offline sync replay** — the path a client controls most directly; and the adapters themselves refuse to produce a number, so a caller that has not been written yet cannot reach around either. The mobile controls are compiled out of release builds via a `const` gate, proven by running `flutter test` twice — once normally and once with `--dart-define=LACTEVA_ALLOW_MOCK_HARDWARE=false` — and that gate is explicitly a convenience, not the boundary. **F-02: access could be granted but never revoked.** `is_active` was enforced in five places and settable in none; `assign_role` had no inverse anywhere. An offboarded employee kept working credentials indefinitely and a mis-granted permission was permanent. Closed with `POST /identity/users/{id}/status` and `DELETE /authz/assignments`, both audited, both tenant-scoped and answering 404 rather than 403 for another tenant's user. Deactivation goes through the AUTH service, not identity alone, because revoking the flag without revoking the sessions leaves the refresh endpoint minting fresh access tokens from a session nobody re-checks — tested as its own case. Reactivation deliberately does NOT restore sessions. **F-04: the invitation token was returned to the inviter**, who could therefore accept the invitation and create an account under the invitee's email, in the invitee's tenant, with the role they were being offered. The response now carries metadata only and the token reaches the invitee through the notification channel. Doing that safely needed a new mechanism: `NotificationView` exposes `payload` and `rendered_text`, so a token placed there would simply have moved the exposure to everyone holding `notification.read` — including the inviter. Hence `notification.secret_payload`, a column no view reads, redacted out of the stored body, and cleared the moment the message is delivered or dies. The token never enters `event_outbox` either, which is why `InvitationService` sends this one message itself: a consumer can only read the event payload, and that table is never pruned and is in every backup. **Every test in the suite now obtains invitation tokens by capturing the delivered message**, because that is the only path that exists — 16 call sites and the CI proof seeder rewritten. **F-06: the rate limiter's failure policy was a default, not a decision.** Fail-open meant a Redis blip silently removed brute-force protection from login, refresh, password reset and invitation acceptance. Replaced with `LACTEVA_RATE_LIMIT_FAILURE_POLICY`, defaulting to **`degrade`**: a limiter error charges the process-local counter instead, so operators can still log in at 5 a.m. — the availability fail-open existed to protect — while an attacker gets `limit x workers` attempts per window rather than unlimited ones. Credential and one-time-token rules carry `fail_closed=True` for the case where even the fallback fails. `fail_open` remains reachable and is **refused in prod**. Migration `8c41f0a7b2d3` (expand-only, one nullable column, up→down→up verified). 43 new tests (1173 total, 1099 passed / 74 skipped / 0 failed), 74 PostgreSQL-only tests, 52 mobile tests across both build modes. Divergences 69 and 70 closed; 71 and 72 recorded as the consequences to know; #9 narrowed.

- DEPLOY-001 regression phase — **three more defects, all found by re-running the proofs the work order requires rather than by trusting the last green run.** (7) **The advisory-lock claim did not hold.** `pg_try_advisory_lock` is SESSION scoped — it belongs to the CONNECTION — and the runner committed the claim session immediately "so it holds no row locks for the duration of the batch". That commit ended the transaction, which returned the connection to the pool *with the lock still on it*; a second runner that checked out the same connection re-entered the lock, was told yes, and both runners worked the same consumer. It reproduces about one run in four as a `uq_notification_event` violation, one FAILED execution and a spent retry — the exact collision the claim was added to stop, in the fix for that collision. Closed with `pg_try_advisory_xact_lock` and a claim transaction that stays OPEN for the batch: a live transaction cannot be returned to the pool, so the lock cannot be borrowed, and PostgreSQL drops it at rollback so it cannot leak either. 25 consecutive clean runs against real PostgreSQL, against roughly 1-in-4 before; a new test asserts the lock is held by an open transaction and leaves nothing in `pg_locks`, and it fails on the session-scoped version. (8) **The proof was verifying its own test residue.** `postgres-proof.sh` ran the PostgreSQL-only suites in the same database it then seeded, backed up and integrity-checked — and those suites legitimately fabricate settlements with no lines and payments meant to lose a race, so step 8 read their leftovers as corruption. Suites now get their own `lacteva_pgtests`; the source database carries only what the platform's own API created. (9) **A single failed payment made its settlement look over-allocated forever.** `payments_never_exceed_the_payable` put the live-status predicate in the JOIN condition, so a line belonging to a failed or cancelled payment survived the outer join with a NULL payment and was still summed — meaning any retry after a declined payment fails the integrity check on every restore from that point on. Fixed to count only matched rows, with a regression test and a control that still catches a genuinely double-paid settlement.

- BKP-003 "Execute and Prove Off-Site Backup Replication" — the second of the two remaining pre-AWS blockers, closed to the limit this machine can actually prove. **What existed:** a backup engine that writes a verifiable directory and restores it (DR-001), a nightly shell wrapper that prunes by `find -mtime`, and an `ObjectStorage` port with `put_object` and `presigned_get_url` — **no S3 integration in the backup path at all**, and `/backup/logical` on the same volume as the database. **What was added:** `core/backup/offsite.py`, a replication layer ON TOP of the existing engine rather than a replacement, because DR-001's evidence is worth more than a rewrite. A backup directory becomes ONE deterministic tar (sorted members, no mtimes) so its checksum is a function of the DATA; it is uploaded, **read back and re-checksummed**, and only then is a sidecar manifest written — the sidecar is the completion marker, so an interrupted upload leaves an orphan archive that `list_backups` ignores and retention never counts. The manifest is stored twice, inside the archive and beside it, and compared on download, which is what catches an archive swapped under a sidecar. The port gained its missing read side (`get_object`, `stat_object`, `list_objects`, `delete_object`) and an endpoint/credential/bucket parameterisation, because a backup must be able to live somewhere other than the application's own MinIO — which dies with the host. Manifests now carry `postgres_version` and `database_identity` (database name plus PostgreSQL's system identifier, never a URL). **Retention** refuses `keep < 1`, excludes the newest backup before considering anything, deletes nothing when there are fewer backups than the threshold, lists only its own `backups/` prefix so it cannot be aimed elsewhere (the generalised DR-001 finding), removes the sidecar before the archive, and **defaults to dry-run** — a retention routine that deletes by default is one that will eventually be run by somebody who was just looking. **PROVEN BY EXECUTION** (`./infra/ci/offsite-proof.sh`, 32 checks, real PostgreSQL 16.2 and a real MinIO running as a separate process with its own credentials and directory): a dairy seeded through the platform's own API to STL-2026-000001 / PAY-2026-000001 / RCP-2026-000001 at 5,647.50 KES, backed up, verified, replicated, duplicate id refused — then **the local backup directory deleted**, a fresh database migrated from empty, and the business recovered from the object store alone with row counts, monetary totals, settlement/payment relationships, RLS (53 policies, 0 unforced), foreign keys, schema revision and the platform integrity check all verified. Plus 22 automated failure tests: upload failure, interrupted upload, corrupted upload caught by read-back, corruption at rest, truncation, archive swap, unreadable sidecar, missing object, duplicate id, local-verify refusal, tar path escape, and every retention boundary including "only one backup" and `keep=0`. **Two defects found by running it**, both in the new code: `stat_object` treated a missing BUCKET as an error, so the very first replication to a fresh destination failed; and the proof harness deleted MinIO's data directory underneath a live server, leaving it healing an unformatted drive and answering 503 — a harness fault, fixed by a fresh store per run and by waiting on `health/cluster` rather than `health/live`. **Stated plainly: the store was on the SAME MACHINE.** This proves independence from the database volume, the database process and the local backup path — not from the host, the disk, the building or the region, and not at scale. Divergence #40 closed; #63 (remote failure domain) and #64 (platform does not encrypt the archive; in-transit TLS enforced, at-rest delegated to the bucket) recorded as what remains.

- `pricing_matrix_row.unit_price` migrated **FLOAT → NUMERIC(12,4)**, with before/after verification executed against PostgreSQL 16.2. This was the top data-integrity item left by DEPLOY-001: BR-0005 made all *arithmetic* exact, but exact arithmetic on an inexact input is still inexact — the price was already approximate before the first multiplication, and it is the number every calculation, settlement, payment and receipt descends from. The new type matches `milk_collection_transaction.unit_price`, the house standard since PRC-004 and the column this value is copied into; a test now fails if the two ever disagree. **The cast was proven safe before the migration was written**, because the answer decides whether it is safe at all: PostgreSQL converts `float8` to `numeric` through the float's SHORTEST round-trip text form, not its binary expansion, so `44.7291` becomes exactly `44.7291` and not `44.729100000000002`. The same experiment showed what the cast does NOT preserve — `44.72915 → 44.7292`, `0.00005 → 0.0001`, `0.00001 → 0.0000` (which also violates `ck_matrix_row_price`) — so the migration **counts any row with more than four decimals first and aborts naming them** rather than silently changing a price. Verified by execution, not assertion: nine representative prices written as `float8`, migrated, and compared row by row (all numerically identical); the `up → down → up` round trip preserves every value; and a deliberately-planted five-decimal price aborts the migration and leaves the column untouched. **Contract change:** `unit_price` now serialises as a STRING in API responses, like every other money field on this API (`payment.amount`, `settlement.net_amount`) — the tests that asserted a JSON number were encoding the old inconsistency. Requests may still send a number; Pydantic parses either into `Decimal`. The admin portal (`string | number` on both the request and response types) and the Flutter client (`(json['unit_price'] as num)` would have THROWN on a string) were both updated. `from_value`/`to_value` deliberately remain FLOAT: they are band BOUNDARIES compared against a quality reading, not money, and converting them changes which band a boundary-valued reading selects — a behavioural change to BR-0004 that needs its own analysis. New PostgreSQL-only suite `test_pricing_precision_postgres.py` (5 tests, wired into `postgres-proof.sh`), because SQLite has no numeric type with a declared scale and would accept every assertion while storing a float. Divergence #61 closed; [DBD-0002 §3b](docs/07-data/DBD-0002-integrity-lifecycle-and-numbering.md).

- DEPLOY-001 "Deployment Rehearsal + Pending-Work Audit" — the application layer executed from a CLEAN git clone and a FRESH virtualenv against **real PostgreSQL 16.2, real Redis 6.2.14 and real MinIO**, with the API served by a real uvicorn process over real HTTP. Migrations applied from an empty database (59 tables, 53 RLS policies, 53 forced, 0 unforced), the least-privilege `NOSUPERUSER NOBYPASSRLS` role was created and asserted, and `prod` was shown to REFUSE `event_bus=memory` and development database credentials by actually failing to start. The full business chain ran on that database: `STL-2026-000001` → `PAY-2026-000001` → `RCP-2026-000001`, 5,647.50 KES, five SMS notifications dispatched in dry-run, zero dead letters. **The rehearsal found what it was for.** Divergence #42 rated two consumer runners on one database "safe (CAS dispatch + idempotency ledger) but untested"; running the API's own consumer loop alongside a second runner produced unique violations on `consumer_execution`, `receipt`, `notification_recipient` and `notification` — business data stayed correct because the constraints held, but every collision marked an execution FAILED, spent one of the event's five retries, and logged an error an operator would page on. A platform that cannot survive its own second replica cannot be scaled horizontally, which is what "workers on exactly one host" was papering over. Closed by a per-consumer `pg_try_advisory_lock` claim, plus savepoint get-or-create in the two places that used check-then-act (`SupplierDirectoryProjection` and `NotificationService.dispatch` — the latter is BR-0017's idempotency key, where a `SELECT`-then-`INSERT` gap turns a correctly-not-sent-twice message into a failed execution). **Three defects were found in that fix before it was accepted, all by execution:** a session-level advisory lock is CONNECTION-scoped, so returning the session to the pool carried the lock away and no runner could ever claim that consumer again (now released in `finally`); committing to release the claim's transaction discarded the `SET LOCAL` RLS bypass, so the runner then saw zero tenant rows, processed nothing and reported success — the exact MT-001 failure shape, reintroduced by adding a commit; and holding the claim session across the batch kept an uncommitted cursor INSERT open that `_advance_in` then waited on from another session, deadlocking a SINGLE runner. The suite itself had a fourth: it asserted only that nothing FAILED, which is trivially true when nothing is processed, and it never registered any consumers — a vacuous pass that the staging rehearsal, not the tests, exposed. `processed > 0` is now asserted. Also verified against the live schema rather than the models: 0 timestamps without timezone, 53/53 RLS forced, and **`pricing_matrix_row.unit_price` still `double precision`** — arithmetic is exact but the stored price is not, now the top data-integrity item before production. No hardcoded credentials, no tracked `.env` or key material, 180 OpenAPI operations all documented, portal build green, `flutter analyze` clean with 49 tests passing. **What is still NOT executed and is stated plainly: Docker, RabbitMQ, nginx, TLS and Terraform** — none is installable in this environment, so `docker-compose.production.yml`, the nginx configuration, systemd units and `deploy.sh` remain structurally reviewed only. QR-0007 C-1 is narrowed, not closed.

- PROD-001 "Production Hardening: Payment Concurrency, Safe Defaults, Email & Receipts" — the QR-0007 findings, executed rather than argued. **The payment locking strategy was found CORRECT** (QR-0007 said so and this re-proved it on PostgreSQL 16.2 across all four requested scenarios: same settlement, opposite-order multi-settlement, same supplier in parallel, and retry-after-failure), so the work went into the invariants nobody had tested around it. **That found a cross-tenant money leak.** `_allocations_for` and the `balances` subquery — the two queries that decide what a farmer is still owed — carried **no tenant predicate at all** and relied entirely on RLS, in direct violation of BR-0022's rule that application filters are defence-in-depth. Under a platform-bound session, or on SQLite where RLS cannot execute, another dairy's payment lines were summed into this tenant's allocated total; the executed test shows a settlement reading `fully_paid=True, outstanding=0`, meaning **the supplier could not be paid at all**. Both queries now filter in SQL, and the regression test reads under the RLS bypass deliberately so it fails if the filter is ever removed. Six invariants are now each an explicit assertion (no double allocation, no overpayment, no negative outstanding, no lost update, no deadlock, no cross-tenant interaction), every one verified to fail when its clause is removed. **Production now fails closed.** Beyond the notification channels ARCH-FINAL-001 caught, `prod` also accepted `event_bus=memory` and `outbox_mode=inline` (accept every publish, deliver nothing), `rate_limit_backend=memory` (each replica grants the full budget again), a `sqlite` or `lacteva:lacteva@` database URL, a `placeholder` PDF renderer, and a gateway selected but unconfigured. All refused at startup, with a reference-configuration test as the control so a passing refusal cannot be an artefact of a broken baseline. **Email has a real transport**: `SmtpEmailProvider`, vendor-neutral by design (SES, SendGrid, Postmark, Mailgun and a co-op's own relay all speak SMTP) and dependency-free — stdlib `smtplib` in `asyncio.to_thread`. Failure classification follows the protocol exactly (5xx and refused addresses/credentials permanent, 4xx and transport transient, anything unfamiliar retryable); the `Message-ID` is derived from the notification id and **stable across retries**, which `email.utils.make_msgid` was not — it mixes in a timestamp, so the first implementation minted a new id per attempt and defeated its own idempotency, caught by a test. **Receipts are real PDFs**: `modules/receipt/pdf.py` writes PDF 1.4 directly with the base-14 fonts — no ReportLab, no Cairo/Pango, no headless browser in the payment path of a single-host village deployment. Deterministic (no embedded timestamp, so an artifact is checksummable without being stored), escaped at the literal-string boundary because supplier names are user input, and verified independently by poppler rather than only by its own parser. Building it exposed that **`GET /receipts/{id}/download?format=pdf` served base64 TEXT under `application/pdf`** — the route called the JSON view's `render()` — so no reader could open a downloaded receipt; `render_artifact()` now keeps the two callers apart. `payment.completed.v1` was enriched so the receipt can say what the money was FOR (issuing dairy, collection center, quantity, weighted average rate); per-collection FAT/SNF are deliberately absent, because a settlement period spans many collections at different quality-based prices and a single "the FAT" would be a fiction. **Tenants can now leave**: `/v1/tenant-data/{export,offboarding-plan,offboard}` with a three-way PURGE / ANONYMIZE / RETAIN classification, because erasure and tax retention genuinely conflict — after offboarding, "how much did this dairy pay in July 2026" is answerable and "who was S-004821" is not. PURGE is the default for an unclassified table, since a table nobody thought about is more dangerous kept than deleted; offboarding requires the organization's exact name as confirmation. The test asserting parent/child consistency caught the first classification being wrong (`supplier_profile` anonymized while `supplier` was purged, orphaning it). **Financial document numbers** moved from `secrets.token_hex(3)` to per-tenant, per-type, per-year sequential series (`RCP-2026-000001`) allocated under a row lock — Kenya's eTIMS, India's GST rules and the EU VAT directive all require a sequential series on a receipt, and the old check-then-act loop also raced. Not gapless under rollback, which is the standard trade and is documented as such. New governed document [DBD-0002](docs/07-data/DBD-0002-integrity-lifecycle-and-numbering.md) records the referential-integrity classification (7 must-enforce / 31 application-invariant / 22 not-a-reference / 6 historical, with enforcement deliberately deferred behind the deployment rehearsal because adding an FK to a populated table takes an ACCESS EXCLUSIVE lock), the v1 data-lifecycle strategy (no premature partitioning; `consumer_execution` named as the table that will hurt first), the numbering decision, and the application database role model now enforced at three levels. 3 migrations, all round-tripped on PostgreSQL 16.2 including against pre-existing rows.

- ARCH-FINAL-001 "Final Enterprise Architecture Review & v1.0 Freeze" ([QR-0007](docs/12-quality/QR-0007-final-architecture-review.md)): an independent Principal-Architect pass over every subsystem before pilot sign-off, conducted by executing guarantees rather than reading them. **Architecture 8.5/10, production readiness 6.5/10, backend NOT yet feature complete** (email has no transport, no printable receipt, no way for a tenant's data to leave the platform). **The central finding is that the platform's single CRITICAL invariant was protected by a source grep:** the two tests pinning ARCH-001's double-payment fix were `inspect.getsource()` string matches asserting the characters `with_for_update=True` appear in the method — and because `FOR UPDATE` is a no-op on SQLite, nothing in the 1,014-test suite could have caught its removal. The race is now **executed** against a real engine in `tests/test_payment_concurrency_postgres.py`, together with a **control that removes the lock and asserts the double payment does occur** (2000.00 allocated against a 1000.00 payable); without the control, the passing test would prove nothing. Wired into `infra/ci/postgres-proof.sh`, where a skip is a hard failure. **Executing it properly found a new defect the lock itself had introduced:** `PaymentService.create` acquired settlement locks in CLIENT-supplied order, so two payments allocating the same two settlements in opposite order deadlocked — reproduced against real PostgreSQL as `DeadlockDetectedError` (SQLSTATE 40P01), reaching the operator as a 500 while paying a farmer, and needing nothing more exotic than one supplier with two unpaid settlements. Fixed by sorting allocations by settlement id so every transaction in the platform takes these locks in the same sequence; the new test was verified to fail with a deadlock when the ordering is removed. **A second class of finding: three production defaults were configured to look healthy while doing nothing.** Both notification channels default to `logging`, whose `send()` returns ACCEPTED — so a production deployment that changes nothing renders every message, records every delivery as accepted, keeps every dashboard green, and tells no supplier anything; `prod` now refuses `logging` and `placeholder` on either channel, leaving `dry_run` and `disabled` as the deliberate choices (email must now declare that it has no transport rather than pretend). And `LACTEVA_RLS_ENABLED=false` short-circuited `bind_tenant`, `bind_platform_context` **and** `assert_rls_is_enforceable` alike, so one environment variable both removed the tenant boundary and silenced the startup check that detects a SUPERUSER connection ignoring every policy — now refused in prod. Recorded and **not** implemented, because both touch delicate guarantees and deserve their own work orders: every consumer scans the entire event log with a separate session and commit per skipped event (O(consumers × events), ~240k wasted transactions/day at a modest dairy), and there is still no retention, archival or **tenant-deletion** path, so a pilot customer can be onboarded but not offboarded. Two Critical items block an unattended pilot and neither is a code defect — **the production stack has never been executed** (no Docker, host or `terraform apply` in any environment that has touched this repository, at exactly the maturity the database layer had before VER-001 found fourteen defects) and **backups share the database volume**, so the DR and PITR proofs restore from a copy that may not survive the incident requiring it.

- PITR-001 "Execute and Prove Point-in-Time Recovery" (**no business behaviour changed**): the physical recovery path, executed. This closes divergence #26, open across four work orders, and it was the last major guarantee on this platform that had never been run. **The headline finding is that the capability did not exist:** production had `wal_level=replica` and **no `archive_mode`**, a combination that looks configured for PITR and is not — `wal_level` makes WAL sufficient to replay, `archive_mode` is what makes it leave the server. Without it WAL is recycled in place, the only recoverable point is the base backup, and the documented **5-minute RPO was fiction** (the real RPO was the age of the last logical backup, up to 24 hours) while three documents described PITR procedures that could not have worked. Now configured in `docker-compose.production.yml` with an `archive_command` that **refuses to overwrite** (`test ! -f` first — silently replacing an archived segment destroys the recovery window from that segment forward and nothing reports it), an `archive_timeout` (a segment is archived when it FILLS, not when it is written, so a quiet night would otherwise leave the last transactions unarchived for hours), and a **separate `wal_archive` volume**, because an archive that dies with the data directory recovers nothing. **Four more defects, all found by executing:** (1) `pg-restore-test.sh` ran `alembic upgrade head` on the recovered instance — a physical restore is byte-identical to its source at the target, so migrating it MUTATES the recovered data by applying a migration that point in time never had, during an incident; it now asserts the revision instead. (2) Both scripts read the database before recovery finished: `pg_ctl -w start` returns when the server ACCEPTS CONNECTIONS, which during recovery is "ready to accept read-only connections" — before the target is reached and before promotion — so everything after it talked to a read-only, still-replaying database; both now poll `pg_is_in_recovery()`. (3) The retention prune could delete **every** base backup: `find DIR -maxdepth 1 -type d` matches DIR itself, so `rm -rf` removes the whole backup root; latent rather than active, because it only fires once `base/` is older than the window — which happens precisely when backups have stopped and the old ones matter most. (4) WAL retention was not tied to base-backup retention at all; the archive is now pruned against the **oldest retained base backup** with `pg_archivecleanup`, never against a date, and refuses to prune rather than guess when it cannot find the `.backup` label. **The timeline trap** is documented and closed: a recovered cluster promotes onto a new timeline, and if it archives, `recovery_target_timeline`'s default of `latest` lets the NEXT recovery follow the recovered timeline and overshoot its target with no error; recovered clusters now set `archive_mode=off` and pin the timeline. `./infra/ci/pitr-proof.sh` runs ten steps against a real cluster, **destroys the primary**, and recovers four times — to a timestamp, a transaction boundary (xid), a named restore point, and latest — asserting for each not only what is present but **what must be ABSENT**, which is the difference between proving point-in-time recovery and proving a restore. Money, receipts, 52 forced RLS policies and the schema revision are identical in every recovery. New docs: [PITR](docs/03-architecture/06-operations/PITR.md) and the [PITR-001 report](docs/03-architecture/06-operations/PITR-001-RECOVERY-REPORT.md); DISASTER_RECOVERY, BACKUP, RECOVERY_CHECKLIST, INFRASTRUCTURE and DEPLOYMENT corrected where they said PITR was unavailable. Six new tests, each verified to fail against the pre-PITR-001 configuration. Remaining: replica promotion, an off-host archive, and recovery time at scale.

- **Phoenix Software Engineering Standard** ([STD-0007](docs/00-standards/STD-0007-phoenix-software-engineering-standard.md)) — a permanent engineering directive rather than a work order: it has no scope, no deliverables and no completion, and it outlives whatever work order is in flight. It records the **project identity** (this repository is not a standalone application; it is the flagship product of Phoenix Software), the six operating scales Lacteva must serve in *one* architecture — individual farmers, collection centers, cooperatives, private dairies, milk unions, multi-country deployments — and **fifteen binding engineering principles**. Three of those get expanded treatment because they carry the most weight here. **Principle 6, every production guarantee must be executable:** stated more strongly than the rest because this repository has the evidence for it — VER-001 and DR-001 executed guarantees that were already written, already reviewed and already CI-wired, and found nine defects, four of them fatal (the platform could not serve one request on PostgreSQL; every RLS policy was inert because the application connected as a superuser; every backup aborted on a `time` column; a corrupt backup restored a settlement worth 1.00 instead of 5647.50). So a PostgreSQL guarantee tested only on SQLite is *untested*, a skipped proof is worse than an absent one because it is green, and a proof must show the guard is capable of *refusing* rather than merely present. **Principle 10, reusable platform capabilities over feature-specific implementations:** the Notification Engine rather than an SMS implementation, the Payment Framework rather than a Razorpay implementation — with the counterweight stated, since a capability with one implementation and no second in sight is speculative generality. **Review policy:** when an earlier decision is *objectively* incorrect, document it, correct it, update the documentation, and never preserve a mistake merely because it already exists — the bar deliberately above "I would have done it differently", as when ABR-002 correctly withdrew two of DBR-001's findings. Also establishes a six-dimension **Definition of Done** (implementation, tests, documentation, architecture consistency, operational impact, production readiness) where "considered and not applicable, because …" is a complete answer and silence is not. Wired into the permanent context: [CLAUDE_CONTEXT](docs/ai/CLAUDE_CONTEXT.md) §0 and its reading order, the standards index and precedence rules, `README.md`, `CONTRIBUTING.md` (PR rules and rejection criteria), and `docs/INDEX.md`. **No business functionality was changed** — this increment is documentation and engineering guidance only.

- ARCH-001 "Final Platform Production Readiness Review": an independent pass over every subsystem, reviewed as if the first dairy goes live tomorrow rather than as the author of the code. **Four production problems found and fixed, one of them critical.** (1) **Two concurrent payments could each claim the full outstanding balance of one settlement.** Allocating is a read-modify-write — read the live allocations, compute what is outstanding, refuse anything larger, insert the line — and nothing locked. Under READ COMMITTED a `SELECT sum(...)` takes no locks, so two transactions never conflict: both read the same sum, both see the full balance, both pass the check, and both insert. **The settlement is paid twice, and nothing detects it**, because partial payment is legitimate so no unique constraint can collide. The settlement row is now taken `FOR UPDATE` *before* the balance is read, which serialises payments against that settlement only — two payments to different settlements still run concurrently. (2) **The connection pool was never configured**, four work orders after ABR-002 rated it the highest-probability cause of the first production incident and put it first in the recommended order. The engine took SQLAlchemy's defaults: 5 connections, no `pool_pre_ping` (so a connection killed by a load balancer, a firewall idle timeout or a database failover is handed to a request and fails it — the "mystery 500s after a network blip" every Python service eventually reports), no recycle, and **no `statement_timeout` or `lock_timeout`** (so an unbounded query holds its snapshot and blocks VACUUM across the *whole* database, and a migration needing `ACCESS EXCLUSIVE` queues behind a long read while every subsequent query queues behind the migration — the classic lock pileup that takes an application down during a "safe" deploy). All configured, with sizing derived from a stated budget rule rather than inherited, and a test asserting the workers × pool product leaves headroom under `max_connections` so an operator can still connect during an incident. Because a 30-second request ceiling would have broken projection rebuilds, backups and deep integrity checks the moment it landed, `platform_session`/`PlatformSessionFactory` raise it to 15 minutes for cross-tenant work — **raised, never removed**, since "unbounded" is the condition that made a timeout necessary. (3) **The payables selector had no index matching its filter.** The screen an operator opens to pay people filters `(tenant_id, status='finalized')` and the only usable index started `(tenant_id, supplier_id, period_from)`, so PostgreSQL read every settlement a tenant had ever had to find the handful unpaid — five years of history is ~50,000 rows scanned to locate ~200. (4) **Money had no database-level guard.** The service refuses a non-positive payment; the database did not, in a schema with two check constraints across fifty-seven tables. `amount > 0` closes every path the service layer does not sit in front of. Migration `ced805436869`. **Also verified and found correct:** the outbox writes in the caller's transaction so a rolled-back business change cannot emit an event; the mobile and portal clients against every API change made since API-001 (page-size bounds now 422 rather than a silent clamp — all client limits are ≤100, checked by a test that reads the client source rather than assuming); the CI proof already runs every PostgreSQL-only module. 14 new tests (985 total), including two PostgreSQL tests that stage what SQLite structurally cannot: that the settlement lock genuinely serialises two concurrent claimants, and that the request path carries a statement timeout at all.
- MSG-001 "Production SMS Delivery Adapter": **suppliers can now actually be told.** Until this, the platform rendered every message, dispatched it off the durable log, retried it, and recorded it — and then handed it to a provider that discarded it. A farmer was never told they had been paid. The gap was documented honestly in three places and closing it was the last functional step in the primary business flow. **The adapter extends the NOT-001 abstraction rather than replacing it.** `send()` now returns a `DeliveryResult` — `provider_message_id` (what a support conversation with the gateway quotes), `status`, and `metadata` (segment count, cost, the gateway's own status string; never credentials) — because a bare reference string is enough to write in an audit trail and not enough to operate. **The central finding was not the adapter: it was that every failure was retried.** An invalid phone number consumed five gateway calls and five backoff windows to reach the answer it had on the first attempt; a missing template — a *deployment* fault, not a delivery fault — did the same, burying the real signal under a retry backlog. Providers now state permanence (`PermanentSendError`) and the retry engine honours it, sending those straight to `dead` on the first attempt. **The base error stays retryable**, so every pre-MSG-001 raiser behaves exactly as it did and an unfamiliar provider error is tried again rather than silently dropping a message a supplier is waiting for. A permanent failure is never a silent drop: recorded, counted, visible in the history, and retryable by an operator who has fixed the data. BR-0017 extended (register v1.16). **Vendor neutrality by construction:** `HttpSmsProvider` posts a small documented JSON contract and classifies outcomes by **HTTP status**, which every gateway agrees on even when their payloads do not — 400/401/403/404/422 permanent, 408/425/429/5xx retryable, timeout and network retryable. Dairy markets differ by country and a deployment may change provider without touching code; a gateway whose shape does not fit implements `ChannelProvider` and is installed through the `register_provider` seam NOT-001 already built. **Idempotency:** every send carries `Idempotency-Key: lacteva-{notification_id}`, stable across every retry, because the one double-send the platform cannot prevent alone is a message the gateway accepted and whose response we lost — only the gateway knows, so it is told. The platform's own uniqueness on `(event_id, template_key, channel)` stops a duplicate *dispatch*; this stops a duplicate *delivery*. **Four modes**, and the distinctions are operational rather than cosmetic: `logging` (dev), `placeholder` ("no gateway configured yet"), **`dry_run`** (renders and logs a real message against production-shaped configuration *without sending* — staging, so a credential or sender-id mistake surfaces before a farmer sees it), `http`, and **`disabled`**, which raises permanently rather than succeeding silently, because a notification marked sent that was never sent is a lie the platform would then repeat to whoever asks why a supplier was not told. An unknown provider name is a startup failure, not a message that quietly goes nowhere. **Security:** `mask_phone()` turns `+254700123456` into `+2547****3456` and is applied at every log site — a log carrying every supplier's number is a copy of the directory with weaker access control than the database it came from; gateway error bodies are truncated to 200 characters before reaching an exception, because they echo the request often enough to carry the number and occasionally the credential; the API key is sent as a bearer header and never logged, and belongs in a Docker secret. **Observability:** a new `notification_provider_errors_total{channel,provider,kind}` where `kind` is a three-value vocabulary — permanent, transient, timeout — never the provider's error string, which is unbounded and partly attacker-influenced; existing sent/failed/dead/retry/latency metrics unchanged. SMS **segment count** is reported in delivery metadata and the dry-run log, because segments are what a gateway bills and a template that quietly crosses the 160-character boundary (70 outside GSM-7) doubles the cost of every message it sends. 41 new tests (971 total) covering success, every transient status, every permanent status, timeout, unreachable gateway, unparseable and wrong-shaped 2xx responses, duplicate dispatch, stable idempotency keys, all five modes, configuration failures, PII masking, credential leakage, and metric cardinality. Docs: [NOTIFICATION-ENGINE](docs/03-architecture/04-technology-layer/NOTIFICATION-ENGINE.md) v1.1, `.env.production.example`, DEPLOYMENT.md and INFRASTRUCTURE.md — whose readiness checklists now say to prove SMS in `dry_run` on staging first, since a wrong sender id is a permanent rejection and suppliers would silently stop being told they were paid.
- IDM-001 "Platform-wide Idempotency Framework": one capability on **every** POST/PUT/PATCH, not a payment-specific solution. A client on a poor network cannot distinguish a lost response from a lost request; it retries, and without help the platform performs the operation twice. This platform is explicitly built for field use over intermittent connectivity, so that is the normal case rather than an edge case. **Three partial answers already existed** and each solved its own problem well — `payment.idempotency_key` (a business *intent*), `sync_operation.operation_id` (one captured operation across batches), `consumer_execution` (one consumer handling one event) — and none of them dedups an **HTTP request**, which is what a retrying client actually repeats. The framework adds that layer and deliberately replaces none of them: they mean different things, and a payment key that survives across two genuinely different requests is a guarantee worth keeping. **The design's central property is that the reservation, the business write and the stored response share ONE transaction.** That required establishing where the pieces can see each other: a router-level dependency has the request's session but never sees the response; a route class has the response and — because FastAPI closes dependency teardown *after* the route handler returns — the session is **still open** when it regains control. That ordering was verified with a probe before the design was committed to, and is now pinned by a test, because if it ever changes the framework would silently stop storing anything. The alternative, a separate transaction for the reservation, leaves a key claiming an effect that never happened and refuses the retry until it expires — stranding exactly the client the framework exists to help. **Behaviour:** a retry after completion replays the original response verbatim (same status, same body, `Idempotent-Replay: true`); a retry while the first is in flight gets 409, because inventing an answer is worse than asking the caller to wait; the same key with a different body gets 400, because replaying would silently discard the second request; a failed operation **releases** its key, since a failure holds no effect worth deduplicating and answering every future retry with it would be wrong. Keys are 1–128 characters, and an **empty header is refused rather than treated as absent** — a client that sends one believes it is protected and is not, and silent non-protection is the failure the framework exists to remove. The fingerprint is a sha256 of method, path and body, never the body itself, because bodies carry credentials and PII and this table has a retention period. **Two defects were found and fixed during implementation.** `include_router` carries each child's own route class through (`route_class_override=type(route)`), so declaring it on the parent alone built every route with the wrapper absent — idempotency would have appeared enabled while storing nothing; the declaration now lives on all 26 sub-routers and a test asserts 174 of 174 `/v1` routes are wrapped. And router-level dependencies run **before** authentication, so `get_current_tenant()` reflected only the `X-Tenant-ID` header — which token-authenticated clients do not send — putting every tenant's keys in one namespace, the same class of defect MT-001 found in the rate limiter; the guard now derives the tenant from the token claim, which is authoritative and costs no database round trip. **Also:** tenant-scoped `(tenant_id, key)` uniqueness with an RLS policy (SEC-002 made an unprotected tenant table a build failure, and this is the first new table since); configurable retention (24 h) swept by a background worker on a timer, small and frequent rather than one large DELETE that would lock the table the request path reads; five metrics (replays, stored, conflicts, mismatches, swept) with the key never used as a label; structured logging; localized messages in all three languages; migration `f73f41473469`. 21 new tests (930 total) — duplicate POST and PUT, mismatched body, empty and oversized keys, failure-releases-key, replay after restart, tenant scoping, expiry and reuse-after-expiry, plus three PostgreSQL tests for the guarantees SQLite structurally cannot stage: SQLite's `StaticPool` gives the whole process one connection, so two "concurrent" requests share a transaction and the unique constraint never fires. [API-0001](docs/06-api/API-0001-platform-core.md) v1.1 documents the capability and closes its own §8.1.
- API-001 "Complete REST API Architecture Review": all **177 operations across 155 paths** reviewed as if preparing a public SaaS release, which changes what counts as a defect. **Three fixes, each architectural rather than local.** (1) **The error contract was never published.** The platform has always RETURNED RFC 9457 problem details — `type`, `title`, `status`, translated `detail`, machine-readable `extra`, `application/problem+json`, `WWW-Authenticate` on 401 and `Retry-After` on 429 — and the OpenAPI document declared exactly **one** non-2xx response, FastAPI's automatic 422. Every generated client therefore treated an error body as an unknown shape, and every integrator would have learned the real contract by causing errors in production. Now published from one place by three mechanical rules: every `/v1` operation declares 401/403/422/429, an operation with a path parameter declares 404, an operation that mutates declares 409 — applied in `main._publish_error_contract` rather than as a `responses=` argument repeated on 177 routes, because a per-route list drifts and nothing fails when one forgets. 174 operations now document the universal set, 95 document 404, 104 document 409. (2) **Page sizes were clamped silently.** Services did `max(1, min(limit, 100))`, so a client paginating with `limit=1000` believed it had read 1000 records, received 100, then jumped to `offset=1000` — **skipping 900 rows it never saw**. Silent clamping turns a page-size mistake into missing data. Every paginated route now declares its bound (`Query(20, ge=1, le=100)`), so the maximum is published in OpenAPI and an out-of-range value is **rejected with 422** rather than quietly honoured as something else. (3) **`/v1/collection-sessions` had no bound at all** — the one business list returning every row, and sessions are opened ~2 per center per day and never deleted, so a tenant with sixty centers accumulates ~44,000 a year into a single response. Now paginated with the same `items/total/limit/offset` envelope as the other thirteen. Also added: the conventional **`Idempotency-Key` header** on payment creation (paying twice is the worst outcome this API has, and a mobile client on a village connection cannot distinguish a lost response from a lost request; the header is accepted alongside the existing body field and wins when both are present). **Reviewed and found correct:** REST semantics throughout (201 for creation, 200 for state transitions on an existing resource, 204 for deletion — the distinction is deliberate and now asserted), CAS-guarded transitions making every state-changing POST retry-safe by construction (the second attempt gets 409, not a double-apply), tenant isolation (a resource in another tenant is 404, never 403, so the API does not confirm it exists), the token's authority over the `X-Tenant-ID` header, audit coverage on state changes, correlation-id propagation, presigned downloads issued only after the tenant-scoped resource check, and the closed set of 7 unauthenticated endpoints — now asserted by test, so a new public endpoint must be added deliberately. New [API-0001](docs/06-api/API-0001-platform-core.md), the first document in a layer whose own rule says an undocumented endpoint is an incident: conventions, the error table with retry guidance per status, the pagination rule (grows with business volume → paginate; bounded by structure → array is fine), retry safety per method, and **seven recorded limitations with the reason each is acceptable** — no general idempotency, no `ETag`/`If-Match`, no client-controlled sorting (an unindexed sort is a way to take the platform down from a query string), no cursor pagination, no batch endpoints, no cache headers, no API-level timeout. 17 new tests (909 total) that assert the contract over the whole OpenAPI document rather than per handler, including that an out-of-range page size is rejected rather than clamped and that a repeated payment request does not pay twice. The Flutter client's `listOpenSessions` was updated for the paginated envelope — the one consumer the change touched, found by grep rather than by a broken build.
- MT-001 "Full Multi-Tenancy Audit": every endpoint, service, repository, projection, consumer, background job, cache key, event handler, migration and reporting query reviewed against the tenant boundary. **Three real defects, one of them severe.** (1) **The bypass was documented and never implemented.** SEC-001 stated that "the relay dispatcher, consumers, and projection rebuilds set `lacteva.bypass_rls`" — nothing did. Those components built sessions from the ordinary factory, which binds neither a tenant nor a bypass, so on PostgreSQL the policy evaluated to false on every clause: `current_setting` returns NULL when unset, `NULL = 'on'` is not true, and `uuid::text = NULL` is not true either. **The entire asynchronous half of the platform could see only platform-global rows** — the relay would find no tenant events to dispatch, consumers would consume nothing, and every projection write would be refused by `WITH CHECK`. No error, no exception, no alert: requests succeed, milk is recorded, and no receipt is generated, no notification sent, no projection updated. That is the failure shape the platform's own runbook calls the most dangerous it has, and SQLite could not catch it — the fourth defect of exactly that shape. Fixed with a **`PlatformSessionFactory`**: components whose job spans tenants (relay, consumer runner, projection rebuilder, backup engine, health probes, the ops APIs) are constructed with a factory whose every session binds the bypass and logs the reason. A factory rather than a call at each of ~25 sites, because a component built with it *cannot forget*, and one built with the ordinary factory is visibly request-scoped. (2) **The per-identifier rate-limit key was not tenant-scoped.** Email is unique *per tenant* (`uq_user_tenant_email`), so `alice@example.com` can be two different people in two organizations — and both were charged to one Redis counter. An attacker with an account anywhere could exhaust that address's login budget in **every** tenant by failing to log in to their own: a cross-tenant denial of service on authentication. `RateLimitRule.key()` now takes a tenant, and the login route passes it. (3) **The notification dispatcher resolved recipients by `subject_id` alone.** Harmless while UUIDs do not collide — but dispatch runs inside the bypass, where RLS is switched off by design, so that filter was the only thing standing between a payment notification and *another dairy's phone number*. Now scoped by tenant as well. **Reviewed and found correct:** object-storage keys (tenant-prefixed, with `platform/` for tenantless objects), document download (resolves the supplier first, which is tenant-scoped), receipt rendering and every receipt query, pagination totals (counted over the already-filtered statement, never a fresh select), all reporting queries including the `settlement_line → settlement` join, audit records (written with and read within a tenant), the notification idempotency key (`event_id` is globally unique, so scoping by it scopes by tenant transitively), JWT claims (the token's tenant is authoritative and a header cannot override it — asserted), and backup/restore (whole-database by definition, and now correctly platform-bound). **No websocket endpoints exist**; a test asserts that, so the first one added fails until its tenant binding is designed — a socket outlives the request that authenticated it. BR-0022 extended (register v1.15): the bypass **must** be set, inside a bypassed session the application filter is the *only* isolation, and a tenant boundary is not only a database boundary — any key namespace built from a per-tenant-unique identifier must carry the tenant. New [RLS-GUIDE §3d](docs/03-architecture/05-security/RLS-GUIDE.md) documents the boundary and the two-factory rule. 22 new tests (892 total), including three PostgreSQL tests that demonstrate the defect rather than argue it: an unbound session sees no tenant events, an unbound projection write is refused, and the platform binding lets a consumer do its job.
- INF-001 "Infrastructure as Code & Production Environment" (**infrastructure only — no business logic, API or schema changed**): a production environment can now be provisioned from zero. **Terraform** for Hetzner Cloud (primary) and AWS (an optional abstraction, deliberately thin — two half-maintained infrastructure definitions are worse than one maintained one, and the second is always the one nobody has applied since March): one VM, one **static IP and one data volume that outlive the machine**, one firewall, SSH keys, provider snapshots. That IP-plus-volume pairing is the whole server-replacement story — build a new machine, re-attach both, deploy; DNS never changes, so no propagation wait and no certificate reissue. `prevent_destroy` on both, and `ignore_changes = [size]` on the volume because it can be grown online and never shrunk, so a smaller number in tfvars must not plan a destroy-and-recreate of the volume holding production data. **Terraform deliberately does not format the volume** — cloud-init does, and only when `blkid` finds no filesystem, because a `format` attribute lets an apply after a state mishap reformat a live database. **cloud-init** installs Docker (with `live-restore`, so a daemon upgrade does not take the platform down), builds the filesystem standard (`/opt/lacteva/releases` + `current` symlink, root-only `/etc/lacteva`, `/var/lib/lacteva` and `/backup` on the data volume), hardens SSH to keys-only with no root login, brings up ufw **and** fail2ban as a second layer inside the machine — the cloud firewall sits outside it and holds even mid-boot or after somebody flushes iptables while debugging — configures chrony (**not cosmetic**: the platform signs JWTs with a 30-second leeway, and a drifting clock rejects every valid token while looking exactly like a key problem), logrotate for host-written logs (a nightly backup log otherwise fills the volume the backups are written to), and enables security-only unattended upgrades with **automatic reboot off**, because rebooting a single-host platform without warning is an unplanned outage. **Firewall: 80, 443, and SSH from named ranges only** — both configurations *refuse `0.0.0.0/0` at plan time*, since key-only auth reduces the risk of exposing sshd to the internet without removing it. **systemd** starts the stack on boot with `RequiresMountsFor=/var/lib/lacteva` (starting before the volume is mounted creates an empty PGDATA on the root disk, silently) and a `TimeoutStopSec` that exceeds the API's 90-second stop grace, so systemd cannot kill the drain DEP-001 exists to make possible. **Backups on timers:** nightly logical (taken, then **verified**, and only then pruned — pruning first means a failing job deletes its way through the retention window and the day you need a restore there is nothing left), weekly physical, and a weekly **restore verification** that loads the newest backup into a throwaway database and runs deep business integrity including a projection rebuild, per BR-0025. All timers are `Persistent=true` so an overnight reboot does not silently skip a night. **`deploy.sh`** is one command: pull → pre-deployment backup → migrate → up → verify → smoke test, with **automatic rollback** on any failure past the migration, because the alternative is a half-deployed platform sitting broken until somebody notices. It never rolls the schema back automatically — a code rollback is safe after an expand-only migration and unsafe after a contract, and no script can tell from the outside — but it reports when the schema moved and points at the compatibility matrix. New [INFRASTRUCTURE.md](INFRASTRUCTURE.md): topology, provisioning, deployment, a scaling table naming what binds first (disk, then PostgreSQL I/O, then consumer CPU, then API concurrency), secret rotation procedures that all follow *add the new one, confirm, remove the old*, maintenance cadence, server replacement, disaster recovery, and a production readiness checklist. 25 new tests (870 total) asserting the properties whose absence is dangerous: SSH cannot be opened to the world, only three ports are reachable, the volume and IP cannot be destroyed, Terraform never formats, cloud-init never reformats a volume that has data, IMDSv2 is required (IMDSv1 turns any SSRF into instance credentials), AWS volumes are encrypted, systemd waits for the mount and allows the full drain, retention runs only after verification, and deploy never invokes `alembic downgrade`. **Nothing here has been applied** — no Terraform binary, cloud account, or host exists in the development environment; the configurations were validated structurally and by those tests. **The largest gap this work order records rather than closes: backups live on the same volume as the database**, so provider snapshots are the only independent copy, and shipping logical backups off-host is the single highest-value remaining piece of infrastructure.
- DEP-001 "Production Deployment Automation" (**no business behaviour, API, or schema changed**): the platform becomes deployable. A nine-container production stack (`docker-compose.production.yml`) with **one published port** — nginx — and everything else on `expose:` only, because reaching the database should be a decision someone makes rather than a port someone forgets. **Startup ordering is by health check and contains no sleep at all** (a test asserts it): postgres and redis must pass `pg_isready`/`PING`, then a one-shot `migrate` service runs `alembic upgrade head` and must **exit zero** before the API is allowed to start — `restart: "no"` is the load-bearing line, because a restart policy would turn a clear migration failure into a crash loop that looks like a slow start, and `service_completed_successfully` then never fires so nothing serves traffic against a schema that did not apply. **Two operational defects were fixed on the way.** (1) **Shutdown abandoned work.** The relay, consumer and health loops were `task.cancel()`ed, which throws wherever the loop happens to be — possibly between a consumer's write and the ledger row recording it. Safe (the transaction rolls back and the event retries) but not clean: every rolling deploy left work to redo. Shutdown is now cooperative — `workers.sleep()` wakes on a flag, each loop finishes the unit of work it is in and exits at its next sleep, stragglers are cancelled after a grace period, and the log reports `drained` versus `cancelled_after_grace` per worker because that difference predicts whether the next start has catching up to do. The engine is disposed last, after the loops, since disposing it while a consumer holds a session turns a clean shutdown into a stack trace. (2) **`/health/ready` was a `SELECT 1`.** A load balancer was told an instance was ready while its consumer loop was dead and nothing downstream was happening — this platform's most dangerous failure shape, because it looks healthy. Readiness now aggregates the same nine probes the ops endpoint and every Prometheus alert use, **degraded stays ready** (only `critical` removes an instance; taking a degraded instance out of rotation turns a partial problem into a total one), and it answers from the background sampler's most recent evaluation rather than running nine probes per poll, because a health check that is itself a load source is how a wobble becomes an outage. The response's `status` field keeps its original two-value vocabulary — DEP-001 is not allowed to move a contract — with the four-level detail added beside it. **Also new:** `.env.production.example` with every variable documented and a test that fails on an undocumented one; **Docker Secrets** support via pydantic-settings' `secrets_dir`, so a signing key need never appear in an environment block; production nginx (HTTPS, HSTS, gzip, websocket upgrade, 25 MB uploads, edge rate limiting, static caching, and `/metrics` restricted to private networks — publishing it would expose tenant counts and error rates); Loki + Promtail reading the container logs the platform already writes, so nothing ships from inside the API process; `infra/deploy/verify-deployment.sh` (readiness, every component, schema revision matches the image, **RLS coverage and FORCE** — a database restored from a pre-SEC-002 backup can serve traffic with the policies simply absent — Redis, outbox actually draining, nginx); and `infra/deploy/smoke-test.py`, which creates its own throwaway tenant, never deletes, and polls for the consumer-generated receipt rather than sleeping. [DEPLOYMENT.md](DEPLOYMENT.md) covers deploy, upgrade, rollback, backup, restore, disaster recovery, version upgrade and troubleshooting — including the **rollback compatibility matrix**: expand-only migrations roll back freely, contract migrations do not, and `alembic downgrade` on a live database drops columns holding data written since the upgrade, so it is a development tool and the honest options are roll forward or restore. 23 new tests (845 total). **Nothing here has been executed** — no Docker or production host exists in the development environment; the artefacts were validated by parsing, static analysis, dry-run against stubs, and tests that assert their contents.
- OPS-001 "PostgreSQL Continuous Verification" (**verification infrastructure only — no platform code changed**): the PostgreSQL-only guarantees get their own pipeline. Five work orders had accumulated proofs that SQLite structurally cannot evaluate — RLS enforcement and coverage, exact numeric aggregation, a scaled numeric column rounding on store, migrations applied to an empty database, and a restore verified rather than reported — and every one of them had already shipped a defect that only a real engine surfaced. They now run in **`.github/workflows/postgres.yml`**, a dedicated workflow that a clean checkout executes end to end. **A version matrix, not a version:** `postgres:16` (the production baseline documented in DBD-0001) and `postgres:17` (the newest release this repository has actually executed against), both required, `fail-fast: false` because learning that 16 passed while 17 failed is the entire point. A single `PostgreSQL verified` job depends on the matrix so branch protection names one check and adding a version later cannot silently stop gating merges. **Continuous, not merely on-change:** the workflow also runs nightly at 03:17 UTC, because a dependency bump or a base-image change can break a guarantee without anyone touching the repository. **Skips became impossible rather than detected.** CI-001 grepped pytest's output for `N skipped` after the fact; a new `tests/postgres_support.py` now raises at *collection* when `LACTEVA_REQUIRE_POSTGRES=1` is set and no database URL is present — a collection error fails the run before any test executes, so it cannot be mistaken for a passing suite — and the proof script re-asserts zero skips, zero failures and non-zero collected from `pytest --junitxml`, structured output rather than prose, because pytest's summary line has changed format before and the XML attributes have not. Verified by dry-running the script against stubbed `psql`/`pg_isready`/`uv run`: steps 0–3 execute in order, the skip assertion fires (`3 PostgreSQL test(s) SKIPPED — a green skip is not a proof`), the missing-report guard fires, and the summary renders. - DB-002 "Exact Numeric Aggregation" (**no API response changed; the reporting module was not redesigned**): the last correctness gap the Architecture Board reviews had left open. Money was already exact — `Decimal(str(x))` arithmetic, `NUMERIC` columns, an explicit rounding policy (BR-0005) — but **aggregation was not**. `net_weight`, `fat` and `snf` are `double precision`, and floating point addition is not associative, so `SUM(net_weight)` depended on the order the planner happened to produce; that order changes with statistics and with parallel workers, and the result was written into a `NUMERIC(16,3)` projection column, which made a non-reproducible number look exact. **Every aggregation in the platform was reviewed and classified**: 13 required conversion (all in `reporting/service.py` — the daily, per-center and per-supplier weight sums, the weighted fat/SNF numerators and denominators, and the two `ORDER BY SUM(...)` clauses), 1 was accepted as lossy-but-harmless (`AVG(event_delivery.latency_ms)`, an operational metric), and the rest were already safe (integer counts, and sums over `NUMERIC` — `gross_amount`, `settlement_line.gross_amount`, `payment_line.amount`, `AVG/MIN/MAX(unit_price)`). The fix is one helper: `_exact()` casts to unconstrained `NUMERIC` inside the aggregate, so the arithmetic stays in SQL and only its exactness changes — deliberately unconstrained, because pinning a scale would round every ROW where the platform rounds the TOTAL once. On PostgreSQL `float8::numeric` renders the shortest decimal that round-trips, the same rule `Decimal(str(x))` follows, so a weight aggregates as the value it displays as. **A second, unreported divergence was found while testing the first:** the reporting projection rounded its running total whenever a flush happened to occur — once per event for the incremental consumer, once per BATCH for the rebuild engine — so a rebuilt projection did not reproduce the incrementally built one, and two rebuilds at different batch sizes disagreed. Six weights of 0.0005 kg came to 0.006 incrementally and 0.003 in one batch: the same events, the same log, two different totals, and no error anywhere. **That was a hole in BR-0015**, whose whole promise is that a rebuilt projection is provably identical to an incrementally built one. The handler now quantizes to the column's own scale at every step, making the flush boundary irrelevant. Registers: BR-0005 extended to SQL aggregation, BR-0015 gains flush independence (register v1.14). 28 new tests: order independence over random insertion orders, rebuild-versus-incremental at batch sizes 1/2/5000 driven through the real projection engine, repeated-rebuild byte-identity (`Decimal.as_tuple()`, not just equality — a value comparing equal with a different exponent still serialises differently), decimal edge cases including classic half-way values, a 10 000-row exactness check, a structural guard that fails if a future report sums a float column directly, and a new PostgreSQL-only module proving the two premises SQLite cannot exhibit — that `SUM(float8)` is order-dependent while `SUM(float8::numeric)` is not, and that `numeric(16,3)` **rounds on store**, which is why the projection divergence was invisible in the main suite. Both are now wired into the CI proof job. **Still open and explicitly out of scope:** the column *types*. `pricing_matrix_row.unit_price`, `from_value`, `to_value` and the three weight columns remain `FLOAT`; this work order made the aggregation exact, not the storage.
- SEC-002 "Complete PostgreSQL RLS Coverage" (P0 — **no business behaviour or API changed**): the architecture principle *every table has an explicit isolation strategy* becomes something the build can check. Each of the 56 tables now declares exactly one of three: **tenant-owned** (carries `tenant_id`, standard policy — 50 tables, derived from the metadata rather than listed, because a hand-kept list is how a new module ships unprotected), **platform-global** (deliberately unprotected, **with the reason on record** — 5 tables), or **mixed** (both kinds of row, or isolated by a column other than `tenant_id` — 12 entries). `unclassified_tables()` returns nothing and a test asserts it, so "nobody decided" is a build failure. **Thirteen tenant-owned child tables gained `tenant_id` and a policy** (migration `f2d18ba60c47`): supplier profiles, bank accounts and documents, settlement lines, payment lines and attempts, receipt lines, price bands, center config/windows/calendar, device health reports, role permissions. They were reachable only through a parent, so SEC-001's "does it have a tenant_id column" rule skipped them and BR-0022's promise — *a query that forgets its filter returns NOTHING* — was simply false for them; `supplier_profile` (names, phones, national IDs) and `supplier_bank_account` (account numbers) were the worst of it. Denormalising is safe because no aggregate here is ever reparented. **`organization` gained an identity policy**: it has no `tenant_id` because it IS the tenant, so it was readable by any bound session and a tenant could enumerate the platform's customer list; it now compares its own primary key, with **no `IS NULL` escape** — creation and platform-admin reads take the audited bypass instead, because both are genuinely cross-tenant acts. **A worse defect was found while verifying the flows: authentication itself was broken under RLS.** `get_current_principal` read `auth_session` and `user_account` — both tenant-owned — and only *afterwards* re-bound to the token's tenant, so under RLS the session row was invisible to the request that owned it and every authenticated call without an `X-Tenant-ID` header would have failed as 401. The token is signed and self-contained, so its tenant claim is authoritative before any row is read; binding now happens there. Three more pre-tenant flows were repaired the same way: **tenant-scoped login** (the tenant is named in the request body, which the middleware never sees), **invitation acceptance** (anonymous, and `invitation` is tenant-owned — resolved by the narrowest possible bypass, one indexed read by token hash, then an immediate bind), and **organization creation** (nobody can be bound to an organization that does not exist yet). `rebind_tenant()` now moves the context variable and the database binding together — `set_current_tenant()` alone left the binding behind, which presents as "the row is invisible to the request that owns it" and was the second half of the same defect. `password_reset_token` is deliberately **not** protected and the reason is recorded: the flow that reads it is definitionally unauthenticated, and a policy there would make password reset impossible for every tenant-scoped user. 22 new tests — 14 PostgreSQL tests running against the **real migrated schema** rather than a synthetic probe table (coverage of enable+force+USING+WITH CHECK across every tenant table, cross-tenant read/insert/update/delete on `settlement_line` and `payment_line`, PII isolation on `supplier_profile`, organization identity isolation, and the bootstrap/registration/invitation/anonymous/role-catalog flows), plus 8 that run on SQLite including `test_authentication_binds_the_tenant_before_reading_any_row`, which records binds and reads on one timeline and was verified to fail against the pre-SEC-002 order. The CI proof script now asserts policy **coverage** rather than policy count — counting would have passed while the money and PII tables sat unprotected, which is exactly what happened. Docs: [RLS-GUIDE](docs/03-architecture/05-security/RLS-GUIDE.md) v1.2 (the A/B/C taxonomy and a table of every pre-tenant flow), BR-0022 extended (register v1.13), [DBD-0001](docs/07-data/DBD-0001-platform-core-database.md) v1.1 — which also **strikes findings F-4 and F-9 as measurement errors**: both were derived from `str(column.type)`, which renders through SQLAlchemy's default dialect, and all 97 timestamps are already `TIMESTAMPTZ` and all 176 ids already native `uuid` on PostgreSQL.

- CI-001 "PostgreSQL Proof" (Phase B, P0 — **infrastructure and verification only; no business behaviour or API changed**): every PostgreSQL-dependent guarantee moves from *documented* to *proven*. Three work orders in a row had ended with a P0 guarantee that was written, tested, and CI-wired but **never actually executed**, because the test stack is SQLite and the guarantee is PostgreSQL-specific. One script — `infra/ci/postgres-proof.sh`, run identically by GitHub Actions and by `docker compose -f docker-compose.proof.yml run --rm proof`, because two pipelines agree until the day it matters — now performs nine steps against a real engine, any of which fails the build: **migrations applied to an EMPTY database** (not incrementally); **RLS enabled AND forced** on every tenant table (`relrowsecurity` alone lets the owner bypass its own policy); the **RLS suite passing and provably not skipped** (a silently skipped security proof is worse than none, because it is green); **a real dairy seeded through the platform's own API** (an empty database restores perfectly and proves nothing); a **logical backup taken and checksum-verified**; a **second, fresh database migrated**; the backup **restored into it**; **deep business integrity** on the restored data (settlements balance, allocations reconcile, receipts are one-per-payment, projections rebuild from the log); and a **fact-by-fact comparison** of source against restored. **Running it for the first time found three defects that every existing test had passed over.** (1) The RLS predicate hid every platform-global row: SQL three-valued logic makes `NULL = 'x'` neither true nor false, so rows with `tenant_id IS NULL` — user accounts before they join an organization, the role catalog, the outbox log — were invisible and un-insertable, meaning **registration itself would have failed on the first production deploy with RLS enabled**; fixed by migration `c94b1ea27f31` adding an explicit `OR tenant_id IS NULL` to both `USING` and `WITH CHECK`, and BR-0022 amended to say so. The old `row-level-security` CI job is replaced by `postgres-proof`. New doc: [POSTGRES-PROOF](docs/03-architecture/06-operations/POSTGRES-PROOF.md), including how to read each failure and what is still unproven. **Honest limit: the script has never run in this development environment** — no Docker, PostgreSQL, or `psql` exists here; every step was validated against SQLite and by inspection, and CI is the first place it executes as a whole. - BAK-001 "Backup, Restore & Disaster Recovery" (Phase B, P0 — **no business behaviour changed**): the platform can now *prove* it recovers. The centre of the work is a test that builds a real dairy (collection → pricing → settlement → payment → receipt → notifications), takes a backup, **deletes every row in every table**, restores, and asserts the money is identical to the cent, the receipt still renders under its original number, the platform still refuses a second payment on a fully-paid settlement (rules came back, not just rows), new business still succeeds, and every business invariant holds — including a deep projection rebuild from the event log. **A successful backup is not evidence; a successful restore is (BR-0025).** **Classification first:** every table is classified critical/important/rebuildable/ephemeral, derived from the mapped metadata rather than hand-maintained, with an unknown table defaulting to *critical*. Projections are excluded because BR-0015 guarantees they rebuild from the log; **consumer ledgers are deliberately included**, because restoring without them replays the entire event log and re-sends every notification and re-mints every receipt — a dedicated test proves consumers do not re-fire after a restore. **The engine** is dialect-portable (so it runs on SQLite and PostgreSQL alike) and writes a manifest with deterministic per-table checksums over primary-key-ordered rows; types are tagged rather than coerced, so a Decimal never becomes a float (BR-0005) and a UUID never becomes a string. Corruption and truncation are detected *before* a restore depends on them, a future format version is refused, and restoring over a non-empty database is refused unless explicitly forced. **Restore is CLI-only and always will be** — an endpoint that overwrites the database is one misrouted request from catastrophe — and it exits non-zero when the restored business is wrong, because that is a failed restore. **Integrity verification** checks the platform's own rules: settlement totals (BR-0011), payment allocations (BR-0018), one receipt per completed payment (BR-0020), orphaned rows, consumer cursors within the log (BR-0014), audit-trail presence, and projection rebuildability (BR-0015); tests prove each check can actually fail. **Operator surface:** a `backups` health component (so a schedule that silently stopped is visible beside everything else), read-only ops endpoints for status/history/classification/integrity, and a CLI with status, history, classification, backup, verify, integrity, and restore. **A live latent bug was found and fixed:** `migrations/env.py` had lost every model import to an earlier `ruff --fix` (they exist only for their registration side effect), so the next `alembic revision --autogenerate` produced a migration that would have **DROPPED EVERY TABLE** — including every payment, receipt, and settlement. Nothing had failed for three commits. Restored, exempted from the linter in `pyproject.toml`, and guarded by a new `test_migrations.py` that also asserts the migration chain stays linear. Physical PostgreSQL PITR (`pg_basebackup` + WAL) is scripted in `infra/backup/` with a five-gate automated restore test and a CI job, but **has not been executed** — no PostgreSQL was available; the logical path is the one demonstrated. New docs: [BACKUP](docs/03-architecture/06-operations/BACKUP.md), [RESTORE](docs/03-architecture/06-operations/RESTORE.md), [DISASTER_RECOVERY](docs/03-architecture/06-operations/DISASTER_RECOVERY.md) (named disasters, RPO 5 min / RTO 4 h with their assumptions stated), [RUNBOOK_BACKUP](docs/03-architecture/06-operations/RUNBOOK_BACKUP.md), [RECOVERY_CHECKLIST](docs/03-architecture/06-operations/RECOVERY_CHECKLIST.md). - OBS-001 "Platform Observability & Alerting" (Phase B, P0 — **no business behaviour changed, no query added to any business endpoint**): operators can now determine platform, consumer, projection, notification, payment, and security health **without reading application logs**. The layer is built around this platform's actual failure shape: it is event-driven, so collection can commit and then every downstream step — outbox, consumer, notification, receipt, projection — can stop *while the API keeps answering perfectly*. That is the dangerous state, so `background_workers` is a first-class health component, consumer lag is a headline metric, and every alert names the business consequence rather than the technical symptom. **Metrics:** all 50 metric families centralized in `core/metrics.py` — previously scattered across four modules, which is how a metrics surface becomes unreviewable — with a **cardinality rule enforced by a test** (labels are bounded vocabularies, never identities; a `tenant_id` label would multiply every series by the customer count, which at 1M dairies is existential). - SEC-001 "Production Security Hardening" (Phase B, P0 — **no business behaviour changed**): the platform's trust boundaries hardened for an enterprise security review. **JWT/RS256 with rotation:** tokens are signed RS256 from a key registry and carry the signing `kid`; verification resolves exactly that key — an unknown, retired, or expired kid is a rejection, never a fallback, and never an algorithm taken from the token's own header (both `alg: none` and HS256-signed-with-the-public-key are proven rejected by hand-assembled forgeries, since PyJWT refuses to build them). Rotation is **additive**: a new key signs while every unexpired predecessor keeps verifying, so no live session is invalidated; retirement kills every token a key signed, at once — the emergency lever. Public discovery at `/.well-known/jwks.json` (active keys only; a retired key is never advertised as trustworthy) and an operator view at `/v1/_security/keys` that cannot return private material. HS256 survives only as a documented rollback path, refused in prod without an explicit secret. **PostgreSQL Row Level Security (BR-0022):** every tenant-owned table gets a policy comparing `tenant_id` against a `SET LOCAL` session variable — transaction-scoped, so a pooled connection cannot carry one request's tenant into the next — with `WITH CHECK` as well as `USING` (without it a caller could move a row *into* another tenant, succeeding silently) and `FORCE` (without it the application, which connects as the table owner, bypasses its own policies). An unbound session matches nothing and fails **closed**; cross-tenant machinery uses an explicit, logged, transaction-scoped bypass rather than a superuser connection. Application filters stay as defense-in-depth. **The table list is derived from metadata, not hand-maintained** — the drift test immediately caught three projection tables that register at consumer discovery rather than at import. SQLite has no RLS, so policy *execution* is proven by a new PostgreSQL CI job whose **skip fails the build**. **Headers/CORS:** nosniff, DENY framing, no-referrer, deny-all Permissions-Policy, `default-src 'none'` CSP, and `no-store` (a shared proxy caching one tenant's data is a leak with extra steps); HSTS opt-in because a browser honours it *after* a rollback; CORS narrowed from wildcard methods/headers to explicit lists, never reflecting an origin. **Rate limiting:** Redis fixed-window, one round trip (INCR+EXPIRE pipelined), on login, refresh, password reset, invitation acceptance, notification preview, projection rebuild, and consumer replay; credential endpoints keyed per-IP **and** per-identifier because credential stuffing and distributed brute force are different attacks and a per-IP budget catches only one. 429 carries structured retry data and a `Retry-After` header. **Fail-open by default and deliberately** — a dairy must not stop accepting milk because a cache is down — with fail-closed one setting away. **Secrets:** nothing sensitive in source (a test greps for committed PEMs); production *refuses to start* on a dev default, a debug flag, or wildcard CORS. **Audit (BR-0023):** login success/failure, refresh, reuse detection, logout, password reset, permission denial, key rotation, and rate-limit violation land in the same immutable trail as business events and mirror to the log stream, so an attacker who reaches the database cannot erase what already left the host. - OFF-001 "Offline Collection Sync" — the last Phase A item, and the field prerequisite: the operator app now collects milk with **no connectivity at all** and reconciles when it returns, without forking a single business rule. **Offline is a transport problem, not a business one** (BR-0021; register v1.8): every operation captured on a device is applied, on sync, by calling the same `MilkCollectionService` method the online API calls, with the same principal, tenant context, and state machine — a step the engine refuses online is refused offline, an archived supplier is still archived, a closed session is still closed. The device is a **recorder, not a decider**: it never prices milk, never validates identity, never advances a state on its own authority, and reports platform-owned values as `pending_sync` rather than guessing; a 409 is an *answer* and is rethrown unchanged, so only transport failures fall back to the queue. **Flutter**: a new `offline/` layer — an `OfflineStore` port with an in-memory adapter and a file adapter that writes-then-renames (atomic, so a crash leaves the previous complete queue or the new one, never half a morning); a durable `SyncQueue` (PENDING/SYNCING/SYNCED/FAILED/CONFLICT, attempts, exponential backoff capped at 5 min mirroring the platform's own consumer schedule, local→server id map, last sync timestamp, conflict metadata) surviving app restart, device reboot, and crash — operations stranded in SYNCING by a process death are recovered on load because replay is idempotent; a `SyncEngine` with batch upload, automatic retry, progress, cancellation honoured *between* batches (work already in flight has its outcome applied first), and resume; and an `OfflineApiClient` that intercepts the collection calls so **the wizard is unchanged** — the operator's flow is answered from a projection folded over the queue. **Backend**: a new `sync` module whose service is explicitly a transport (`_dispatch()` routes each kind to the online service; if a business decision ever appears there, the design has failed), with client-generated `operation_id` as the idempotency key — a lost acknowledgement re-sends without doubling a collection — and `client_reference`/`target_ref` local ids resolved to server ids **across batches and persisted server-side**, which is what makes an interrupted sync resumable rather than restartable. - RCP-001 "Receipt Engine" — the artifact a farmer can hold. A new `receipt` module whose Receipt aggregate owns ReceiptLines (one per settlement the payment covered). - PAY-001 "Payment Execution Engine" — the money finally moves (as a record): a new `payment` module whose Payment aggregate owns PaymentLines (the allocation against each settlement) and PaymentAttempts (the execution history). **Payments consume settlements and never modify them** — only a FINALIZED settlement is payable, allocations belong to one supplier and one currency, and the settlement side stays untouched (BR-0018). **Outstanding balance is always computable**: payable − live allocations, where draft/pending/processing/completed all RESERVE (a draft is an intent that must stop a second payment claiming the same money) and failure/cancellation release — which is what makes partial payment, remaining balance, and duplicate prevention one rule instead of three. - PLT-001 "Projection Lifecycle & Replay Framework" — projections become first-class platform infrastructure ahead of Notifications/Offline/Analytics/AI read models.
