## [Unreleased]

### Added

- INF-001 "Infrastructure as Code & Production Environment" (**infrastructure only — no business logic, API or schema changed**): a production environment can now be provisioned from zero. **Terraform** for Hetzner Cloud (primary) and AWS (an optional abstraction, deliberately thin — two half-maintained infrastructure definitions are worse than one maintained one, and the second is always the one nobody has applied since March): one VM, one **static IP and one data volume that outlive the machine**, one firewall, SSH keys, provider snapshots. That IP-plus-volume pairing is the whole server-replacement story — build a new machine, re-attach both, deploy; DNS never changes, so no propagation wait and no certificate reissue. `prevent_destroy` on both, and `ignore_changes = [size]` on the volume because it can be grown online and never shrunk, so a smaller number in tfvars must not plan a destroy-and-recreate of the volume holding production data. **Terraform deliberately does not format the volume** — cloud-init does, and only when `blkid` finds no filesystem, because a `format` attribute lets an apply after a state mishap reformat a live database. **cloud-init** installs Docker (with `live-restore`, so a daemon upgrade does not take the platform down), builds the filesystem standard (`/opt/lacteva/releases` + `current` symlink, root-only `/etc/lacteva`, `/var/lib/lacteva` and `/backup` on the data volume), hardens SSH to keys-only with no root login, brings up ufw **and** fail2ban as a second layer inside the machine — the cloud firewall sits outside it and holds even mid-boot or after somebody flushes iptables while debugging — configures chrony (**not cosmetic**: the platform signs JWTs with a 30-second leeway, and a drifting clock rejects every valid token while looking exactly like a key problem), logrotate for host-written logs (a nightly backup log otherwise fills the volume the backups are written to), and enables security-only unattended upgrades with **automatic reboot off**, because rebooting a single-host platform without warning is an unplanned outage. **Firewall: 80, 443, and SSH from named ranges only** — both configurations *refuse `0.0.0.0/0` at plan time*, since key-only auth reduces the risk of exposing sshd to the internet without removing it. **systemd** starts the stack on boot with `RequiresMountsFor=/var/lib/lacteva` (starting before the volume is mounted creates an empty PGDATA on the root disk, silently) and a `TimeoutStopSec` that exceeds the API's 90-second stop grace, so systemd cannot kill the drain DEP-001 exists to make possible. **Backups on timers:** nightly logical (taken, then **verified**, and only then pruned — pruning first means a failing job deletes its way through the retention window and the day you need a restore there is nothing left), weekly physical, and a weekly **restore verification** that loads the newest backup into a throwaway database and runs deep business integrity including a projection rebuild, per BR-0025. All timers are `Persistent=true` so an overnight reboot does not silently skip a night. **`deploy.sh`** is one command: pull → pre-deployment backup → migrate → up → verify → smoke test, with **automatic rollback** on any failure past the migration, because the alternative is a half-deployed platform sitting broken until somebody notices. It never rolls the schema back automatically — a code rollback is safe after an expand-only migration and unsafe after a contract, and no script can tell from the outside — but it reports when the schema moved and points at the compatibility matrix. New [INFRASTRUCTURE.md](INFRASTRUCTURE.md): topology, provisioning, deployment, a scaling table naming what binds first (disk, then PostgreSQL I/O, then consumer CPU, then API concurrency), secret rotation procedures that all follow *add the new one, confirm, remove the old*, maintenance cadence, server replacement, disaster recovery, and a production readiness checklist. 25 new tests (870 total) asserting the properties whose absence is dangerous: SSH cannot be opened to the world, only three ports are reachable, the volume and IP cannot be destroyed, Terraform never formats, cloud-init never reformats a volume that has data, IMDSv2 is required (IMDSv1 turns any SSRF into instance credentials), AWS volumes are encrypted, systemd waits for the mount and allows the full drain, retention runs only after verification, and deploy never invokes `alembic downgrade`. **Nothing here has been applied** — no Terraform binary, cloud account, or host exists in the development environment; the configurations were validated structurally and by those tests. **The largest gap this work order records rather than closes: backups live on the same volume as the database**, so provider snapshots are the only independent copy, and shipping logical backups off-host is the single highest-value remaining piece of infrastructure.
- DEP-001 "Production Deployment Automation" (**no business behaviour, API, or schema changed**): the platform becomes deployable. A nine-container production stack (`docker-compose.production.yml`) with **one published port** — nginx — and everything else on `expose:` only, because reaching the database should be a decision someone makes rather than a port someone forgets. **Startup ordering is by health check and contains no sleep at all** (a test asserts it): postgres and redis must pass `pg_isready`/`PING`, then a one-shot `migrate` service runs `alembic upgrade head` and must **exit zero** before the API is allowed to start — `restart: "no"` is the load-bearing line, because a restart policy would turn a clear migration failure into a crash loop that looks like a slow start, and `service_completed_successfully` then never fires so nothing serves traffic against a schema that did not apply. **Two operational defects were fixed on the way.** (1) **Shutdown abandoned work.** The relay, consumer and health loops were `task.cancel()`ed, which throws wherever the loop happens to be — possibly between a consumer's write and the ledger row recording it. Safe (the transaction rolls back and the event retries) but not clean: every rolling deploy left work to redo. Shutdown is now cooperative — `workers.sleep()` wakes on a flag, each loop finishes the unit of work it is in and exits at its next sleep, stragglers are cancelled after a grace period, and the log reports `drained` versus `cancelled_after_grace` per worker because that difference predicts whether the next start has catching up to do. The engine is disposed last, after the loops, since disposing it while a consumer holds a session turns a clean shutdown into a stack trace. (2) **`/health/ready` was a `SELECT 1`.** A load balancer was told an instance was ready while its consumer loop was dead and nothing downstream was happening — this platform's most dangerous failure shape, because it looks healthy. Readiness now aggregates the same nine probes the ops endpoint and every Prometheus alert use, **degraded stays ready** (only `critical` removes an instance; taking a degraded instance out of rotation turns a partial problem into a total one), and it answers from the background sampler's most recent evaluation rather than running nine probes per poll, because a health check that is itself a load source is how a wobble becomes an outage. The response's `status` field keeps its original two-value vocabulary — DEP-001 is not allowed to move a contract — with the four-level detail added beside it. **Also new:** `.env.production.example` with every variable documented and a test that fails on an undocumented one; **Docker Secrets** support via pydantic-settings' `secrets_dir`, so a signing key need never appear in an environment block; production nginx (HTTPS, HSTS, gzip, websocket upgrade, 25 MB uploads, edge rate limiting, static caching, and `/metrics` restricted to private networks — publishing it would expose tenant counts and error rates); Loki + Promtail reading the container logs the platform already writes, so nothing ships from inside the API process; `infra/deploy/verify-deployment.sh` (readiness, every component, schema revision matches the image, **RLS coverage and FORCE** — a database restored from a pre-SEC-002 backup can serve traffic with the policies simply absent — Redis, outbox actually draining, nginx); and `infra/deploy/smoke-test.py`, which creates its own throwaway tenant, never deletes, and polls for the consumer-generated receipt rather than sleeping. [DEPLOYMENT.md](DEPLOYMENT.md) covers deploy, upgrade, rollback, backup, restore, disaster recovery, version upgrade and troubleshooting — including the **rollback compatibility matrix**: expand-only migrations roll back freely, contract migrations do not, and `alembic downgrade` on a live database drops columns holding data written since the upgrade, so it is a development tool and the honest options are roll forward or restore. 23 new tests (845 total). **Nothing here has been executed** — no Docker or production host exists in the development environment; the artefacts were validated by parsing, static analysis, dry-run against stubs, and tests that assert their contents.
- OPS-001 "PostgreSQL Continuous Verification" (**verification infrastructure only — no platform code changed**): the PostgreSQL-only guarantees get their own pipeline. Five work orders had accumulated proofs that SQLite structurally cannot evaluate — RLS enforcement and coverage, exact numeric aggregation, a scaled numeric column rounding on store, migrations applied to an empty database, and a restore verified rather than reported — and every one of them had already shipped a defect that only a real engine surfaced. They now run in **`.github/workflows/postgres.yml`**, a dedicated workflow that a clean checkout executes end to end. **A version matrix, not a version:** `postgres:16` (the production baseline documented in DBD-0001) and `postgres:17` (the newest release this repository has actually executed against), both required, `fail-fast: false` because learning that 16 passed while 17 failed is the entire point. PostgreSQL 18 is deliberately absent — nothing here has validated it, and an untested version in a required matrix is a red build waiting for someone else's morning. A single `PostgreSQL verified` job depends on the matrix so branch protection names one check and adding a version later cannot silently stop gating merges. **Continuous, not merely on-change:** the workflow also runs nightly at 03:17 UTC, because a dependency bump or a base-image change can break a guarantee without anyone touching the repository. **Skips became impossible rather than detected.** CI-001 grepped pytest's output for `N skipped` after the fact; a new `tests/postgres_support.py` now raises at *collection* when `LACTEVA_REQUIRE_POSTGRES=1` is set and no database URL is present — a collection error fails the run before any test executes, so it cannot be mistaken for a passing suite — and the proof script re-asserts zero skips, zero failures and non-zero collected from `pytest --junitxml`, structured output rather than prose, because pytest's summary line has changed format before and the XML attributes have not. Locally, with no URL, the suites still skip: a developer without PostgreSQL should not be blocked, and a pipeline whose whole purpose is PostgreSQL must not pass without it. Those are different situations and are now treated differently on purpose. **The proof script gained** a published summary (a nine-row table of what was proven with its evidence, written to `$GITHUB_STEP_SUMMARY` in CI and to stdout locally — one code path), real teardown (the throwaway databases are dropped on exit unless `KEEP_DATABASES=1`, because a failed run is far easier to diagnose with the database still standing), the server version echoed and reported, and a guard for the case where the test step produced no JUnit report at all. **`docker-compose.proof.yml`** takes `POSTGRES_VERSION` and `KEEP_DATABASES` so a laptop can reproduce any matrix leg exactly. **The SQLite pipeline is untouched** — `ci.yml` still gates every push with the fast, hermetic ~790-test suite, and the duplicated `postgres-proof` job was removed from it rather than left to drift; a comment names its replacement. Verified by dry-running the script against stubbed `psql`/`pg_isready`/`uv run`: steps 0–3 execute in order, the skip assertion fires (`3 PostgreSQL test(s) SKIPPED — a green skip is not a proof`), the missing-report guard fires, and the summary renders. New reference: [POSTGRES-PROOF](docs/03-architecture/06-operations/POSTGRES-PROOF.md) v1.1.
- DB-002 "Exact Numeric Aggregation" (**no API response changed; the reporting module was not redesigned**): the last correctness gap the Architecture Board reviews had left open. Money was already exact — `Decimal(str(x))` arithmetic, `NUMERIC` columns, an explicit rounding policy (BR-0005) — but **aggregation was not**. `net_weight`, `fat` and `snf` are `double precision`, and floating point addition is not associative, so `SUM(net_weight)` depended on the order the planner happened to produce; that order changes with statistics and with parallel workers, and the result was written into a `NUMERIC(16,3)` projection column, which made a non-reproducible number look exact. **Every aggregation in the platform was reviewed and classified**: 13 required conversion (all in `reporting/service.py` — the daily, per-center and per-supplier weight sums, the weighted fat/SNF numerators and denominators, and the two `ORDER BY SUM(...)` clauses), 1 was accepted as lossy-but-harmless (`AVG(event_delivery.latency_ms)`, an operational metric), and the rest were already safe (integer counts, and sums over `NUMERIC` — `gross_amount`, `settlement_line.gross_amount`, `payment_line.amount`, `AVG/MIN/MAX(unit_price)`). The fix is one helper: `_exact()` casts to unconstrained `NUMERIC` inside the aggregate, so the arithmetic stays in SQL and only its exactness changes — deliberately unconstrained, because pinning a scale would round every ROW where the platform rounds the TOTAL once. On PostgreSQL `float8::numeric` renders the shortest decimal that round-trips, the same rule `Decimal(str(x))` follows, so a weight aggregates as the value it displays as. **A second, unreported divergence was found while testing the first:** the reporting projection rounded its running total whenever a flush happened to occur — once per event for the incremental consumer, once per BATCH for the rebuild engine — so a rebuilt projection did not reproduce the incrementally built one, and two rebuilds at different batch sizes disagreed. Six weights of 0.0005 kg came to 0.006 incrementally and 0.003 in one batch: the same events, the same log, two different totals, and no error anywhere. **That was a hole in BR-0015**, whose whole promise is that a rebuilt projection is provably identical to an incrementally built one. The handler now quantizes to the column's own scale at every step, making the flush boundary irrelevant. Registers: BR-0005 extended to SQL aggregation, BR-0015 gains flush independence (register v1.14). 28 new tests: order independence over random insertion orders, rebuild-versus-incremental at batch sizes 1/2/5000 driven through the real projection engine, repeated-rebuild byte-identity (`Decimal.as_tuple()`, not just equality — a value comparing equal with a different exponent still serialises differently), decimal edge cases including classic half-way values, a 10 000-row exactness check, a structural guard that fails if a future report sums a float column directly, and a new PostgreSQL-only module proving the two premises SQLite cannot exhibit — that `SUM(float8)` is order-dependent while `SUM(float8::numeric)` is not, and that `numeric(16,3)` **rounds on store**, which is why the projection divergence was invisible in the main suite. Both are now wired into the CI proof job. **Still open and explicitly out of scope:** the column *types*. `pricing_matrix_row.unit_price`, `from_value`, `to_value` and the three weight columns remain `FLOAT`; this work order made the aggregation exact, not the storage.
- SEC-002 "Complete PostgreSQL RLS Coverage" (P0 — **no business behaviour or API changed**): the architecture principle *every table has an explicit isolation strategy* becomes something the build can check. Each of the 56 tables now declares exactly one of three: **tenant-owned** (carries `tenant_id`, standard policy — 50 tables, derived from the metadata rather than listed, because a hand-kept list is how a new module ships unprotected), **platform-global** (deliberately unprotected, **with the reason on record** — 5 tables), or **mixed** (both kinds of row, or isolated by a column other than `tenant_id` — 12 entries). `unclassified_tables()` returns nothing and a test asserts it, so "nobody decided" is a build failure. **Thirteen tenant-owned child tables gained `tenant_id` and a policy** (migration `f2d18ba60c47`): supplier profiles, bank accounts and documents, settlement lines, payment lines and attempts, receipt lines, price bands, center config/windows/calendar, device health reports, role permissions. They were reachable only through a parent, so SEC-001's "does it have a tenant_id column" rule skipped them and BR-0022's promise — *a query that forgets its filter returns NOTHING* — was simply false for them; `supplier_profile` (names, phones, national IDs) and `supplier_bank_account` (account numbers) were the worst of it. Denormalising is safe because no aggregate here is ever reparented. **`organization` gained an identity policy**: it has no `tenant_id` because it IS the tenant, so it was readable by any bound session and a tenant could enumerate the platform's customer list; it now compares its own primary key, with **no `IS NULL` escape** — creation and platform-admin reads take the audited bypass instead, because both are genuinely cross-tenant acts. **A worse defect was found while verifying the flows: authentication itself was broken under RLS.** `get_current_principal` read `auth_session` and `user_account` — both tenant-owned — and only *afterwards* re-bound to the token's tenant, so under RLS the session row was invisible to the request that owned it and every authenticated call without an `X-Tenant-ID` header would have failed as 401. The token is signed and self-contained, so its tenant claim is authoritative before any row is read; binding now happens there. Three more pre-tenant flows were repaired the same way: **tenant-scoped login** (the tenant is named in the request body, which the middleware never sees), **invitation acceptance** (anonymous, and `invitation` is tenant-owned — resolved by the narrowest possible bypass, one indexed read by token hash, then an immediate bind), and **organization creation** (nobody can be bound to an organization that does not exist yet). `rebind_tenant()` now moves the context variable and the database binding together — `set_current_tenant()` alone left the binding behind, which presents as "the row is invisible to the request that owns it" and was the second half of the same defect. `password_reset_token` is deliberately **not** protected and the reason is recorded: the flow that reads it is definitionally unauthenticated, and a policy there would make password reset impossible for every tenant-scoped user. 22 new tests — 14 PostgreSQL tests running against the **real migrated schema** rather than a synthetic probe table (coverage of enable+force+USING+WITH CHECK across every tenant table, cross-tenant read/insert/update/delete on `settlement_line` and `payment_line`, PII isolation on `supplier_profile`, organization identity isolation, and the bootstrap/registration/invitation/anonymous/role-catalog flows), plus 8 that run on SQLite including `test_authentication_binds_the_tenant_before_reading_any_row`, which records binds and reads on one timeline and was verified to fail against the pre-SEC-002 order. The CI proof script now asserts policy **coverage** rather than policy count — counting would have passed while the money and PII tables sat unprotected, which is exactly what happened. Docs: [RLS-GUIDE](docs/03-architecture/05-security/RLS-GUIDE.md) v1.2 (the A/B/C taxonomy and a table of every pre-tenant flow), BR-0022 extended (register v1.13), [DBD-0001](docs/07-data/DBD-0001-platform-core-database.md) v1.1 — which also **strikes findings F-4 and F-9 as measurement errors**: both were derived from `str(column.type)`, which renders through SQLAlchemy's default dialect, and all 97 timestamps are already `TIMESTAMPTZ` and all 176 ids already native `uuid` on PostgreSQL.
- DBR-001 "Database Inventory & Review Pack" (**documentation and architecture review only — no schema, migration, or line of code was changed**): [DBD-0001 Platform Core Database](docs/07-data/DBD-0001-platform-core-database.md) becomes the permanent **Database Architecture Reference**. Complete inventory of all **56 tables** grouped by module, each with purpose, every column (name, type, nullability), primary key, foreign keys, unique and check constraints, indexes, relationships, expected row growth, classification (transactional / reference / projection / audit / infrastructure), hot-warm-cold lifecycle, whether it should ever be partitioned, whether it holds tenant-owned data, and how it participates in the outbox. Four ERDs (money path, tenant and access, reference data, event framework), a module dependency graph derived from actual imports, a stated scale model, the **top 20 tables by expected production volume**, a partitioning assessment, and 13 numbered optimization findings. Every structural fact is transcribed programmatically from `Base.metadata` after `import_all_models()` — nothing was typed by hand, which is exactly the discipline CI-001 established for whole-schema operations. **The review found what the platform had not been forced to look at.** (F-1) **Nineteen of 56 tables carry no `tenant_id` and therefore no RLS policy**; fifteen of those have no foreign key either, so nothing at the database level ties them to a tenant — including `supplier_profile` (name, phone, national ID) and `supplier_bank_account` (account numbers). BR-0022's promise that a forgotten filter returns nothing holds for 37 tables, not 56. (F-2) **Four foreign keys and two check constraints exist in the entire schema**; cross-module absence is a defensible modular-monolith choice, intra-module absence is not, and `backup/integrity.py`'s orphan checks are the platform verifying after the fact what the database could have made impossible. (F-6) **The published unit price is a `FLOAT`** — `pricing_matrix_row.unit_price`, `from_value`, and `to_value` — so BR-0005's exact `Decimal` arithmetic begins from an inexact input, and half-open band boundaries are compared as floats. (F-3) **No retention, no archival, and no tenant-deletion path**: ~45 B rows and ~12 TB of heap per year at the modelled scale, nothing ever removed, and right-to-erasure not reliably executable. Plus: 97 naive `DATETIME` columns that should be `TIMESTAMPTZ` for a 50-country platform (F-4); 13 `JSON` columns that should be `JSONB` (F-5); 38 of 158 indexes redundant with a composite's leading column and 18 low-cardinality status indexes without a tenant prefix, with partial-index replacements proposed (F-7, F-8); 176 `CHAR(32)` id columns costing an estimated 15–20% of heap and index size against native `uuid` (F-9); no connection-pool configuration, `pool_pre_ping`, or statement timeout, and the PgBouncer transaction-mode constraint that RLS's `SET LOCAL` imposes (F-10); nullable columns inside unique constraints, where `uq_role_tenant_name` and `uq_user_tenant_email` do **not** enforce platform-global uniqueness (F-11). Findings are ordered by consequence and sequenced so no table is rewritten twice. **Nothing was implemented** — the work order was review only, and every number derives from a stated scale model because the platform has no production deployment and therefore no measured data.
- CI-001 "PostgreSQL Proof" (Phase B, P0 — **infrastructure and verification only; no business behaviour or API changed**): every PostgreSQL-dependent guarantee moves from *documented* to *proven*. Three work orders in a row had ended with a P0 guarantee that was written, tested, and CI-wired but **never actually executed**, because the test stack is SQLite and the guarantee is PostgreSQL-specific. One script — `infra/ci/postgres-proof.sh`, run identically by GitHub Actions and by `docker compose -f docker-compose.proof.yml run --rm proof`, because two pipelines agree until the day it matters — now performs nine steps against a real engine, any of which fails the build: **migrations applied to an EMPTY database** (not incrementally); **RLS enabled AND forced** on every tenant table (`relrowsecurity` alone lets the owner bypass its own policy); the **RLS suite passing and provably not skipped** (a silently skipped security proof is worse than none, because it is green); **a real dairy seeded through the platform's own API** (an empty database restores perfectly and proves nothing); a **logical backup taken and checksum-verified**; a **second, fresh database migrated**; the backup **restored into it**; **deep business integrity** on the restored data (settlements balance, allocations reconcile, receipts are one-per-payment, projections rebuild from the log); and a **fact-by-fact comparison** of source against restored. **Running it for the first time found three defects that every existing test had passed over.** (1) The RLS predicate hid every platform-global row: SQL three-valued logic makes `NULL = 'x'` neither true nor false, so rows with `tenant_id IS NULL` — user accounts before they join an organization, the role catalog, the outbox log — were invisible and un-insertable, meaning **registration itself would have failed on the first production deploy with RLS enabled**; fixed by migration `c94b1ea27f31` adding an explicit `OR tenant_id IS NULL` to both `USING` and `WITH CHECK`, and BR-0022 amended to say so. (2) A CLI backup captured **one table and three rows** while reporting success. (3) Restore crashed ordering a table absent from its own metadata. The last two shared one root cause, and it is a whole bug class: **`Base.metadata` completeness is a property of import order, not of the code**, so every whole-schema operation reads a partial truth by default and reports success on it — the same class that left `migrations/env.py` one autogenerate away from dropping every table in BAK-001. Closed by `core/model_registry.py`, whose `import_all_models()` is a **function call** rather than an import block precisely because a bare import is indistinguishable from dead code and has already been deleted once by an automated lint fix; migrations, the backup engine, and classification all call it, the per-file lint exemption it replaces is gone, and **BR-0026** (register v1.12) states the rule with guard tests behind it. Also new: `infra/ci/seed_proof_data.py`, which drives the platform in-process over ASGI and deliberately avoids the app lifespan — its background loops interleave with the seeding requests, and on SQLite's `StaticPool` that shares a single connection and **silently loses writes**. The old `row-level-security` CI job is replaced by `postgres-proof`. New doc: [POSTGRES-PROOF](docs/03-architecture/06-operations/POSTGRES-PROOF.md), including how to read each failure and what is still unproven. **Honest limit: the script has never run in this development environment** — no Docker, PostgreSQL, or `psql` exists here; every step was validated against SQLite and by inspection, and CI is the first place it executes as a whole. Physical PITR remains scripted but unproven. 769 tests collected (758 local + 11 PostgreSQL-only).
- BAK-001 "Backup, Restore & Disaster Recovery" (Phase B, P0 — **no business behaviour changed**): the platform can now *prove* it recovers. The centre of the work is a test that builds a real dairy (collection → pricing → settlement → payment → receipt → notifications), takes a backup, **deletes every row in every table**, restores, and asserts the money is identical to the cent, the receipt still renders under its original number, the platform still refuses a second payment on a fully-paid settlement (rules came back, not just rows), new business still succeeds, and every business invariant holds — including a deep projection rebuild from the event log. **A successful backup is not evidence; a successful restore is (BR-0025).** **Classification first:** every table is classified critical/important/rebuildable/ephemeral, derived from the mapped metadata rather than hand-maintained, with an unknown table defaulting to *critical*. Projections are excluded because BR-0015 guarantees they rebuild from the log; **consumer ledgers are deliberately included**, because restoring without them replays the entire event log and re-sends every notification and re-mints every receipt — a dedicated test proves consumers do not re-fire after a restore. **The engine** is dialect-portable (so it runs on SQLite and PostgreSQL alike) and writes a manifest with deterministic per-table checksums over primary-key-ordered rows; types are tagged rather than coerced, so a Decimal never becomes a float (BR-0005) and a UUID never becomes a string. Corruption and truncation are detected *before* a restore depends on them, a future format version is refused, and restoring over a non-empty database is refused unless explicitly forced. **Restore is CLI-only and always will be** — an endpoint that overwrites the database is one misrouted request from catastrophe — and it exits non-zero when the restored business is wrong, because that is a failed restore. **Integrity verification** checks the platform's own rules: settlement totals (BR-0011), payment allocations (BR-0018), one receipt per completed payment (BR-0020), orphaned rows, consumer cursors within the log (BR-0014), audit-trail presence, and projection rebuildability (BR-0015); tests prove each check can actually fail. **Operator surface:** a `backups` health component (so a schedule that silently stopped is visible beside everything else), read-only ops endpoints for status/history/classification/integrity, and a CLI with status, history, classification, backup, verify, integrity, and restore. **A live latent bug was found and fixed:** `migrations/env.py` had lost every model import to an earlier `ruff --fix` (they exist only for their registration side effect), so the next `alembic revision --autogenerate` produced a migration that would have **DROPPED EVERY TABLE** — including every payment, receipt, and settlement. Nothing had failed for three commits. Restored, exempted from the linter in `pyproject.toml`, and guarded by a new `test_migrations.py` that also asserts the migration chain stays linear. Physical PostgreSQL PITR (`pg_basebackup` + WAL) is scripted in `infra/backup/` with a five-gate automated restore test and a CI job, but **has not been executed** — no PostgreSQL was available; the logical path is the one demonstrated. New docs: [BACKUP](docs/03-architecture/06-operations/BACKUP.md), [RESTORE](docs/03-architecture/06-operations/RESTORE.md), [DISASTER_RECOVERY](docs/03-architecture/06-operations/DISASTER_RECOVERY.md) (named disasters, RPO 5 min / RTO 4 h with their assumptions stated), [RUNBOOK_BACKUP](docs/03-architecture/06-operations/RUNBOOK_BACKUP.md), [RECOVERY_CHECKLIST](docs/03-architecture/06-operations/RECOVERY_CHECKLIST.md). Migration `6560a9a90ab9`; 38 new tests (765 collected).
- OBS-001 "Platform Observability & Alerting" (Phase B, P0 — **no business behaviour changed, no query added to any business endpoint**): operators can now determine platform, consumer, projection, notification, payment, and security health **without reading application logs**. The layer is built around this platform's actual failure shape: it is event-driven, so collection can commit and then every downstream step — outbox, consumer, notification, receipt, projection — can stop *while the API keeps answering perfectly*. That is the dangerous state, so `background_workers` is a first-class health component, consumer lag is a headline metric, and every alert names the business consequence rather than the technical symptom. **Metrics:** all 50 metric families centralized in `core/metrics.py` — previously scattered across four modules, which is how a metrics surface becomes unreviewable — with a **cardinality rule enforced by a test** (labels are bounded vocabularies, never identities; a `tenant_id` label would multiply every series by the customer count, which at 1M dairies is existential). New coverage for payments, receipts, offline sync, pricing, settlements, auth/authz failures, rate limiting, JWT verification, projection lag/drift, notification provider latency, and per-component health. **Bug found and fixed:** HTTP metrics labelled the router-relative path, silently dropping the `/v1` prefix — a future v2 API would have collided into the same series; labels are now the templated full path, so an id can never leak in. **Correlation (BR-0024):** one id flows request → outbox event → consumer → notification/receipt, with the consumer now *rebinding* it into its log context — the link that was missing, exactly where a chain crossing a process boundary needs it most. **Health:** a four-level model (healthy/warning/degraded/critical) across eight components, overall status = **worst** component (averaging hides outages), a failing probe becomes `critical` rather than a 500, and **degraded stays ready** because pulling a degraded instance removes capacity that still works without fixing anything. **Alerts:** 12 rules declared once and driving both the operator API and the generated Prometheus rules, so pager and dashboard cannot disagree; every rule carries an **action** — a test enforces it, because a rule without one is a notification and notifications train operators to ignore alerts. Thresholds document the judgement behind each number. **Operator API:** `/v1/_ops/overview` (the first screen), `/health`, `/alerts`, `/alert-rules`, plus consumer **pause/resume** through the same config kill switch the runner already reads — one switch, not two that can disagree. **Tracing:** OpenTelemetry supported but not required — spans are no-ops unless the SDK is installed *and* an exporter configured, and configured-but-uninstalled warns loudly rather than implying instrumentation that is not happening; correlation works with or without it. **Artifacts:** 7 generated Grafana dashboards, Prometheus scrape config, and alert rules generated from the platform's own definitions. - SEC-001 "Production Security Hardening" (Phase B, P0 — **no business behaviour changed**): the platform's trust boundaries hardened for an enterprise security review. **JWT/RS256 with rotation:** tokens are signed RS256 from a key registry and carry the signing `kid`; verification resolves exactly that key — an unknown, retired, or expired kid is a rejection, never a fallback, and never an algorithm taken from the token's own header (both `alg: none` and HS256-signed-with-the-public-key are proven rejected by hand-assembled forgeries, since PyJWT refuses to build them). Rotation is **additive**: a new key signs while every unexpired predecessor keeps verifying, so no live session is invalidated; retirement kills every token a key signed, at once — the emergency lever. Public discovery at `/.well-known/jwks.json` (active keys only; a retired key is never advertised as trustworthy) and an operator view at `/v1/_security/keys` that cannot return private material. HS256 survives only as a documented rollback path, refused in prod without an explicit secret. **PostgreSQL Row Level Security (BR-0022):** every tenant-owned table gets a policy comparing `tenant_id` against a `SET LOCAL` session variable — transaction-scoped, so a pooled connection cannot carry one request's tenant into the next — with `WITH CHECK` as well as `USING` (without it a caller could move a row *into* another tenant, succeeding silently) and `FORCE` (without it the application, which connects as the table owner, bypasses its own policies). An unbound session matches nothing and fails **closed**; cross-tenant machinery uses an explicit, logged, transaction-scoped bypass rather than a superuser connection. Application filters stay as defense-in-depth. **The table list is derived from metadata, not hand-maintained** — the drift test immediately caught three projection tables that register at consumer discovery rather than at import. SQLite has no RLS, so policy *execution* is proven by a new PostgreSQL CI job whose **skip fails the build**. **Headers/CORS:** nosniff, DENY framing, no-referrer, deny-all Permissions-Policy, `default-src 'none'` CSP, and `no-store` (a shared proxy caching one tenant's data is a leak with extra steps); HSTS opt-in because a browser honours it *after* a rollback; CORS narrowed from wildcard methods/headers to explicit lists, never reflecting an origin. **Rate limiting:** Redis fixed-window, one round trip (INCR+EXPIRE pipelined), on login, refresh, password reset, invitation acceptance, notification preview, projection rebuild, and consumer replay; credential endpoints keyed per-IP **and** per-identifier because credential stuffing and distributed brute force are different attacks and a per-IP budget catches only one. 429 carries structured retry data and a `Retry-After` header. **Fail-open by default and deliberately** — a dairy must not stop accepting milk because a cache is down — with fail-closed one setting away. **Secrets:** nothing sensitive in source (a test greps for committed PEMs); production *refuses to start* on a dev default, a debug flag, or wildcard CORS. **Audit (BR-0023):** login success/failure, refresh, reuse detection, logout, password reset, permission denial, key rotation, and rate-limit violation land in the same immutable trail as business events and mirror to the log stream, so an attacker who reaches the database cannot erase what already left the host. New security documentation layer `docs/03-architecture/05-security/`: [SECURITY](docs/03-architecture/05-security/SECURITY.md), [THREAT-MODEL](docs/03-architecture/05-security/THREAT-MODEL.md) (12 threats, each with residual risk and its proving test), [JWT-ROTATION](docs/03-architecture/05-security/JWT-ROTATION.md), [RLS-GUIDE](docs/03-architecture/05-security/RLS-GUIDE.md), [SECURITY-CHECKLIST](docs/03-architecture/05-security/SECURITY-CHECKLIST.md) (pre-production gate, monitoring signals, incident response). - OFF-001 "Offline Collection Sync" — the last Phase A item, and the field prerequisite: the operator app now collects milk with **no connectivity at all** and reconciles when it returns, without forking a single business rule. **Offline is a transport problem, not a business one** (BR-0021; register v1.8): every operation captured on a device is applied, on sync, by calling the same `MilkCollectionService` method the online API calls, with the same principal, tenant context, and state machine — a step the engine refuses online is refused offline, an archived supplier is still archived, a closed session is still closed. The device is a **recorder, not a decider**: it never prices milk, never validates identity, never advances a state on its own authority, and reports platform-owned values as `pending_sync` rather than guessing; a 409 is an *answer* and is rethrown unchanged, so only transport failures fall back to the queue. **Flutter**: a new `offline/` layer — an `OfflineStore` port with an in-memory adapter and a file adapter that writes-then-renames (atomic, so a crash leaves the previous complete queue or the new one, never half a morning); a durable `SyncQueue` (PENDING/SYNCING/SYNCED/FAILED/CONFLICT, attempts, exponential backoff capped at 5 min mirroring the platform's own consumer schedule, local→server id map, last sync timestamp, conflict metadata) surviving app restart, device reboot, and crash — operations stranded in SYNCING by a process death are recovered on load because replay is idempotent; a `SyncEngine` with batch upload, automatic retry, progress, cancellation honoured *between* batches (work already in flight has its outcome applied first), and resume; and an `OfflineApiClient` that intercepts the collection calls so **the wizard is unchanged** — the operator's flow is answered from a projection folded over the queue. **Backend**: a new `sync` module whose service is explicitly a transport (`_dispatch()` routes each kind to the online service; if a business decision ever appears there, the design has failed), with client-generated `operation_id` as the idempotency key — a lost acknowledgement re-sends without doubling a collection — and `client_reference`/`target_ref` local ids resolved to server ids **across batches and persisted server-side**, which is what makes an interrupted sync resumable rather than restartable. Conflicts are structured and never silently overwritten: `already_accepted`, `supplier_unavailable`, `session_closed`, `unresolved_reference`, `invalid_state`, and `rate_card_changed` — the last of which **applies anyway**, because milk is perishable and MVP-001 forbids blocking a collection on pricing, so the collection stands and the divergence is flagged. - RCP-001 "Receipt Engine" — the artifact a farmer can hold. A new `receipt` module whose Receipt aggregate owns ReceiptLines (one per settlement the payment covered). Receipts are **generated only by consuming `payment.completed.v1`** off the durable log — never requested by a business module, never issued for a draft, failed, or cancelled payment — and one completed payment produces exactly one receipt, enforced by a unique `(tenant, payment)` constraint so consumer replay re-finds the artifact instead of handing a farmer a second one (BR-0020; register v1.7). Because the content is frozen, the receipt **copies** what it shows (supplier name and code, payment reference and method, settlement numbers, centers, periods, amounts) at generation time: re-deriving later could show a different world, and a receipt must show the world as it was when the money moved — proven by a test that renames the supplier afterwards and asserts the receipt is unchanged. Lifecycle generated → delivered → archived is the ONLY permitted mutation (CAS-guarded); archived receipts stay fully queryable, listable, and renderable, and the module has no update or delete path at all — a test asserts DELETE/PUT/PATCH are 405. **Rendering** is a pure derivation of the immutable record, so nothing is stored and any format re-derives identically forever: a `ReceiptRenderer` Protocol with a registry mirroring the NOT-001 provider abstraction ships `json` (canonical), `html` (self-contained — no external stylesheet, font, image, or script, because a village printer has no connectivity), and a **PDF placeholder** that announces itself as one (`placeholder: true` surfaces as a badge in the portal and a card in the app) so a download never quietly pretends to be a real PDF; **no PDF engine or external service is integrated**, and a deployment swaps one in with a single `register_renderer` call. - PAY-001 "Payment Execution Engine" — the money finally moves (as a record): a new `payment` module whose Payment aggregate owns PaymentLines (the allocation against each settlement) and PaymentAttempts (the execution history). **Payments consume settlements and never modify them** — only a FINALIZED settlement is payable, allocations belong to one supplier and one currency, and the settlement side stays untouched (BR-0018). **Outstanding balance is always computable**: payable − live allocations, where draft/pending/processing/completed all RESERVE (a draft is an intent that must stop a second payment claiming the same money) and failure/cancellation release — which is what makes partial payment, remaining balance, and duplicate prevention one rule instead of three. The balance list joins allocation sums in SQL and filters/paginates in the database, so a growing payables ledger is never fetched whole. **Lifecycle** draft → pending → processing → completed (immutable) with failed (retryable) and cancelled (terminal); every transition CAS-guarded; cancelling a *processing* payment is deliberately refused because money may be in flight and the truthful sequence is fail-then-cancel; every execution opens a NEW attempt row (number, provider, reference, operator, timestamps, failure reason) so a payment's failure history survives its success (BR-0019; register v1.6). **Idempotent execution** via a client-supplied `idempotency_key` unique per tenant: re-posting returns the existing payment instead of paying twice. - PLT-001 "Projection Lifecycle & Replay Framework" — projections become first-class platform infrastructure ahead of Notifications/Offline/Analytics/AI read models.
