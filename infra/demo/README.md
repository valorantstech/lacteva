# Demo Dataset

A deterministic, repeatable dairy for customer demonstrations. Everything it
creates is produced by driving the platform's own API, so every amount on every
screen was calculated by the pricing engine and the settlement rules — not by
the seeder.

## Commands

All four run against whatever `LACTEVA_DATABASE_URL` points at.

```bash
python infra/demo/seed_demo.py seed       # build the dataset
python infra/demo/seed_demo.py verify     # assert it is present and consistent (exit 1 if not)
python infra/demo/seed_demo.py purge      # remove it — demo organizations only
python infra/demo/seed_demo.py reset      # purge, then seed
python infra/demo/seed_demo.py consumers  # relay + drain: mint receipts and notifications
```

### Locally

```bash
cd services/platform-core && .venv/bin/alembic upgrade head   # schema first
cd ../.. && LACTEVA_DATABASE_URL=sqlite+aiosqlite:///./demo.db \
  services/platform-core/.venv/bin/python infra/demo/seed_demo.py seed
```

### On the deployed host

The seeder runs inside the API container, which already has the application,
its dependencies and the database URL:

```bash
ssh lacteva-dev
cd /opt/lacteva/releases/<release>
sudo docker compose -f docker-compose.production.yml --env-file /etc/lacteva/.env.production \
  exec -T api python /app/infra/demo/seed_demo.py seed
```

`seed` takes several minutes: it walks roughly 350 collections through the full
state machine, one HTTP call per step, because that is what makes the numbers
real.

## What it creates

| | |
| --- | --- |
| Organizations | **Lacteva Demo Cooperative** (`lacteva-demo`) and **Lacteva Isolation Demo** (`lacteva-isolation-demo`) |
| Users | a `tenant-admin` and a `tenant-viewer` in the main organization, a `tenant-admin` in the second |
| Centres | 5 ready centres (hours, active, an operator, a live scale) plus 1 in the second organization |
| Suppliers | 24 active suppliers, assigned to centres, plus 3 in the second organization |
| Rate cards | a superseded 2025 card, the published 2026 card in force, and a 2027 draft awaiting approval |
| Matrices | a FAT band matrix per card — three bands, so the demo shows three different rates |
| Collections | ~350 completed over 22 days, plus one rejected, plus an open session for today |
| Settlements | two finalized periods per supplier, one paid and one awaiting payment |
| Payments | completed, processing and failed — the states an operator actually has to handle |
| Receipts | one per completed payment, generated by the consumer |

## Rules this dataset obeys

- **Nothing is calculated here.** Rates come from the published rate card via
  the resolution engine; amounts from `pricing/calculator.py`; settlement totals
  from `calculate_totals()`; balances from the payment service.
- **BR-0027 is demonstrated, not described.** A collection is recorded into a
  period *after* that period was finalized, is therefore stranded, and is
  carried forward into a later open settlement — the real scenario PILOT-001
  found and PILOT-F03 fixed.
- **BR-0011 holds**: adjustments are zero and `verify` asserts
  `net == gross + adjustments` on every settlement it finds.
- **No settlement is finalized empty**, because the platform refuses to and the
  seeder does not ask twice.
- **Suppliers are assigned to a centre before activation**, because the platform
  refuses to activate a supplier with nowhere to deliver.

## The one direct write

A collection's business date is its creation date (`tx_date =
as_utc(tx.created_at).date()`) and the platform has **no back-dating API** —
deliberately, because an operator must not be able to move milk through time.
A demo with only today's data has nothing to settle, so the seeder stamps
`created_at` on the transaction row immediately after creation and **before**
pricing. The domain then prices, settles and pays it as a genuine collection on
that day.

That timestamp is the only value written directly to a business table, and it is
written before any money exists. If a future release adds a supervised
back-dated entry endpoint, this should use it instead.

## Safety

`purge` deletes rows whose `tenant_id` is one of the two demo organizations, and
the table list comes from `core/rls.py`'s own declaration of what is
tenant-owned — so a table added later is covered without editing the seeder.
Data in any other organization, including pilot data, cannot be caught by it.

`verify` exits non-zero and names the problem, so it can be used as a gate
before a demonstration:

```bash
python infra/demo/seed_demo.py verify || echo "demo data is not ready"
```
