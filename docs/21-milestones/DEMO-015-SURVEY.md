# DEMO-015 — The survey

DEMO-015 asks for the dairy's primary workflow:

```
CUSTOMER → MILK DELIVERY → DAILY DELIVERY REPORT → MONTHLY BILL → PAYMENT → RECEIPT
```

**Almost all of it already existed.** DEMO-009 built the receivable side —
customers, delivery plans, deliveries, invoices, customer payments,
allocations, receipts — with the same guarantees as the procurement side and
the opposite direction of money. DEMO-010 added receivables reporting and the
dashboard. DEMO-012 put the round on a phone. DEMO-013 and DEMO-014 made every
figure speak the organization's currency, clock and language.

So the first thing this milestone did was **not write code**. It executed the
chain end to end on real PostgreSQL, because this repository's history says
that is where the defects are: four work orders that did nothing but run
already-reviewed guarantees found fourteen.

## 1. What was executed first

`infra/ci/sales-chain-proof.sh` — a new entry point, run before any change:

| Step | Asserted |
|---|---|
| 0 | an Indian dairy onboarded from a country code alone: INR, Asia/Kolkata |
| 1 | four customers, each on an agreed plan, each billing in the org's currency |
| 2 | 124 deliveries across 31 days, quantities varying per customer per day |
| 3 | the client's own `amount`/`unit_price`/`currency` ignored; the domain priced it |
| 4 | the month's report totals equal the sum of its deliveries, to the paisa |
| 5 | a bill equals exactly its 31 deliveries; its lines add to its total |
| 6 | a second bill for the same period, and an overlapping one, both refused |
| 7 | a part payment moves the balance by exactly the amount paid |
| 8 | one payment produced exactly one receipt, generated by a consumer |
| 9 | paying the rest closes the bill and clears the balance |
| 10 | a cancelled draft releases its milk, which can then be billed again |
| 11 | another dairy gets 404 for every one of it — never 403 |

**Result: the chain holds.** ₹118,916.50 over 2,469.750 L, `INV-2026-000001` →
`CPY-2026-000001` → `CRC-2026-000001`, zero failures. Nothing in §4–§12 of the
work order needed rebuilding.

## 2. Existing architecture

**One deployable, many modules.** Each folder under
`src/platform_core/modules/` is a bounded context. The receivable side is five
of them, and they reference each other by UUID only:

| Module | Owns | Key tables |
|---|---|---|
| `customer` | who is bought from us, and at what agreed rate | `customer`, `delivery_plan` |
| `delivery` | milk leaving for a customer | `milk_delivery` |
| `billing` | what is owed, what was paid, and the proof | `customer_invoice`, `customer_invoice_line`, `customer_payment`, `customer_payment_allocation`, `customer_receipt` |
| `reporting` | read-only summaries across contexts | none — it owns no data |
| `authz` | the permissions every route above is guarded by | `role`, `user_role` |

`reporting` is the **one sanctioned exception** to the module-boundary rule: it
may SELECT across contexts because it owns nothing, writes nothing, emits
nothing and duplicates no business logic.

**Existing entities.** A `Customer` carries code, name, type, phone, address,
status, billing mode, billing day and currency — with **no currency default**,
deliberately, since DEMO-013 found that a defaulted `"KES"` minted Kenyan
shillings in an Indian dairy and said nothing. A `DeliveryPlan` carries the
agreed product, standing quantity, unit and rate; changing a rate supersedes
the plan rather than editing it, so a delivery priced last week can still be
explained. A `MilkDelivery` is unique per `(tenant, customer, date, slot)` — a
second morning delivery is a correction, not another sale, and would double
the bill. A `CustomerInvoice` is unique per live period, enforced by a
**partial** index excluding cancelled rows, so a cancelled draft cannot block
its own period forever.

**Existing APIs**, all present before this milestone:

```
POST/GET/PUT /v1/customers … /{id} /{id}/status /{id}/plan
POST/GET      /v1/deliveries        GET /v1/deliveries/report
POST          /v1/deliveries/{id}/amend
POST/GET      /v1/invoices          POST /v1/invoices/{id}/issue | /cancel
POST/GET      /v1/customer-payments GET /v1/customers/{id}/balance
GET           /v1/customer-receipts
GET           /v1/reports/sales/summary  /v1/reports/receivables  /v1/reports/dashboard
```

**Existing UI routes:** `/customers`, `/customers/[id]`, `/deliveries`,
`/billing`, `/invoices/[id]`, `/receivables`, `/receipts`, `/reports`, `/`.

**Existing mobile:** one Flutter application with three experiences chosen by
permission — collection operator, delivery rider, customer — sharing one
authentication, one offline queue and one API client.

## 3. What DEMO-015 adds

Four things, each because a question a dairy owner asks could not be answered:

**"To whom?"** `/v1/deliveries/report` grouped by day only. It now carries
`by_customer` rows — code, name, product, count, volume, rate, value, skips —
ordered by value in SQL. The rate is `null` rather than averaged when a
customer's deliveries disagree about it. Customers are named through a new
`CustomerService.directory()` batch lookup rather than a join, because the
delivery module references a customer by UUID; two queries, not one per row.

**"Can I have that as a file?"** `/v1/deliveries/report.csv`. Its totals row is
the platform's own aggregate, not a sum of the lines above it, so the file
cannot disagree with the screen. Amounts carry no symbol and no grouping,
because a spreadsheet reads `1234.50` as a number and `₹1,234.50` as text.

**"How did this customer come to owe me this?"** `balance()` answers only
*what is owed now*. The new statement shows the movement from an opening
balance and holds to `opening + billed − paid = closing`; when the window ends
today, `closing == balance().outstanding`, so a customer's page and the
receivables report can never tell two stories about one debt.

**"Does it work in Hindi?"** Not on the phone. DEMO-014 wrote
`record.delivered`, `record.quantityHint` and the rest into all three catalogs
and the record-delivery screen used none of them — every string on the screen
an operator touches six hundred times a day was an English literal.

Plus one defect the portal carried: **"Today" was UTC's today.** Defensible for
Kenya (UTC+3); wrong for India (UTC+5:30), where before 05:30 IST the delivery
report and the delivery form's default date were both a day behind.

## 4. What is intentionally outside this milestone

| Not built | Why |
|---|---|
| A general ledger — accounts, journals, ageing buckets | §13 asks for a statement, not an ERP. The identity it holds to is stated above and tested; anything more is DEMO-009-FINAL §14's remaining work |
| PDF export of the delivery report | §15 asks for CSV *or* PDF "if the existing infrastructure supports it cleanly". Receipt PDF rendering exists but is receipt-shaped; a report renderer is a project, not a corner |
| The invoice NUMBER in the CSV | It belongs to the billing module, and a delivery references it by UUID. `billed` yes/no answers the question the file is downloaded to ask |
| Multi-month seeded history | The showcase customer gets two bills over two halves of the window, which demonstrates a real opening balance without doubling a seed that already takes fifteen minutes |
| Adjustments on an invoice | Fixed at zero by the same rule (BR-0011) that fixes settlement adjustments at zero. The arithmetic carries the term so the day it becomes real nothing moves |
| Everything in work-order §24 | AI, IoT, GST/e-invoicing, gateways, routing, WhatsApp — named as future milestones |

## 5. Where the numbers come from

Nothing on a screen or in a file is computed by a client. The rule, stated
once and enforced in four places:

* the **rate** is the customer's plan's, resolved server-side; `RecordDeliveryCommand` has no price field, so a client cannot send one;
* the **amount** is `quantity × unit_price`, computed once in `Decimal` in `DeliveryService.record` and stored;
* every **total** is a SQL aggregate over the whole filtered set, never over a page;
* the **statement's** running balance arrives from the server and the portal prints it.

`core/money.py` decides how many decimal places a currency has, in one place,
so a zero-decimal currency is a lookup rather than a defect.
