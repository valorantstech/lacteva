# DEMO-015 — Dairy Daily Operations, Delivery Reports & Monthly Billing

The milestone began by **not writing code**.

DEMO-009 had already built the whole receivable chain, so the first act was to
execute it end to end on real PostgreSQL — because this repository's history
says that is where the defects are. The chain held. What did not exist were
the answers to four ordinary questions a dairy owner asks, and one of those
questions found a defect that would have mis-dated an Indian dairy's morning
round.

**Five defects found. Four of them only by running things** — on a real
engine, in a real browser, against the live deployment. **AWS cost: none.**

## 2. Database changes

**None.** `alembic --autogenerate` produces an empty migration, so DEMO-015
deployed without a database operation.

The one migration that reached production in this deployment is DEMO-014's
`c5e83b19d740`, which was written and verified earlier and had never shipped:
`collection_center.timezone` becomes nullable, and every row holding the
literal `'UTC'` — the default's fingerprint — is cleared to mean *inherit*.
**Ten production centres were reclassified**, which is the entire point: all
ten were the default, none was a deliberate choice, and a Kenyan centre
claiming UTC is claiming a clock three hours from the one its milk is
collected on. Verified up → down → up on real PostgreSQL before deploying.
`user_account.timezone` is added, nullable, display-only.

## 3. APIs added or changed

| Endpoint | Change |
|---|---|
| `GET /v1/deliveries/report` | **Changed, additively.** Gains `currency`, `quantity_unit` and `by_customer[]` (code, name, product, deliveries, quantity, unit_price, amount, skipped) |
| `GET /v1/deliveries/report.csv` | **New.** `text/csv` with `Content-Disposition`; same filters as the report |
| `GET /v1/customers/{id}/statement` | **New.** Opening balance, entries, closing balance; optional `date_from`/`date_to` defaulting to the dairy's own month |

`unit_price` on a per-customer row is **null rather than averaged** when that
customer's deliveries in the window disagree about the rate. One blended
number would hide a mid-month rate change while looking authoritative.

## 4. Portal changes

* the delivery report gains the per-customer table and a plain download link —
  the proxy streams the file, so nothing about the report is assembled in
  JavaScript;
* the customer page gains the statement: four figures and a running balance,
  printed from the response and never recomputed;
* **`resolveRange` and the delivery form now resolve "today" in the
  organization's zone** (see §16);
* 30 new message keys across English, Hindi and Arabic.

Both new cards read `report.by_customer?.length` rather than `.length`: during
a rolling deploy the portal can be newer than the API for a few seconds, and a
screen that throws on a missing field turns version skew into a blank page.

## 5. Mobile changes

The record-delivery screen — the one an operator touches six hundred times a
day — now speaks the catalog it already shipped with (§16, defect 3). No
behavioural change; the offline queue, the API client and the round screen are
untouched.

## 16. Defects discovered and fixed

**1. "Today" was UTC's today, not the dairy's.** `resolveRange` computed every
preset window from `Date.UTC`. Defensible while every tenant was Kenyan —
Nairobi is UTC+3, so the two agree for all but three hours of the night — and
wrong for India at UTC+5:30, where between midnight and 05:30 IST the delivery
report asked for the previous day's round and labelled it *Today*. Worse, the
**delivery form defaulted its date the same way**, so an operator recording
the morning round before dawn would have filed it a day early — onto the wrong
month's bill. Both now resolve through the organization's zone.

**2. The mobile record-delivery screen ignored its own catalog.** DEMO-014
wrote `record.delivered`, `record.quantityHint`, `record.amountNote` and the
rest into all three catalogs; the screen rendered English literals beside
them. An Indian dairy could switch to Hindi and its operators would still read
English on the screen they use most. Nothing failed, because a catalog nobody
calls is silently correct.

**3. The portal's delivery report was half in Hindi.** Found in the browser,
on the deployed stack: the per-customer table, the date presets and the
download button read Hindi while the page's heading, description and all four
summary tiles stayed English — `delivery.title` and `delivery.subtitle` had
been sitting unused in all three catalogs since DEMO-014. The same defect as
#2, in the other client, found the same way. Two guards now: one that the keys
exist in all three languages, and one that reads the page's own source and
fails if any of the literals it used to render is still there — a key that
exists while the page ignores it is exactly what happened, and only the second
test catches it.

**4. A test asserted a premise that was false.** DEMO-014's timezone-hierarchy
test picked 22:00 UTC to show Kolkata and Nairobi disagreeing about the date.
At 22:00 both are already tomorrow; the window where they differ is 18:30 to
21:00. The code was right and the test was wrong — it would have passed while
proving nothing.

**5. Money quantized at a hard-coded two decimals in six modules.** Closed by
`core/money.py` reading the currency registry. No arithmetic changed for any
currency in use; what changed is that the assumption now lives where it can be
corrected.

## 17. Known limitations

* **No PDF of the delivery report.** §15 permits CSV *or* PDF "if the existing
  infrastructure supports it cleanly"; receipt rendering exists but is
  receipt-shaped.
* **Customer receipts have no list page of their own.** `/receipts` lists
  supplier receipts (`RCP-`); customer receipts (`CRC-`) appear on the
  customer's page only.
* **The CSV carries `billed` yes/no, not the invoice number.** The number
  belongs to the billing module and a delivery references it by UUID.
* **The statement is not a ledger** — no accounts, journals or ageing buckets,
  by §13's own instruction.
* **The seeded history is one month.** The showcase splits it into two bills
  to demonstrate an opening balance; a genuine multi-month history would
  double a seed that already takes fifteen minutes.
* **The demo tenant carries the verification's own records** — one delivery
  for Sharma Household on 2026-08-14 and the Pillai Household ledger. Both are
  real platform records, created through the API, and both are intended to be
  demonstrated.
* **`phoenix-demo` stores its country as lowercase `in`** where every other
  organization is uppercase. Harmless — `resolve()` normalizes — but it is the
  one row that would break a lookup written the obvious way.

## 18. Recommended next milestone

**Make the dairy's day repeatable without a person.** The chain now works and
is demonstrable; what it lacks is the standing-order automation a real dairy
runs on — generating the day's deliveries from delivery plans, so a round of
three hundred households is confirmed rather than typed, with exceptions
(skips, quantity changes, holidays) as the only manual acts. That is the
difference between a system a dairy can be shown and one a dairy can use, and
every piece it needs — plans, slots, the idempotent delivery record, the
offline queue — already exists.
